# Map an existing project

Map the project so that an Agent starting a change learns from the map, before reading the code, which part to change, the rules it must keep, what else changes with it, and how to verify. Tent drafts the parts from the code and checks the map; you decide the parts and write what they hold. Save each part as soon as it is written, so a session that stops early leaves a map the next one continues.

1. Run `tent workspace scan --draft tent-draft.json`. It writes a `write-many` batch to that file and the full evidence beside it in `tent-draft.report.json`, and prints a short receipt: counts, the guidance files, and findings by kind. Exit 1 means there are findings to settle; both files are written either way. The report has one line per part with its tests, co-changing parts, history and findings; when you reach a part, search the report for `"ref":"@core"` with its own ref to get that line. A Workspace that already has Nodes gets no draft: fill its gaps as the last paragraph says.
2. Read the guidance files it lists, README first, then files such as AGENTS.md, CONTRIBUTING and design notes. Write the project goal and the conventions that hold across the project, as step 3 says, and save them as step 4 says before you read any part's code.
3. Then take one part at a time, a leaf or a small subtree: read its code, its line in the report and its recent history (`git log --oneline -- <path>`), where commit messages name the rules and the changes that travel together. Write its entries in `tent-draft.json` with your own editing tools:
   - **Parts**: each part is a `goal` Node that owns its code; the draft already nests them through `parent` refs. Make the smallest part small enough to read whole before changing it, about ten code files; split a larger one along its subdirectories, import groups, or file-name stems where imports cannot separate it, as inside a Go or Java package. Split it by responsibility even when its files import each other in a cycle or always change together; size comes first. Keep a parent part only where the project itself groups its children. Generated code goes with its source, and tests beside their code go with that code. A separate test directory is not a code part: keep the draft's `Tests` Node with plain directory sources.
   - **Names**: replace path-like names such as `src flask` with what the project calls that part. Keep every `ref`.
   - **Project goal**: add one top-level `goal`, a sibling of the top-level parts rather than their parent, that says why the project exists and what it promises its users, from the README. List the parts' directories and file-name stems as its sources without `track`, so it covers the code it speaks for while the parts keep owning it. Put conventions that hold across the whole project in `prompt` Nodes under it.
   - **Part goals**: the body says what the part is for and what it promises to the code that uses it.
   - **Under each part**: `prompt` Nodes for what grep cannot find: rules this code must keep, including those no single file states, such as who releases what it acquires, what a failure leaves behind, and what existing callers or saved data still rely on; what else changes with it and how to verify; and known exceptions. A decision with its reasons gets its own `prompt` tagged `decision`; a multi-step way of working, such as adding a command or cutting a release, gets its own `prompt` tagged `procedure`. A known open problem from the docs becomes an `output` tagged `issue`. Take each from the guidance files, code comments or commit history, and link the source. Tent keeps the lists of covering tests and co-changing parts current, so do not copy them; write what they leave out: which behavior a change must keep and under which options or modes, which of those tests guard it, and why the parts change together. Where the code implements an outside standard, such as Unicode text segmentation or an RFC, name and link it and say which edge cases the code follows or departs from. Do not list files or entry points.
   - **Rules**: a rule is a promise the project makes, and it names its source: the docs, a test that asserts it, a commit message or a maintainer's comment. Link a section of a long document as `path#Heading`, so an edit elsewhere in it does not mark the rule behind. Keep the rule as wide as its source: a test backs the cases it checks, not every case like them. Do not write how the code works today as a rule; a later fix would read as breaking it. Where the code simplifies or departs from its own docs or an outside standard, record that as an `output` tagged `issue`, not as a rule.
   - **Tags**: give a Node the tags that help find it, from none to several: a form such as `spec`, `decision`, `procedure`, `direction`, `reference` or `issue`, plus the topic words this project uses.
   - **Sources**: a part owns code through a directory such as `{"resource":"src/api/","track":"structure"}`, or in a flat directory through a file-name stem such as `src/flask/views*` with the same `track`; only such a source makes a Node a module. Paths start at the Workspace root. A parent part may keep its own directory: each file belongs to the most specific source that covers it, so files no child claims, new ones included, stay with the parent. Root code such as a package entry or `build.rs` goes as a plain file source in the part it belongs to; root configuration stays in `Setup`.
   - **Links**: links are relative to the Node's own file. A top-level part lives at `.tent/<Name>/<Name>.md`, so it links the README as `../../README.md`, and each level deeper adds one `../`. Link another item of the batch as `[Core](@core)`.
   - **Findings**: a `review` finding names root code with no clear owner; add it to the part it belongs to. An issue such as `module.oversized`, `deps.cycle` or `history.always-together` names refs in `nodeIds` and says how to fix it; change the boundary, or keep an intended exception with one body line such as `allow:deps.cycle [Markdown](@markdown) shares link parsing`. When a cycle or shared history crosses a boundary you split for size, keep the boundary and allow the cycle or history; do not merge back. The `imports` count describes what Tent could not resolve in the code, not the map; leave it and mention it to the user.
4. Run `tent node write-many --draft tent-draft.json`. It saves every entry whose body you have written, removes them from the file and points the remaining entries at the new Node ids. An entry stays in the draft until its body is written, so leave a part's body empty until you have read it. If it names a parent whose body is still empty, write that body and run the same command again; on another error, fix only what it names and run it again. Then go back to step 3 for the next part. The save that empties the draft deletes it and the report.
5. Run `tent workspace check-modules` and fix what it reports until it is clean; keep an intended exception with an `allow:` line as step 3 shows.
6. Start `tent ui --idle-timeout 300` as a background command the user can see and stop. Give the user the address it prints and the part tree from `check-modules --json`: each entry under `modules` has its place in the tree as `path`, its `name`, and its code `files`.

A session that finds `tent-draft.json` continues from it: the entries left in it are the parts still to write, so go on with steps 3 and 4.

To fill gaps in an existing map, map only what `check-modules` reports as uncovered and leave existing parts as they are. A map whose Nodes hold only plain directories has no parts yet: keep those Nodes, add `track` to the code directories that should be parts, make them `goal` Nodes, leave a separate test directory plain, and write them as step 3 says.
