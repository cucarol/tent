# Map an existing project

Give the code a small tree of module Nodes. A module is where later work records what the code cannot hold: rules, change flows, exceptions and decisions. Tent supplies facts and checks the map; you choose the modules.

1. Run `tent workspace scan`. Read the guidance files it lists, such as AGENTS.md or CONTRIBUTING, and the README first. Use its directory dependencies, cycles, generated directories and file-name groups. `--json` has the full lists; take coverage gaps from `coverage.directories`.
2. Draft about ten to fifteen first-level modules that follow the project's own structure. Split a module again only where it is large and its parts change apart. A dependency cycle stays inside one module, generated code goes with its source, and tests go with the code they test when the layout allows. When the files of one large directory import one another in a tangle, split it by dependency layer instead of by feature: files that import nothing above them form the lowest module. `scan --json` lists file imports in `imports.edges`.
3. Each module is a `prompt` tagged `spec`, under one `prompt` that holds the map, or under its parent module. Its code goes in `sources` as `{"resource":"src/api/","track":"structure"}`. In a flat directory, use the file-name stems of its files, such as `src/flask/views*` or `src/core/card-*`, with the same `track`; a module may have several. Only such a directory or prefix makes a Node a module: a Node holding only plain files is not one, and `check-modules` reports its code as `map.unowned`. A module with child modules holds no material that covers them. Root configuration and other files that are not code go in one setup Node as plain file `sources`, never `./`. Code always belongs to a module: a root file that is code, such as the package entry, its root type declarations or `build.rs`, goes as a plain file source in the module it belongs to, and tool scripts such as `scripts/` get a module of their own.

   The body holds what grep cannot find: rules this code must keep, what else must change with it and how to verify, known exceptions, and decisions with their reasons. Take them from the guidance files and docs, and link those. Do not list files or entry points. Links are relative to the Node's own file, and a leading `/` means `.tent/`: a module at `.tent/Map/Core/Core.md` links the README as `../../../README.md`. Link another item of the same batch as `[Core](@core)`; a later batch links it by its Node id.
4. Create all of them in one `tent node write-many --input-json -`, with items like `{"op":"create","ref":"core","parent":"@map","name":"Core","type":"prompt","tags":["spec"],"sources":[{"resource":"src/core/","track":"structure"}],"body":"..."}`. On an error, fix only what it names.
5. Once `write-many` has returned its commit, run `tent workspace check-modules` and fix what it reports. Import lines on stderr, `importIssues` in `--json`, describe the code, not the map: leave the Nodes as they are for them and mention them to the user. An intended exception gets one body line such as `allow:deps.cycle [Markdown](../Markdown/Markdown.md) shares link parsing`. `modules` in `--json` lists the Nodes Tent treats as modules; a Node you meant as one that is missing there needs a directory or prefix source. If `history.always-together` and `module.oversized` contradict each other, follow history: merge the modules and allow the size. After two rounds, stop and show the user the module tree, counting modules as `check-modules` lists them, with the findings that remain.

To fill gaps later, map only what `check-modules` reports as uncovered and leave existing modules as they are. A map whose Nodes hold only plain directories has no modules yet: keep those Nodes, add `track` to their sources and rewrite their bodies as step 3 says.
