# Map an existing project

Give the code a small tree of module Nodes. A module is where later work records what the code cannot hold: rules, change flows, exceptions and decisions. Tent supplies facts and checks the map; you choose the modules.

1. Run `tent workspace scan`. Read the guidance files it lists, such as AGENTS.md or CONTRIBUTING, and the README first. Use its directory dependencies, cycles, generated directories and file-name groups. `--json` has the full lists; take coverage gaps from `coverage.directories`.
2. Draft about ten to fifteen first-level modules that follow the project's own structure. Split a module again only where it is large and its parts change apart. A dependency cycle stays inside one module, generated code goes with its source, and tests go with the code they test when the layout allows.
3. Each module is a `prompt` tagged `spec`, under one `prompt` that holds the map, or under its parent module. Its code goes in `sources` as `{"resource":"src/api/","track":"structure"}`; in a flat directory, a file-name group such as `src/core/card-*` works the same way. A module with child modules holds no material that covers them. Root configuration and small tool directories such as `.github/` go in one setup Node as plain file `sources`, never `./`. A root file that is code, such as the package entry or its root type declarations, goes as a plain file source in the module it belongs to, so module checks include it.

   The body holds what grep cannot find: rules this code must keep, what else must change with it and how to verify, known exceptions, and decisions with their reasons. Take them from the guidance files and docs, and link those. Do not list files or entry points. Links are relative to the Node's own file, and a leading `/` means `.tent/`: a module at `.tent/Map/Core/Core.md` links the README as `../../../README.md`. Link another item of the same batch as `[Core](@core)`.
4. Create all of them in one `tent node write-many --input-json -`, with items like `{"op":"create","ref":"core","parent":"@map","name":"Core","type":"prompt","tags":["spec"],"sources":[{"resource":"src/core/","track":"structure"}],"body":"..."}`. On an error, fix only what it names.
5. Once `write-many` has returned its commit, run `tent workspace check-modules` and fix what it reports. Import lines on stderr, `importIssues` in `--json`, describe the code, not the map: leave the Nodes as they are for them and mention them to the user. An intended exception gets one body line such as `allow:deps.cycle [Markdown](../Markdown/Markdown.md) shares link parsing`. After two rounds, stop and show the user the module tree with the findings that remain.

To fill gaps later, map only what `check-modules` reports as uncovered and leave existing modules as they are.
