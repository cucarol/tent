# Tent V0.1 Specification

This document defines Tent's current public contract. Retired commands and wire fields are removed rather than kept as aliases. Core owns document semantics and local persistence; the CLI and plugin are thin entrypoints. Judgments such as ahead and behind are derived from current context. Events such as reception, verification and material baselines are retained.

## 1. Purpose and workspace

The three semantic concepts are Node, Role, and Card. Tent maintains useful parts of Agent context as linked Markdown documents: Nodes preserve reusable facts and references, Roles preserve a work direction, and Cards record prompt inputs. Normal work, answers, code edits, review and Git integration remain in the host conversation and the user's tools. Ordinary tasks need no Role or Card. There is no separate Return, managed Agent, Session registry, occupation system or task scheduler.

One Tent belongs to one workspace: the directory containing `.tent/`. Its stable `workspaceId` lives in `.tent/settings.json` and survives relocation. Ordinary commands use existing settings; they do not repair, reidentify or register the workspace. Missing or corrupt identity fails explicitly. A saved identity does not establish exclusive ownership across separate copies. Automatic discovery checks each directory for its own Tent and stops at a Git checkout boundary. At a linked worktree, it reads the `.git` pointer and `commondir` to find the main checkout’s `.tent/`, without starting Git. A submodule pointer without `commondir`, a nested clone, or a bare repository without a main checkout does not inherit a parent workspace. CLI commands and hooks share this discovery rule; Node edits from a linked worktree write to the main checkout’s `.tent/`. Material observations, drift and brief read the main checkout’s files, so unmerged worktree changes do not make Nodes behind. Explicit --workspace selects the intended workspace.

`tent new <workspace>` or `tent new --workspace <workspace>` prepares an empty scaffold and independent SQLite history database in a workspace-local staging directory before publishing `.tent/`. When both selectors are supplied, they must resolve to the same directory; a mismatch fails before initialization. Failed preparation removes its owned staging directory and remains retryable; existing `.tent` data is never replaced. Initialization creates no Node, Role registry, remote or empty commit and does not analyze or split the project. The workspace may itself use Git or ordinary files. `.tent/` is excluded from the product repository; its SQLite history is independent. Initialization never edits project files or creates an attachments directory. In a Git project it adds `.tent/` to the exclude file resolved by `git rev-parse --git-path info/exclude`, shared by the main checkout and linked worktrees; existing ignore rules and project `.gitignore` bytes remain intact. Outside Git it writes no project ignore file.

Project instructions remain in workspace `AGENTS.md`. Tent neither copies their authority nor configures third-party analysis applications. Desktop, execution engines and application/format adapters are outside this version. The bundled Web UI reads and edits the same local graph through Core.

## 2. Node and OKF fields

A Node is a directory with its identity Markdown at `<directory>/<basename>.md`. A directory without that identity file is a transparent grouping folder: its Nodes belong to the nearest ancestor Node, or to the root. Placement expresses the parent/child tree; a stable `node-…` id remains the lookup handle across moves and renames. Creation requested by parent ID resolves that identity inside the same Workspace mutation lock as the write: a prior rename follows the original parent, while a missing or ambiguous parent fails without creating a child. Reuse of its old path never redirects creation to a different Node. Tent's Node vocabulary has three types: a Node has one `type`, exactly `goal`, `prompt` or `output`. Any other value, including a `goal|prompt|output-<label>` form, makes the document an invalid Tent Node; it is not converted. Retained versions follow the same rule: pinned Card sources and historical reads treat any other value as an invalid document. A Tent written before this rule is converted once, its retained history included, rather than read through an alias. Form and topic belong in tags. There is no separate kind field.

The filename is the display name. If `title` is present, saves and structural renames keep it aligned; it is not another identity. Names must be portable Windows file names on every platform: creation, rename and batch creation reject `< > : " / \ | ? *`, a trailing dot, and the reserved device names `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, `COM¹`, `COM²`, `COM³`, `LPT¹`, `LPT²` and `LPT³` in any case, with or without an extension. The raw input is rejected if it contains a C0 control character (U+0000–U+001F, including tab, CR and LF), DEL (U+007F), U+2028 or U+2029, even at either end; leading and trailing whitespace as JavaScript `trim()` defines it is then removed. C1 controls (U+0080–U+009F) are not rejected. Tags belong in each document and are aggregated on demand. `tags` is the native cross-cutting field of OKF v0.2 §4.1; Tent gives tags no behavior, registry or lifecycle, and keeps them free text without path separators or newlines. Core exports the suggested `NODE_TAG_PRESETS`: `direction`, `requirement`, `decision`, `spec`, `reference`, `procedure`, `asset`, `evidence`, `analysis` and `issue`. `node tags` without arguments lists the tags of current Nodes with their counts and marks presets; `--include-archived` also counts deprecated Nodes. Unknown YAML fields survive ordinary edits. Invalid identity/type data and duplicate handles are diagnosed, not silently repaired. Unusable subtrees stay outside ordinary content operations; explicit raw inspection remains available where supported.

Record context that will help later work: confirmed goals and constraints, useful reference pointers, observed findings, decisions and facts about real outputs. Goals can exist before implementation; unperformed results cannot. Prefer an existing fact owner and split independently useful context as it emerges. No initial task skeleton, per-turn quota, copied transcript or full-tree maintenance pass is required.

`goal` and stable `prompt` keep confirmed intent, agreements, decisions and their reasons, including who confirmed them and when if known. An Agent decides within its Role; for undecided matters it asks the user in conversation or sends a Card to the Role that owns the decision, then records the settled result as a Node. Agents do not write draft Nodes. A user may intervene by changing any Node, but observing is enough. These documents do not carry commit ids, test counts or merge/delivery status: consult Git and Card history for those records. Useful verification belongs in dated `output` evidence. A Card's reception state is not evidence that its requested work is complete.

### Lifecycle

Reuse OKF v0.2 §5.4 `status: draft|stable|deprecated`; omitted means stable. Status is local to the document. Draft Nodes from other OKF tools remain readable and editable: a draft goal is not a requirement and never counts ahead; a draft prompt supplies no module rules or `allow:` exceptions; a draft output is not evidence and cannot resolve any goal's ahead state. Draft directory declarations do not establish module ownership or coverage, including the confirmed-intent basis of ancestor goals. A stable descendant remains effective under a draft ancestor. Brief adds one draft count and `tent node list --status draft` entry line only when drafts exist, without their contents. Editing, historical versions, material changes, checked-material records and parent status do not change status automatically. Unknown values remain intact with a diagnostic and no assumed currentness; an ordinary CAS edit may preserve them or explicitly replace them with a supported value.

Deprecated Nodes remain explicitly readable and editable without reactivation. Default resource lookup excludes them; hierarchy navigation can expose a deprecated ancestor to reach a current child. Unknown fields, including `mode`, are ordinary metadata and do not control lifecycle.

`node archive <nodeId>` preflights the current subtree and writes deprecated only to documents not already deprecated. It captures selected preimages and returns the immutable event containing the status changes; a no-op subtree creates no commit. `node restore <nodeId> --archive-commit <commit>` accepts a published single-parent event containing only the relevant status-to-deprecated edits. Current identities, paths and bytes must still match, and no later retained change to those paths may exist, including edit-and-revert. Restoration changes only those status declarations, including an originally omitted value; it leaves previously deprecated and newly added children alone. It never rewrites retained history or revives deleted documents. Never-captured external edit-and-revert intent cannot be inferred.

### Materials and links

Reuse `resource` for the primary described material and ordered `sources` for independently related material. Each source has `resource` and may preserve standard or custom descriptive metadata. Source order, repetitions and spelling remain significant. These references locate materials; they do not prove ownership, access, synchronization or a complete impact set.

Local paths use `/` separators. `./` and `../` resolve relative to the declaring Markdown; leading `/` resolves from `.tent` and cannot escape it. A `file:` URI names an absolute filesystem path. Relative paths can reach workspace material outside `.tent`. Queries/fragments and percent encoding retain their reference meaning. Windows drive paths and UNC spelling must use a URI rather than an ambiguous local path. Node creation and writes validate new or changed addresses without requiring external file existence; unchanged legacy addresses remain editable. Source reordering, removal and metadata edits retain existing address occurrences, while additional occurrences require validation. Ordinary files inside `.tent/` cannot be materials: new declarations are rejected with a direction to use Workspace files or Node, Role and Card documents, while existing declarations remain editable and `workspace check` reports them invalid. Recognized native Node, Role and Card references retain their protocols with consistent relative-path and `file:` URI behavior. Ordinary body links are existence references, not material baselines. After native Node, Role and Card reference resolution, a local body link whose decoded path ends in `/` requires an existing directory; a local path without that marker still requires a file. This includes relative, `.tent`-rooted and absolute `file:` addresses. Directory links cannot select a query or fragment. Checking a directory body link does not enumerate or read its members, create a fingerprint or change `sources` semantics.

In stored documents, a bare `sources.resource` can be ordinary description. Tent preserves it as unresolved instead of guessing from an extension or the existence of a similarly named file. Use an explicit `./`, `../`, `/` or absolute URI when mechanical resolution is wanted. A spaced label such as `note: reference` is description; an unspaced URI such as `urn:example:1` is an address. `resource` itself is a material address. Remote URIs are addresses and are not fetched by Tent.

At the CLI boundary, new material declarations in `--resource`, `--sources-json`, `card create --source`, structured write frontmatter and batch create/frontmatter use Workspace-root file or directory paths, including leading `/`; directory addresses end in `/`. They are serialized to document-relative addresses. A Card response source `/cards/<card-id>.md` keeps its `.tent` root in CLI input as well as stored documents; this exception applies only to `sources`, not ordinary Workspace materials or `resource`. Bare sources become paths when they match an existing Workspace file, an explicitly slash-marked directory or a valid final-segment prefix selector; use `./` to explicitly declare a missing path, retaining the final `/` for a directory. `card create` warns on stderr, without changing what it stores, when a source starting with `./`, `/` or `.tent/` names no existing file, directory, Node or Role. Node IDs, absolute URIs and batch `@ref` keep their reference semantics. Unchanged existing material occurrences retain their stored addresses, and batch raw documents keep document addressing. Resource search uses the same Workspace-root CLI convention. `workspace check` reports `unanchored-material-file` for bare stored sources matching an existing local file or slash-marked directory, with a document-relative suggestion; it never rewrites them.

Local Markdown materials (`.md` or `.markdown`, including `file:` URIs) can select a section with a nonempty fragment, such as `../Design/Design.md#State`. The fragment is the heading text, decoded once from percent encoding, not a generated slug. The material version covers that section's text, including its heading and nested sections, ending at the next heading of the same or higher level, with text line endings normalized. For a Node material, its semantic resource/source addresses remain part of the fingerprint; other frontmatter and sections do not affect it. Missing or duplicate headings make the material unavailable; confirmation cannot clear an unavailable material's recorded basis. Batch saves resolve relative material addresses and batch references against the final document bytes. Addresses without a section and fragments on non-Markdown files retain whole-file versioning. This adds no metadata fields, and Card sources still pin complete Node or Role versions.

Standard Markdown links, standard fields and bare known `node-[a-z0-9]{6}` tokens in body text support discovery of related Nodes. Bare tokens outside Markdown link and definition spans form `mention` occurrences, including code and HTML text; unknown handles, longer tokens and self mentions do not. Mentions are never rewritten or canonicalized for semantic fingerprints. One Markdown AST parser drives relationship discovery and link rewriting, including reference-style links. Lookup matches exact identity, path or full name; ambiguous names remain unresolved. Wiki text such as `[[Name]]` is ordinary text. Core saves turn known Node IDs in link destinations, `resource` and `sources.resource` into relative document paths. Occurrences keep their original ranges and declaration paths. Unresolved references are visible. Tent does not add an in-document annotation protocol. Moves/renames rewrite resolvable affected live links and material addresses while preserving unknown fields, source order and occurrences; they do not rewrite historical Card input. Code, quoted HTML and unrelated text are not interpreted as links to rewrite.

Input materials use `resource` and `sources`. An output retains comparison bases for every goal ancestor without extra frontmatter; later changes are informational and never make the output behind. Its nearest goal remains the display owner. Other custom fields survive without transformation or material semantics. The Agent uses its existing tools to read actual materials; Tent provides no application or media adapters.

Markdown paths leaving `.tent` remain external to the Node index, even when an internal Node has the same trailing path. Internal Node renames must not redirect these references; moving the declaring Node adjusts relative addresses to preserve their original material targets.

## 3. Reading, editing and retained versions

### Progressive disclosure

Header discovery resolves identity, hierarchy, status and duplicates without reading unrelated bodies. NodeFs reads frontmatter in 4096-byte blocks and stops at the closing fence; an unterminated header may require EOF to diagnose it. Before sharing or persisting a newly read prefix, its initial path state, opened handle state, post-read handle state and final path state must agree. Derived caches, including the Stop index, retain the state returned with that same header observation; an earlier independent stat cannot identify those bytes. This remains an O(N) live metadata scan, without a watcher or an atomic snapshot of concurrent editor changes.

Read scopes may cache parsed YAML values and original key order under `.tent/.git/tent-material-cache/document-headers.bin`, keyed by the content ETag of validated frontmatter prefix bytes. Header bytes, material fingerprints and revision digests may use the disposable `file-state.json` cache in the same directory. Every request validates the selected files' size, nanosecond mtime, ctime and available device/file identity. A matching entry reuses its observation without rereading source content only when its mtime is earlier than the cache observation time minus the conservative filesystem timestamp window. Racy entries always reread content. The implementation uses a one-second window; nanosecond fields do not imply that the filesystem has nanosecond precision. Content changes that preserve all of those state fields may be missed. `node check <id>` bypasses these state hits and reads the selected Node and required materials by content, including its goal/output comparison scope.

Empty or narrow reads retain other parsed headers, up to 10,000 entries, preferring headers observed by the latest cache update. They do not empty the parser cache between map navigation and detail requests.

Read scopes may also retain Markdown syntax in `.tent/.git/tent-material-cache/markdown-syntax.bin`, keyed by SHA-256 of the exact body passed to the parser. Entries contain link occurrences, mention exclusion spans, destination spans and root heading spans, without resolved Node identities or material versions. Each call applies its current catalog, known IDs, destination mapping, section selection and edit range. A changed body is parsed again; unchanged bodies reuse their syntax across processes. Narrow reads retain other bodies, up to 10,000 entries, preferring bodies observed by the latest cache update.

Semantic content may be retained in `semantic-content.bin` in the same directory, keyed by the normalized body, ordered canonical material declarations and resolved Markdown destinations. Each invocation resolves these inputs using the current document path, Workspace root and Node identity/path mapping, including edits to an existing catalog object; a matching input reuses canonical content without rewriting Markdown destinations. Unrelated Node mappings do not invalidate an entry. Narrow reads retain up to 10,000 entries. This does not cache Node validity or material observations.

Structure material derivations may retain their dependency sets in `structure-derived.bin` in the same directory. Each observation still validates current membership, path types and the source/configuration bytes selected by its coverage. Within one input scope, coverage membership, completed path-type observations and content digests may be shared across materials; the next scope rebuilds them. A hit also requires matching versions of every supporting file requested by the previous import resolution; these files must still occur in the validated listing. Changed input versions, membership or coverage run the ordinary Core resolvers again. Failed validation of a formerly required supporting file falls back to current resolution, since changed configuration may have removed that requirement. Entries hold no Node lifecycle, validity, goal state or complete query result.

One brief, Stop read or authenticated UI GET/HEAD owns one input scope. Already acquired bytes are reused by revision, header parsing, relationships and snapshots; a partial header read supplies its acquired prefix to a later full read. Parallel HTTP requests never share input scopes, in-flight source queries or complete results. Conflict retries and explicit single-Node checks start fresh content observations, and mutation checks do not reuse the surrounding read snapshot. Parsed-value callers receive separate mutable values; YAML aliases, negative zero and preserving edits retain their ordinary behavior. These caches do not hold Node validity or a complete brief/snapshot result. Missing, corrupt or incompatible caches and failed cache writes fall back to ordinary reading/parsing. Cache writes change no project file, Node/Card/Role document, Git commit or reference; native-edit collection retains its normal save and conflict rules.

Within that request, source listing, link rejection and state-cache lookup share one initial `lstat` per file. Parent directories are resolved once per request and must be ordinary directories whose real paths remain inside the allowed root without symlink or junction traversal. A regular file under a validated parent needs no per-file `realpath`; a state-cache hit returns the prior observation without a second path signature check. When source content is actually read, opened-handle and final path identity checks remain independent of those initial observations and reject concurrent replacement. These checks provide request-local observations, not an atomic snapshot; the next request validates paths and file states again.

Core queries return complete metadata and requested text, without CLI byte budgets, pagination or continuation cursors. CLI `node list`, summary reads and parent/children navigation disclose bounded identity, title, type, tags and location metadata. Tent does not project or interpret Node `description`; existing values remain unknown YAML and survive ordinary edits, without a replacement summary derived from body text. Without filters, `node list` returns direct children. `--type <type>` and repeated `--tag <tag>` instead select matching Nodes from the whole subtree under `--parent`, or the Workspace, in tree order; every given tag must match. An invalid `--type` is a usage error. Oversized display metadata is marked and retains a raw `metadataRead` address. Metadata-only responses do not provide a full-document write basis or capture history. A full text read can be required for link relations, but discovery never captures versions. Text search belongs to the Agent's native file tools.

`listWorkspaceRelations` returns Markdown-link, mention and standard-field occurrences from all valid Node, Role and Card documents in one query. Node `relations` exposes these occurrences in both directions, including incoming Role links and pinned Card sources, with source ETags qualifying range reads across all three kinds. It uses the same Markdown parser and material resolution rules, preserving source indices and body ranges. Retained Card sources resolve to their historical identity even after live moves or path reuse; `changedSince` reports retained path changes, including edit-and-revert. Invalid version declarations remain explicit diagnostics. Discovery does not receive Cards or capture history.

`readWorkspaceRevision` hashes identity-document paths, sizes and SHA-256 content digests, order, settings and the current retained event. Digests use file-state validation; a same-size edit with a restored mtime is observed when ctime or file identity changes. It performs no Markdown parsing, capture, repair or background watching; it is a change indicator, not an atomic filesystem snapshot.

`node get` body/raw reads load the selected full document after a matching header observation. `node get <nodeId> --full --json` supplies the complete body and exact ETag for CAS editing; add `--view raw` for the complete original document including frontmatter. The internal `readNodeForEdit` function returns the raw editing snapshot and optionally informational output changes. Complete live `node get` body/raw reads, including `--full`, and complete `read-many` output items expose `changedSince`; historical reads and summaries do not compare later live materials. An initially invalid document, a lookup-to-read conflict and an I/O failure remain distinct errors. `node list --full` explicitly reads the full tree without capturing history; it is not the default discovery path.

`node get` is strictly read-only: it does not capture history, refresh baselines, or compute associations by default. Body/raw reads, including `--full`, expose declared `resource` and `sources` as an ordered `materials` array of decoded Workspace-relative paths (nonlocal references retain their address). Text mode prints one `Material: <path>` line immediately below ETag, including for an empty body, without reading material contents. Oversized metadata follows the existing bounded-read continuation contract. Complete body/raw reads return top-level `nodeId`, `text` and `etag`; partial reads additionally carry the range and continuation. Pure live body/raw reads add `uncaptured: true` when their document bytes differ from current retained event or have never been captured. Text mode explains that the next write, brief or hook collects them; this notice is outside the text and ETag. `role show` and `card show` also use top-level `text` and `etag`. There is no nested `node` alias in these CLI reads. The explicit `--context` option adds a bounded navigation summary (up to 1 KiB), outside the document and ETag, on first/full reads only. Historical and continuation reads do not append it. Context rows show identity, title and type without description or body excerpts; Cards expose their delivery state and return result. Discovery outputs expose unencoded Workspace-relative file paths and applicable Markdown heading names for the Agent's own file reader; brief omits derived Card paths and root paths in favor of their IDs. Stored material addresses and historical version paths keep their canonical semantics.

Pure-read relationship queries and explicit context derive document relationships, hierarchy and material declarations from the latest captured documents in current retained event. Their drift still compares those declarations and retained bases against current external material bytes, using the same inspection rules as brief/check. Material observations do not create history or move bases. Reading a live document does not change the retained document view; `uncaptured` makes the two versions explicit. No material-observation records or observation-only commits are introduced.

Discovery and export remain live: `node list`, summary, resource lookup, `list --full` and `read-many` return current disk content, paths, hierarchy and material fields. New or moved Nodes remain discoverable before capture and carry `uncaptured: true`; changed selected documents carry the same marker, except that header-only resource lookup marks only a new or moved path absent from retained history, never a body-only edit. Their text output includes the same collection notice. This does not change event-derived explicit relations/context or attached drift.

`node search --resource <address>` resolves an explicit material address and returns every valid, nondeprecated, nonarchived Node that exactly declares it or whose directory/prefix material covers the Workspace file. It reuses the shared Core coverage rules. Each Node appears once with its most specific matching material as evidence: exact matches first, then longer coverage prefixes, with stable Node path/id order for ties. The result names the matching field, source index when applicable, address and exact/coverage kind. It reads headers only, never bodies or captured versions, and returns no full-document `etag` or `match.read.expectedEtag`. Its pagination revision follows the returned header information; read a Node separately to obtain content or an editing basis. Ordinary Workspace file lookup excludes `.tent/`, including when a broad directory or prefix could cover it.

Agent-facing Node, Role and Card reads use `text` for body and raw content, including `node get --full`, `node list --full` and `read-many` items. The selected view changes the content, never the field name; read responses have no `body` alias. Structured write inputs still use `body` to distinguish a replacement body from a raw document.

`readNodeTimes(fs, nodeIds)` and authenticated `GET /api/nodes/times?nodeId=...` return selected `{nodeId, contentChangedAt, recordedAt}` rows in first-request order, with duplicate ids removed. `contentChangedAt` is the UTC ISO event time of the latest retained change to the Node's semantic body or material addresses. Creation counts; confirmation, provenance, tags, lifecycle and other metadata do not. It shares the synchronization fingerprint, including canonical material targets and Node identities at each historical version, so moves and their automatic link rewrites do not count as content changes. A retained edit-and-revert counts as the later change. Material file bytes are not observed. Missing/unreadable history or live semantic content not matching its latest retained version gives null, never a guessed filesystem modification time; an unavailable selected historical version does not discard another Node's readable time. Invalid and missing live Node ids retain the normal read errors.

For an output, `recordedAt` is the latest valid declared `generated.at` or `verified.at`, normalized to UTC; it is null for other Node types or absent timestamps. This is a recording/confirmation time for reaction comparisons, independent of the existing earliest-time `outputAt` completion rule. These are recorded clock times, not a proof of causal order. The query reads current selected documents on every request, shares one batch of selected historical versions, and neither captures native edits nor advances baselines. It adds no persistent document fields and does not run in the default snapshot.

CLI Node reads without the complete body or raw document mark their ETag as `read:<etag>`, including metadata, partial pages, non-first fragments and bounded single-save readbacks. This basis can continue reads and support metadata-only edits, but Core rejects it for body/raw replacement with `INCOMPLETE_READ`; callers must obtain a complete live read first. A complete single-response body/raw read retains the canonical ETag. Batch save receipts return the canonical saved ETags for the writer's known complete inputs; they are not discovery reads. The marker prevents accidental replacement from incomplete reads; it is not authorization, a signed receipt or proof against a caller deliberately removing it. Core's complete document reads and UI editing snapshots retain canonical ETags.

Successful CLI Node, Role and Card mutations identify the resolved `workspaceRoot` in JSON and show a Workspace line in human output.

CLI body/raw, search and relation pages share a 16 KiB compact JSON budget. Large display values are marked as truncated or omitted and retain exact source ranges and qualified read addresses; a truncated display is not an executable material reference. Oversized occurrences must not prevent later results from being enumerated. Text ranges use UTF-16 offsets and preserve surrogate pairs and CRLF boundaries. Body excerpts address original text.

Cursors are deterministic continuation addresses usable across short-lived CLI processes, not permissions or signed receipts. They bind source, query, observed revision and position. A changed relevant revision requires a fresh query. Header/hierarchy cursors survive body-only changes, while text cursors require the observed body revision. No cursor secret or Session cache is needed. Role/Card pages carry explicit ETag/range continuations. Summary requests do not accept text ranges, cursors or an expected full-document ETag.

CLI `node read-many` accepts an ordered unique `nodeIds` list and `view: body|raw`, selects documents through Core `prepareNodeBatch`, and applies `start` and a response budget including outer fields. It never captures. An item's partial text continues through live `node get`; outer `page.nextIndex` starts a fresh live batch, not a whole-graph snapshot. Changed files require a fresh read; range, ETag and response-budget checks remain in force.

CLI text reads show Node bodies in both ordinary and full reads, relation kinds and endpoint identities, Card receipts with id/target/state, and drift identities/states/reasons. Failures end with one copyable `Next: tent …` inspection or help command. `node create --id` accepts an unused Node id; existing identities or sibling names fail without overwriting, and a sibling collision identifies its existing Node. Complete first body/raw pages carry ordinary write-capable ETags; only partial Node reads carry `read:` ETags. Mutation receipts remain separate from the minimal read shape.

### Save semantics

`node write --input-json` accepts an observed `baseEtag`, body and/or frontmatter patch, and optional `readBack`. Omitted fields and unknown metadata survive. Raw edits and structured edits use the same Core rules. Identity, type and lifecycle retain their explicit validation. A stale basis is rejected; the CLI must not refresh it just before overwriting.

The default save response contains metadata and the captured event version. Core `readBack` returns requested text from the actual saved bytes without rereading the file; CLI bounds that response. A partial page does not mean the whole body was read. No-op saves validate CAS, avoid rewriting Markdown and still capture newly observed bytes when needed.

Node and Role edits recheck their originally observed bytes after asynchronous reference resolution, before saving or capturing the result. An intervening external edit is a conflict; it does not become a refreshed write basis. Storage errors remain storage errors.

Creation can save body, resource, sources and tags together. An initial file/order failure rolls back the newly created Node. Deletion removes a whole Node subtree without requiring archive first; it does not delete referenced materials or rewrite inbound references. Move children that should survive before deleting their parent.

`writeNodesBatch` / `node write-many --input-json` accepts `{items:[...]}` with ordered `create` and `update` operations. A create supplies a unique local `ref`, `name`, `type`, optional `parent`, body, tags and material fields. `@ref` identifies a Node created by this batch in parent references, Markdown link destinations and material addresses; forward references and mutual links are supported, while cyclic parents and unknown references are rejected. An update supplies an existing `nodeId`, a complete live-read `baseEtag`, and raw or structured changes. Duplicate updates, stale ETags and incomplete `read:` bases are rejected before saving. Input validation identifies the failing item index and field; missing required fields such as `ref` explicitly say they are required.

The batch validates and prepares every final document before writing, holds one Workspace lock, and captures its changed documents in one Tent commit. A failed batch rolls back its own document, directory and ordering changes; rollback failures report affected paths and conflicts while preserving external edits. Existing pending structural recovery runs first under the same lock and retains its separate recovery history. Results preserve input order and contain each saved `nodeId`, `path` and exact `etag`, so known complete inputs need no confirmation read. The batch does not return a copy of every body. No-op batches add no commit when the selected bytes are already retained. The lock serializes Tent writers; it does not make filesystem writes and SQLite atomic against external editors or process termination.

`checkGraph` inspects Node, Role and Card documents without editing, history capture or structural recovery. The CLI `workspace check` first runs the native-edit collection boundary described below. It returns compact `issues` for `unresolved-link`, `invalid-material-address`, `missing-material-file`, `missing-material-section` and `node-git-mismatch`, plus `errors` for documents that cannot be fully inspected. `node-git-mismatch` names a Node identity document that exists on disk but not in the current retained event tree, or exists in that tree but not on disk; it is skipped without initialized Tent history. A section issue identifies a missing or duplicated Markdown material heading; unrelated I/O failures remain inspection errors. Core paths are relative to `.tent`; CLI inspection paths are Workspace-relative. Local material checks use Workspace-relative and absolute `file:` resolution. For a leading-slash body link missing under `.tent`, if the same file or explicitly slash-marked directory exists from the Workspace root, the unresolved-link reason gives the correct document-relative link, retaining URI encoding, the directory marker and any valid query or fragment. This diagnostic neither changes the leading-slash anchor nor rewrites the document. External URIs and plain source descriptions are not fetched. Retained Card sources are checked against their complete pinned versions. CLI exits zero for a clean report and one when issues or inspection errors exist, retaining the JSON report on stdout. This checks addresses, file or directory presence and selected section availability, not semantic freshness; `node check` remains the separate per-Node material-version comparison.

Explicit `node create`, `write`, `append` and `write-many` receipts include advisory `warnings` when a goal or prompt declares a local file material that is not tracked by its owning Git index. The hint recommends `output` for a result observed at one time, because the untracked file's old bytes are not retained for a content comparison. Both `resource` and `sources` count; output Nodes, directory/prefix coverage, remote or unresolved sources, and Tent identity documents do not trigger it. Missing files or Git inspection failures are not guessed to be untracked. This advice is not stored in the Node and does not change its type, synchronization basis, write success or confirmation rules. The Core write result and the HTTP Node-save response carry the same advice; CLI text prints it once and JSON keeps the array. It does not add work to brief or drift, nor retain material bytes.

Those receipts also advise when this write adds a whole local Markdown material to a goal or prompt and the document has at least two sibling section headings below its title. Changing a section reference to a whole-document reference counts as adding the whole material; retaining a whole reference does not repeat the advice. Markdown syntax determines headings, excluding code blocks and frontmatter. Both ordinary files and Tent identity documents qualify. Section references, directory/prefix structure, remote or unresolved sources, outputs and unreadable materials do not trigger this hint. The advice recommends specific sections when those are sufficient; it never rewrites declarations, changes a type, or confirms a synchronization baseline.

### Native file reads and edits

Agents can read a Node's Markdown through their native file reader and edit its body with tools that check the old text. Node creation, material declarations, explicit confirmation and Card protocol operations remain available through the CLI. Before Node, Role and Card mutations, Workspace export/brief/check/drift and SessionStart hooks observe the Workspace, Core compares current Node bytes with independent current retained event and collects valid edits under the mutation lock. Tool hooks use only native successful results and existing module coverage; they do not collect edits or acquire the mutation lock. Stop is silent. Pure CLI reads (`node get/read-many/list/search/relations/history`, tag discovery, `role list/show`, `card list/show/get/watch` and `workspace scan/check-modules`) do not collect native edits or capture their selected documents. Help and pure Core queries do not collect edits.

Collection retains the exact native file bytes without rewriting the document or inventing producer metadata. Valid frontmatter changes use the same identity, material, provenance and lifecycle validation as CLI raw edits. Existing material and goal bases remain unchanged; newly declared materials follow the same save rules as CLI additions. Invalid YAML or metadata is left untouched and uncaptured, quarantined for the current command, and listed in full by workspace check; brief shows the first 10 with a true total and inspection command when more exist. Untracked new files remain discoverable by check; create Nodes through the CLI. A later native repair is checked again against retained bytes. Storage failures and unstable observations are never classified as invalid frontmatter.

An unchanged collection probe needs no mutation lock. If its initial document scan detects changing bytes, collection acquires the lock and observes once again before validating or capturing anything. A concurrent-edit failure during that locked observation still fails collection; storage failures do not trigger another observation. This never retries a save or a caller's action.

Each boundary retains the final bytes it observes. Two edits separated by collection boundaries retain two versions; intermediate edits between boundaries are not automatically recoverable. Native tools remain responsible for avoiding lost updates; Tent does not add a second editing harness.

### Appending

`node append <id> --body <text|-> [--heading <title>]` appends to the current body under the Workspace mutation lock without a preceding read or ETag. The optional plain-text heading selects an existing section and appends at its end, including after nested subsections; when absent from the body, it creates a level-two heading. Duplicate matching headings are an explicit error, and headings in code blocks do not count. The boundary has one blank line and a normalized trailing newline. Successful concurrent appends do not overwrite one another. CLI writes wait briefly to acquire a busy lock before reporting a timeout; they never retry an action already started or bypass its ETag check. It returns the saved full-document ETag and event version. Use this operation for additions instead of reading and replacing the entire body.

Appending uses normal address validation, Node synchronization and history capture. It does not confirm existing material or output bases and cannot clear their drift. Agents edit type, tags and body text through their file tools or `node write`; full-document CAS remains required when using the latter for replacement.

### Captures and diffs

Explicit saves capture selected identity documents' exact UTF-8 bytes into immutable events in `.tent/.git/history.sqlite`. Core Node, Role and Card reads capture only when explicitly requested with `capture: true`; ordinary UI browsing can stay read-only. Pure CLI reads, including `node read-many`, never request capture. A partial batch item continues against live bytes; an unchanged file continues, while a changed file rejects its cursor and requires a fresh read. Range, ETag and output budgets still apply. No-op selected captures create no new commit. Historical queries themselves do not capture. An explicit Core capture while reading one page retains the source document; it does not claim every page was read. Never-observed editor intermediates are not recoverable by contract.

Capture publishes only the selected bytes and changed Node basis records in one synchronous SQLite transaction. The authoritative store is `.tent/.git/history.sqlite`; `.git/` is retained as an operational directory for the database, file transaction journal and disposable material caches, without a private Git history repository or backend fallback. A read never initializes an absent history store. Card publication and reception require initialized Tent history. Project-repository Git observation remains independent and read-only; initialization keeps its existing controlled local-exclude behavior when Git is available.
`version: {commit,path}` names a complete history-document path within `.tent`. `node get --version-json` reads that exact Node after live edits, rename or deletion. Core `readDocumentVersion` also reads Role and Card documents and `canvas.json`. Core `readDocumentDiff` compares two captured documents for the UI and reports path changes separately. Historical continuation binds the retained source, and cannot silently fall back to live bytes. The existing historical reader source label `kind: git` remains a wire label for a fixed version, not a backend selector. The Web map lays every topic out itself and keeps no coordinates for topics. The fixed `.tent/canvas.json` file stores only what a person chose. These attachments and line endpoints create no Tent relations. Regions, coordinates for topics, the old `forms`, grouped position layers, and versions 1 and 2 are rejected, without compatibility reads or automatic conversion. References to absent Nodes are retained; Core never prunes the canvas. The file is limited to 5 MiB of UTF-8, participates in workspace revision, history/diff and complete export, and carries no Node/Role/Card identity.

Failures report affected paths and preserved external edits instead of a false complete success.

### Node synchronization and outputs

`Tent-Node-Record` is a commit-message trailer in the independent repository at `.tent/.git`. Each line contains a JSON pair `[nodeId, record]`, validated as `NodeBasisRecord` in `src/core/base/node-basis-record.ts`; a commit can carry records for several Nodes. Version 1 records carry `v: 1`, ordered material identities and observed content versions, optional fingerprint versions, a coverage goal's own intent basis, and an output's ancestor-goal bases with their observed materials. Same-version extension fields are accepted. The record is written with the affected document when its basis changes, outside Markdown frontmatter.

All fields below belong to record version 1. Core's `prepareNodeSyncSave` constructs records for creation, saves and confirmation; the SQLite history validates and writes them in event records. `DocumentHistory.nodeRecords` validates retained records for current synchronization inspection. CLI and UI do not interpret trailers independently.

| Field                               | Version 1 value and meaning                                                                                                                                                                                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`                                 | Required literal `1`; selects the record schema.                                                                                                                                                                                                                     |
| `materials`                         | Required ordered array of this Node's material bases, including an empty array.                                                                                                                                                                                      |
| `materials[].identity`              | Required canonical material identity. Local `file:` URIs use `file-sha256:<hex>`; declarations that cannot be resolved use `unresolved-sha256:<hex>`. Their raw addresses are not retained in the record.                                                            |
| `materials[].version`               | Optional 64-character lowercase SHA-256 content digest; absent means no sampled version.                                                                                                                                                                             |
| `materials[].fingerprintVersion`    | Literal `2`; required when `version` is present, optional otherwise.                                                                                                                                                                                                 |
| `materials[].structureDependencies` | Optional structure basis: sorted unique external targets, directories ending in `/` (Workspace root is `./`) and file targets without a trailing slash. Its digest must match `version`, including in ancestor-goal bases. An observed empty dependency set is `[]`. |

Same-version extension fields at any object level survive reading, but do not supply a baseline for known fields. Capture and export reject machine-absolute paths even in extensions. The record version and semantic fingerprint version are separate: the former selects the shape, the latter identifies the digest algorithm. Retired `repository` and `directoryFiles` fields are tolerated as opaque extensions when reading old records, ignored by synchronization, and omitted from newly constructed bases. Existing history is not migrated.

Ahead is a current finding with reasons; there is no inferred start time. Captures do not write acknowledgment trailers, and readers ignore old `Tent-Output-Acknowledged` fields without changing history.

`DocumentHistory.nodeRecords()` reads the latest record for each Node on the retained event sequence. Missing, unversioned, unsupported or invalid records provide no baseline for that Node, while other Node records remain usable. A newly written versioned record containing a machine-absolute path cannot be captured or exported. Migration preserves original historical bytes for audit, validates imported records, and retains invalid or unsupported records as unknown bases. An output without a usable record has unknown comparisons; metadata or structural edits cannot invent its baseline, and unknown comparisons never make a frozen output behind. One explicit confirmation establishes its current basis when its materials are readable. Ordinary saves cannot invent missing existing bases; new material declarations can acquire their own initial observations while previous unknown bases stay unknown. Core's `retainedNodeRecords` uses these bases for synchronization queries. CLI and UI consume these Core results; the SQLite event records are authoritative.

`node check <id>` computes independent `ahead` and `behind` findings from the current Node and local materials without changing Nodes or capturing history. A goal can have both findings; each counts separately. Neutral synchronization details remain available on inspection without becoming a task or map mark. These facts are independent of OKF v0.2 §5.4 lifecycle `status`. A matching version proves only that recorded bytes still match, not semantic correctness. Unavailable or remote versions remain explicitly unknown; inspection makes no network requests.

Creating or saving a Node automatically observes local `resource` and `sources` with SHA-256 of the selected Markdown section or, without one, the whole file. The basis is retained by Node ID in the same SQLite event as the document, outside frontmatter. The retained event sequence supplies the current record. Derived file observations reuse a local file-signature cache across CLI invocations, separating complete files and individual sections. No manual hash input is needed. Every ordinary save retains existing material and goal versions, including an output whole-body rewrite and native file edits. Only creation or explicit confirmation establishes or refreshes existing dependencies. Metadata edits, no-op saves and equivalent line-ending changes cannot clear `behind`. New declarations are observed on save; unavailable known materials retain their old basis. Document reads never refresh it; native collection preserves old bases and observes only newly declared materials. Batch writes record final saved documents and bases together and roll both back on failure before the SQLite commit.

A local material address ending in `/` declares directory coverage in either `resource` or `sources[].resource`. It follows the same CLI and stored-address rules as a file, preserving the trailing slash; queries and fragments are invalid. Without `track: structure`, a directory supplies coverage for resource lookup and module checks, but no content fingerprint, baseline or changed-file list. Adding, deleting, renaming or editing its members does not make a Node or dependent output behind. Declaration and link-output checks retain lightweight address and directory-existence validation without recursively reading members. A rule that must follow content names the specific file or Markdown section.

Structure observation leaves project files, Node/Role/Card documents and Git commits/references unchanged. It does not execute Git filters, fetch missing objects or initialize repositories. Nonignored current members use trustworthy Git ignore interpretation; tracked ignored members remain excluded. Outside project Git, Git interprets Workspace `.gitignore` rules using the empty `.tent/.git/ignore-context/.git` tool context without private or global excludes. Workspace initialization and one-shot migration setup create this unborn context with an empty template and Git's native filesystem defaults; no history commits or ref publication use it. Observations never initialize it. Missing Git affects only this interpretation's availability, not SQLite initialization or document CRUD. Without a trusted interpreter, rules requiring interpretation make the observation unavailable. Workspace enumeration independently excludes `.tent/`, including root-directory and `.t*` coverage, regardless of ignore rules. One inspection may share listed path types between its live/tracked listings and material resolvers; later inspections observe them again, including missing paths and errors. These listing types never replace the live path, symbolic-link and file-identity checks used when reading source bytes. Concurrent ancestry checks in one request may share an in-flight path query; a finished query never authorizes a later read. Final file-identity checks always issue their own fresh query, including when another ancestry query is still pending.

File and section materials are read only at their declared live location. Missing or unreadable materials are unavailable and remain behind; Tent does not search other checkouts or substitute retained Git blobs. No repository locator is recorded for fallback.

A local address ending in one `*` in its final segment declares prefix coverage, for example `src/core/card-*`. It covers paths beginning with that prefix, including nested paths. Other wildcard positions, multiple stars, queries and fragments are invalid. Without `track: structure`, prefixes supply only coverage, with no member-content reads or baselines. The parent directory must exist for existence checks; an empty match is valid. Prefix and directory membership share `src/core/base/material-coverage.ts`; no child module is automatically subtracted, and `.tent/` never belongs to Workspace file coverage.

Only a `sources` entry can opt into structure observation with `track: structure`, and only for a directory or prefix material. Omitted `track` keeps directory/prefix coverage only; top-level `resource` does not enable structure tracking. A module is a Node with at least one such explicit structure source; tags never enable this behavior. Structure means the set of outgoing local dependencies from member production files, using the shared `extractRepositoryImports` static extractor. Test-file imports do not participate. For each structure source, internal targets are the union of the same Node's structure-source members, resolved with the shared member rules. Ordinary coverage sources and other Nodes do not expand this union. Each source retains its own outgoing dependency set and baseline; only target exclusion uses the union. External targets are grouped by directory, except a nonmember sibling in the importing member's directory is represented by its file path, so a prefix group can distinguish its neighboring files. Incoming dependencies, file membership and ordinary content changes are not part of the fingerprint. Creating, deleting or renaming files changes a structure fingerprint only when the outgoing target set changes.

Structure observations retain `structureDependencies` outside frontmatter. `node check` exposes up to 20 `changedDependencies` in target order, each with `target` and `state: added|deleted`; `changedDependenciesOverflow` reports any omitted count. Coverage and structure declarations of the same address can coexist; only the structure declaration stores a basis. The `track` mode contributes to goal and Node-material semantic fingerprints, so changing it is a material declaration change visible to dependent outputs. Old directory-content records are ignored without migration. Existing baselines still move only through the normal creation, new-declaration and explicit confirmation rules; editing prose does not silently acknowledge changed material.

Structure observation inherits the shared extractor's supported languages and resolution limits; it is not a syntax validator or a guarantee about runtime dependency behavior. Unsupported languages supply no import edges. Reported relevant resolution failures and unreadable required bytes leave the observation unavailable; no partial set is confirmed as a complete dependency basis. Reads retain the same zero-authoritative-write boundary as content observation.

A Go import targets a package directory. If all of that package's production files are members, the edge is internal; if none are members, the package directory is an external dependency. If only part of the package belongs to the Node's structure-source union, the observation is unavailable and identifies the partially overlapping package. A package-level edge cannot establish which individual nonmember files are dependencies, so it must not be discarded or expanded into guessed file edges.

A structure-tracked module's prose can become stale after code-content edits without mechanical drift. Turn-end review is best effort: shell or external-editor edits absent from the observed turn, cancelled turns and undelivered prompts may never be raised. A rule that must follow specific content must also name that file or SPEC section as content material. Fewer structure alerts do not establish greater accuracy or complete content freshness.

Goal and Node-material semantic fingerprints contain LF-normalized body text, ordered canonical `resource`/`sources[].resource` addresses and explicit structure modes. Type, tags, provenance, lifecycle, descriptive source metadata and Card response edges do not contribute. Ordinary text materials normalize line endings; binary bytes remain exact. Confirming an upstream Node without changing its meaning does not make consumers behind.

An output records a result at one time. Changes to its own materials or any ancestor goal never make it behind, regardless of tags, including `asset`. Only an explicit `stale_after` expiry makes an output behind. Its retained comparison bases still cover its own materials and every goal ancestor between it and the root, including deprecated or archived ancestors. A goal's body, ordered material addresses and materials are compared independently of type, tags, lifecycle and verification metadata. Confirming a goal refreshes its own material basis and, when it or a current descendant goal declares local Workspace directory or prefix coverage, its own intent basis; it does not refresh any output's comparison bases. A batch uses the final saved goal and material bytes regardless of item order.

Unavailable baselines remain unknown. Reads do not reconstruct, confirm, rewrite, migrate or bulk-confirm old records.

Complete live output reads return informational `changedSince` entries when recorded and current versions actually differ. Each entry is `{kind: "material", resource}` for an own material or `{kind: "goal", nodeId, name}` for the nearest goal (the first goal upward, skipping intervening prompts and outputs). More distant goals do not produce notices; their retained bases and comparison states remain unchanged. Each changed goal appears once even when both its body and materials changed. No changes means the field is omitted. These entries are separate from the Node text and never enter the brief's behind list. Inspection retains exact material addresses, goal IDs and distinct recorded/current versions; unavailable or unknown comparisons are not claimed as known changes. Explicit output confirmation refreshes its comparison bases and verification time, clearing the changes that can be observed. Reads and ordinary saves do not refresh those bases.

`readOutputComparisons` provides a pure selected-output batch using the same observation as synchronization. Each result has `nodeId`, nearest-first `goals: [{goalId, state}]` and `changedSince` (an empty array when no change is known). A goal is `current` only when its body and all comparable materials match the output's retained basis; any proven difference makes it `changed`, otherwise a missing basis, unreadable material or inconclusive inspection makes it `unknown`. Unknown never claims a change or a match. An ancestor body that cannot be read is locally unknown; other ancestors retain their completed comparisons, while known changedSince entries remain limited to own materials and the nearest goal, and other selected outputs still return. Output expiry and its own material changes do not alter goal comparisons. Duplicate output IDs are read once in first-request order; unknown IDs and non-output Nodes are rejected. The query captures no native edits, writes no baselines and does not inspect unrelated output bodies. `GET /api/outputs/compare?nodeId=<id>&nodeId=<id>` exposes this batch to the authenticated bundled UI on demand, independently of the snapshot cache; it adds no automatic snapshot work.

Every `goal` is a requirement regardless of tags. A goal declaring at least one local Workspace directory or prefix in `resource` or `sources`, or having a current descendant goal with such coverage, retains its own semantic intent basis on creation or explicit confirmation. Grouping goals use their own body and declarations for this basis; child intent is not folded into it. Adding a qualifying descendant does not silently establish a missing parent basis. Batch creation and confirmation use the final hierarchy and declarations. Ordinary saves and native capture preserve it. Matching that basis clears ahead independently of outputs; a missing or changed basis requires confirmation or a matching current output. Single files, Node/Role references and external URLs do not qualify, and `track: structure` is not required. Its material drift remains an independent behind finding. For goals without this coverage, a goal without any active `output` anywhere in its subtree is ahead. When there is no matching own intent basis, outputs clear ahead only when at least one current output has retained baselines matching that goal's current body and all its materials. Missing or unavailable comparisons cannot establish a match. One output must match the whole goal; partial matches from different outputs cannot be combined. An output under a nested goal can satisfy its ancestor goals independently. Confirming one output or creating a new matching output clears ahead without refreshing the older outputs' informational changes. This uses the existing current-output scope, adds no time fields and replays no history. A change to an output's own material alone does not make its goal ahead. ### Authorship, verification and expiry

Readers also accept OKF's single verification mapping.

The draft summary and live `check-modules --json` module facts include two current, derived fields. They are computed from repository evidence, never written into Node bodies or retained as coverage claims:

- `testedBy: string[]` lists distinct, sorted Workspace-relative test files with direct static imports into handwritten production members, plus uniquely resolved static re-export definitions for names proved to be used as values by those tests. An existing Core test-to-entry import edge is required; re-export attribution never creates a missing entry edge or relaxes a language parser's condition/build-context limits. Tests, generated files and vendor files are not production targets. No test execution, transitive helper coverage or implicit same-package reference is inferred. - `coChanges: {moduleId, sharedCommits, moduleCommits, ratio}[]` lists non-ancestor module pairs meeting the existing history thresholds below. `moduleCommits` counts eligible commits touching the current module, and `ratio` is `sharedCommits / moduleCommits`, so the two directions can have different ratios. The pair is selected using the less-frequently changed member's ratio and lift, as in the history rules. Core's `MODULE_MAP_THRESHOLDS` defines these rules:

- `map.uncovered`: tracked files with no coverage, grouped by immediate parent directory. This rule cannot be excepted; generated and vendor files still need a covering Node.
- `map.unowned`: covered handwritten production code files without a module owner, grouped by immediate parent directory. It uses the same code classification as the size rules, excluding tests, generated and vendor files. Coverage by an ordinary Node does not establish module ownership. This rule cannot be excepted; add a directory or filename-prefix structure source to the responsible Node, or attach the files to an existing module. Module identity and the Stop entry point remain unchanged.
- `module.oversized` / `module.skewed`: only leaf modules with at least 20 handwritten production code files qualify; tests, generated and vendor files are excluded. A module must exceed 20% of repository production files, or strictly exceed three times the mathematical median of its other nonempty sibling modules. It must also contain at least two directory or filename-prefix groups of at least three production files each. Oversized takes precedence over skewed.
- `deps.cycle`: a pair has `module-load` imports in both directions, with at least three such imports in the smaller direction and a smaller/larger ratio of at least 10%. Deferred, type-only and compile-time occurrences contribute neither counts nor ratios; a separate loading occurrence of the same import still counts. Tests and `index.*` barrel files are excluded; ancestor/descendant module edges are internal. Go package targets use directory-material ownership, or the unique module owning all direct non-test Go files in the package, not a fabricated target file. A package split among modules without a directory owner is reported as unassigned, rather than inventing a dependency edge. Execution filtering does not remove dependency edges, test-attribution evidence or unassigned-import diagnostics.
- `history.always-together`: a pair shares at least five commits, at least 90% of the less-frequently changed member's commits, and lift of at least two. Lift is shared commits times eligible commits divided by the product of individual commit counts. History follows first-parent and excludes empty commits and commits changing more than 50 files. Ancestor/descendant module pairs are excluded from both history rules.
- `history.generated-apart`: the same history thresholds, but more than half of at least one module's member files are generated. It replaces `history.always-together` for that pair.

A size rule is excepted when its exact positive marker `allow:<rule-code>` appears in that module's body, without spaces around the colon. A pair rule is excepted when either module has a body line containing that marker and a resolvable Markdown link to the other module, such as `allow:deps.cycle [other](../other/other.md)`. Merely mentioning a rule code, including saying it must be fixed, does not declare an exception. No prescribed heading or duplicate declaration is required; an unrelated link, a link on a different line or a code-fenced link does not declare a pair exception. `map.uncovered` and `map.unowned` cannot be excepted. Rules in active descendant prompt Nodes apply to their nearest module ancestor, stopping at nested modules. Pair links resolve relative to the prompt document before applying to that module. Goal and output descendants do not supply rules. Exceptions never change stored documents or hide inspection failures.

Import extraction is a pure Core function over Workspace-relative POSIX paths and caller-supplied file contents. It resolves literal TS/JS imports, exports, require and dynamic import calls through relative paths and scoped `tsconfig*.json` paths aliases; Go module-local imports target package directories; Python imports resolve repository-local files under the root, `src` or `lib`, including relative imports. Extensionless script targets try `.ts`, `.tsx`, then `.d.ts` before JavaScript suffixes; directory index candidates likewise try `index.ts`, `index.tsx`, then `index.d.ts` before JavaScript indexes. Edges are deduplicated and ordered; unresolved relative imports and unparseable configurations are reported separately, without claiming complete language/compiler analysis. Source/configuration reads never follow symbolic links.

Every `RepositoryImport` has a mandatory `execution` classification. All classes remain dependency evidence, including for structure observations, module edges and direct test attribution. Occurrences with the same importer, target and specifier but different execution classes remain distinct; an eager occurrence cannot be erased by a type-only or deferred occurrence.

- `module-load`: a source-level runtime load outside a function body, including ordinary Python imports, script imports/re-exports and literal top-level `require`/dynamic `import`, PHP include/require expressions, and Go package imports (which establish package initialization order). Ordinary conditional branches are conservatively included; this is possible loading evidence, not proof that the branch runs.
- `deferred`: Python imports in function/method bodies (including nested and async definitions), script literal loads in function/method/arrow bodies or default parameters, and PHP include/require expressions in function/method/closure/arrow bodies. A class body in Python executes while the class is defined and inherits its enclosing context; a method body is deferred.
- `type-only`: TypeScript declaration-wide `import type`/`export type`, type-only import-equals declarations, all dependencies in `.d.ts`/`.d.mts`/`.d.cts` files, and Python imports under a recognized positive `TYPE_CHECKING` suite. Python recognizes imports of `TYPE_CHECKING` from `typing`/`typing_extensions`, their aliases, and qualified module aliases, with optional parentheses. Nested suites inherit the context. Runtime `else` branches, negated guards and compound conditions do not become type-only by assumption.
- `compile-time`: Rust module/use declarations, Java imports, C# using directives, C/C++ preprocessor includes and PHP namespace use declarations. These establish source/name dependencies; the extractor does not claim that these declarations load or initialize the referenced code at runtime.

Classification uses lexical source context, not a call graph, interpreter, type checker or build pipeline. It does not evaluate immediate function invocations, decorators, runtime rebinding of typing guards, arbitrary constant conditions or compiler-dependent semantic import elision. In particular, inline TypeScript modifiers such as `import { type T }` and `export { type T }` remain `module-load`, as `verbatimModuleSyntax` can retain an empty import/re-export with a module specifier; mixed type/value declarations do too. Only declaration-wide type syntax guarantees erasure independently of those emit choices. Complex script type expressions and class field initialization are not analyzed as execution contexts.

The current proof subset recognizes unambiguous value calls/construction and Python decorators, Python top-level `from ... import ...`/literal `__all__`, relative JS/TS re-exports, and unconditional file-based Rust `pub use` chains from determinate namespace imports. Other syntax may conservatively retain only its entry evidence. No interpreter, compiler, external package resolver or source execution is used. A test helper classified by its path can itself import production code, but its consumers are not credited with its imports. No test execution, transitive helper traversal, implicit same-package references or runtime coverage is inferred. Inline unit tests inside production files and custom test paths not recognized by the shared test classifier are not attributed. Full Cargo target selection, custom source sets and other build-tool inference remain outside this evidence.

Rust extraction reads supplied `Cargo.toml` static package/target/dependency fields, including workspace edition/dependency inheritance, renamed path dependencies, custom library names and explicit binary paths. Explicit library targets retain the default `src/lib.rs` path when omitted, including with `autolib=false`. Library and binary discovery switches are independent: a default library remains discoverable unless `autolib=false`, regardless of other target declarations; binaries remain discoverable unless `autobins=false`, except that Rust 2015 defaults to no additional inferred binaries when a `bin` table is present. An explicit `autobins=true` enables those additional binaries. Other target classes do not disable binary discovery. A target's explicit edition overrides its package edition for import resolution. A local crate is reachable through a declared path dependency, or a binary's own package library; sharing a workspace alone does not establish an import. Default library/binary/build-script roots and regular `mod name;` declarations establish file module contexts; inline modules preserve their declared directory and parent context. Both module declarations and `use` paths produce file edges. Nested use groups, alias bindings, `self`, `super`, `crate`, edition-dependent bare roots and enum variants resolve through known module/item declarations. Ordinary expression groups, arrays and call/closure arguments preserve block-local use declarations. Globs contribute evidence for the named module or enum file only. They never expand into inferred symbol/file dependencies. Rust nested comments, quoted/byte/raw strings and character literals cannot create imports; lifetimes do not mask later declarations. Exact `#[cfg(test)]` items and `#[test]` functions are omitted, including their regular file modules.

Rust extraction does not evaluate Cargo, features, target selection, build scripts or macro expansion. Conditional dependencies, other `cfg`/`cfg_attr`, `path` attributes, procedural generation, unknown macros, `include!`, generated source, ambiguous modules, alias/re-export chains, unavailable required bytes and files without a known Cargo/module context produce explicit diagnostics. Direct re-export declarations can supply an edge to their known definition; consumer paths through re-export bindings remain unresolved. Standard-library names and manifest-declared external dependencies supply no local edge; unknown names are diagnosed rather than classified as external. Cargo patch/replace resolution is unsupported and diagnosed. Known limitation: when an explicit binary changes the path of a target with the same name as a default binary, the default entry may still be included and contribute additional edges; extraction does not reproduce Cargo's complete target-inference rules. This is static import evidence, not a complete Rust symbol or runtime dependency graph. For a narrow structure material, pure Core requests its own Cargo ancestry, declared local dependency configurations, root/ancestor declarations and the source bytes needed to resolve member use paths. FS fulfills those requests through its existing inspection-scoped shared reads. Independent packages and unused sibling module bodies are not required bytes; their configuration/source failures do not poison the observation. Materials with no Rust members do not inspect Rust context. Failures in actually required configuration, ancestor or used dependency bytes keep the basis unavailable.

Java extraction indexes declared packages and top-level/nested classes, interfaces, annotations, enums and records from supplied production `.java` bytes. Explicit type imports, single static imports and static wildcard imports contribute file edges only when their named type has one known local definition. A static member import targets its named declaring type's file; a nested type import targets that nested declaration's file. Comments, character/string literals and text blocks cannot create declarations or imports. Duplicate local definitions remain ambiguous; build classpaths do not select one. Unresolved `java.*`, `javax.*` and `jdk.*` names supply no local edge. Other unresolved imports and ordinary wildcard imports remain diagnostic; wildcard packages never fan out into speculative file edges.

Java build collection reads `pom.xml`, `build.gradle[.kts]` and `settings.gradle[.kts]` without executing Maven or Gradle. Standard `src/main/java`, literal Maven modules/sourceDirectory (including a leading `${project.basedir}/` or `${basedir}/`) and literal Gradle project includes describe source roots. Repository-wide declared types are candidates regardless of build reachability; this is import evidence, not a verified classpath. Malformed/unavailable configuration, unresolved source-root/module expressions, Maven profiles/plugin-added roots, Gradle sourceSets/custom project directories/applied scripts/composite builds and dynamic includes produce diagnostics. Parent-POM inheritance, dependency/classpath selection, generated declarations, build profiles and custom Gradle source-set evaluation are not reproduced. Same-package implicit references, fully qualified expression uses, inheritance/reflection and complete JPMS semantics are outside this import graph; `module-info.java` and Unicode escape preprocessing are explicitly diagnosed. Narrow structure observations request their Java build ancestry and direct source files in candidate import packages, including potential enclosing-type packages, to index differently named compilation units. Required source/configuration failures keep the observation unavailable; independent packages and non-Java materials do not require Java context.

C# extraction indexes declared namespaces and top-level/nested classes, structs, interfaces, enums, records and delegates from supplied production `.cs` bytes. Block and file-scoped namespaces, relative qualified names, escaped identifiers and `global::` qualification are recognized. Ordinary, global, static and alias using directives are parsed; static type imports and type aliases contribute a file edge when exactly one reachable local definition is known. A global directive records evidence from its declaring file; consumers without a directive are not inferred. Namespace using directives, including namespace aliases, do not identify a dependency file and remain diagnostic rather than expanding into every namespace member. Duplicate/partial declarations remain ambiguous. Unresolved `System` names supply no local edge; other unresolved names remain diagnostic. Comments, character literals, ordinary/verbatim/interpolated/raw strings and using resource statements cannot invent imports.

C# projects use the closest containing `.csproj` directory with conventional descendant sources and literal, Workspace-local `ProjectReference` paths, including Windows separators. References bound candidate declarations and are followed transitively without executing MSBuild; project references alone do not create source imports. Namespace shadowing uses the same reachable-project scope as type lookup. Files without a containing project use repository-wide declaration candidates. Multiple projects sharing a source directory are diagnosed. Malformed/unavailable project bytes, dynamic/conditional references, missing local project targets, custom `Compile` items, imported MSBuild configuration, `Directory.Build.props/targets`, implicit usings and conditional source compilation remain diagnostic. Standard descendant layout is retained when unsupported configuration is encountered. MSBuild property/profile/target evaluation, linked/generated sources, complete compile-item selection, alias chains, extern aliases, generic using aliases, Unicode escape identifiers and implicit same-namespace/expression references are not resolved. Narrow structure materials request their containing/referenced projects and production declarations within that scope, since C# namespaces need not match directories; projectless materials request all C# declarations. Required source/configuration failures keep the observation unavailable; independent projects and non-C# materials do not require that context.

C/C++ extraction reads production `.c`, `.cc`, `.cpp`, `.cxx`, `.C`, `.h`, `.hh`, `.hpp`, `.hxx`, `.inc`, `.inl`, `.ipp` and `.tpp` files. Literal quoted `#include` directives resolve exact supplied files relative to the importing file, including parent-directory paths that stay inside the Workspace. Paths are case-sensitive POSIX paths; absolute paths and backslash-separated names are not mapped. There is no basename search or inferred root/include/src search path. Comments, ordinary/character/raw strings and C++ numeric digit separators cannot invent directives; backslash-newline splicing occurs before lexical recognition. Duplicate edges and self-includes are omitted. Test imports and targets follow the shared exclusions.

C/C++ preprocessing conditions are not evaluated: every literal include in every branch is evidence, including inactive branches and guarded headers. Macro includes, `include_next`, malformed/unavailable source and unresolved quoted includes produce diagnostics. Angle-bracket includes supply no local edge because their search paths are unknown; standard and external headers are not fetched. Containing `CMakeLists.txt` and `compile_commands.json` are collected but their include paths are explicitly diagnosed as unevaluated; CMake, Make, compiler commands, forced includes, macro expansion, generated headers and complete build target selection are not executed or reproduced. Narrow structure materials request only their member source bytes and containing recognized configuration; target header bytes and independent C/C++ source/configuration are unnecessary to identify a direct include edge. Required byte failures and relevant diagnostics keep that structure basis unavailable. Materials without C/C++ members request no C/C++ context.

PHP extraction reads production `.php` code inside standard `<?php` and `<?=` regions. Namespace `use` declarations support leading qualification, aliases, comma lists and grouped/mixed imports in global, semicolon-namespace and block-namespace scope. Class-like names map through the closest containing `composer.json`'s literal `autoload` and `autoload-dev` PSR-4 mappings: nonempty prefixes end in a namespace separator, paths are package-relative, directory arrays retain their order, more-specific prefixes are tried first, and the empty prefix supplies a fallback. Only exact supplied Workspace-local `.php` paths create edges; absent targets, imports without a PSR-4 context, namespace-only aliases, and function/constant imports remain diagnostic rather than guessing files or expanding namespaces. Target file contents need not be parsed to identify PSR-4 evidence. Comments, HTML, quoted/interpolated strings, heredoc/nowdoc and compiler data cannot invent imports. Closure capture and trait insertion `use` are distinguished from namespace imports and supply no inferred edges.

PHP `require`, `require_once`, `include` and `include_once` recognize relative string literals, including bare names and explicit `./` or `../` paths. Core tries the importing file's directory and then the Workspace root, keeps every distinct supplied local file candidate, and attaches a diagnostic to each candidate because actual runtime resolution depends on `include_path` and the current directory. If neither location has a local candidate, only a diagnostic is returned. Candidate paths must remain inside the Workspace; this is approximate module-level dependency evidence, not a claim about exact runtime loading. Source anchors are limited to `__DIR__` and `dirname(__FILE__)` with literal suffix concatenations and parentheses. Other concatenations, variables, function calls, direct `__FILE__` and other `dirname` forms remain diagnostic without retaining a static prefix. All conditional branches supply evidence. Interpolated expressions, unsupported string escapes, streams, absolute/drive/backslash paths, missing local targets, short open tags requiring configuration and malformed/unavailable bytes are diagnostic. PHP execution, runtime condition evaluation, custom autoloaders, Composer installation/vendor metadata, package dependency resolution, PSR-0, classmap/files autoloading, include-path/target-dir configuration, trait composition and expression references are not reproduced. Unsupported Composer autoload fields are skipped with diagnostics while valid PSR-4 entries remain usable. Narrow structure materials request only member PHP bytes and their closest containing Composer configurations; target bytes and independent PHP source/configuration are unnecessary. Required byte failures and relevant diagnostics keep that structure basis unavailable; non-PHP materials request no PHP context.

Dependency graphs are projected at directory depths one and two. A directed edge points from importer to dependency, entries have no incoming edge, cycles are strongly connected components of at least two directories. The default text uses depth two; JSON preserves both projections and all source edges. Generated directories include `gen`, `generated`, `__generated__` and generated protobuf suffixes, with a reminder to keep them with their source. Guidance includes AGENTS/CLAUDE/GEMINI/CONTRIBUTING/ARCHITECTURE/DESIGN/HACKING documents, package `doc.go`, `.cursor/rules` and README documents no deeper than two directories. A flat directory has more than twenty code files directly inside it; generated files are excluded, tests are included. Prefix counts group names through their first hyphen or underscore, listing groups of at least two files; these are naming facts, not inferred modules.

Valid Nodes that are neither deprecated nor archived establish material coverage; Roles and Cards do not. Directory and prefix coverage use the same shared Core membership authority as module checks and Stop. A declared directory covers its descendant paths recursively even if currently missing, with a path-component boundary so `src/core/` never covers `src/core-other/`. A single final `*` declares a prefix, including nested paths beginning with that prefix; coverage does not read a glob path. A file material or section covers that file. An existing path with the wrong declared file/directory kind produces an inspection error.

`readMaterialOverlaps(fs, workspaceRoot, nodeIds)` and authenticated `GET /api/nodes/material-overlaps?nodeId=...` compare the current material declarations of selected Nodes on demand. They return `{nodes: [{nodeId, issues}], pairs: [{left, right, shared}]}` in first-request order with duplicate ids removed and one pair per two distinct Nodes. Each shared item carries both declaration occurrences (`field`, source `index`, original `resource`, optional `track`) and an `intersection`: Workspace `file`, `directory` or `prefix` with its relative `path`, an exact native `document` path, or an exact external `uri`. Directory/prefix intersections use the shared coverage resolver and the narrower overlapping prefix; directory/file and prefix/file membership use the same authority as resource lookup. File sections share their file's coverage. This describes declared coverage, including missing Workspace files, without scanning or reading members, following symlinks, fetching URIs, comparing content or claiming that rules agree. Only usable current Nodes establish coverage; a broad Workspace declaration never includes `.tent` documents. Internal Node/Role/Card declarations are validated and compare only as exact documents; external URIs only as exact references. Card response sources are relationship bookkeeping and do not establish shared material coverage.

Unresolved or invalid declarations appear in their Node's `issues` with the original occurrence and reason, while known intersections remain available. An empty `shared` list with issues does not prove that the pair has no overlap. These reads inspect current headers, do not replay or capture history, do not advance baselines, and are separate from the default snapshot. Invalid and missing selected Node ids use the normal read errors.

`GET /api/modules/deps` is a separate authenticated read query returning `{basis: {head}, modules: [{nodeId, files}], edges: [{from, to, imports}], cycles: [[nodeId]], uncovered, unresolved, computedAt, fresh, mode, reason?}`. Modules are usable current Nodes with an explicit `sources[].track: structure` declaration. They use the shared material coverage resolver; the longest matching prefix wins for each file, and equally specific modules all own it. `files` counts distinct nonignored regular Workspace files owned by each module, including tests and non-code files. Empty modules remain in the result. Symbolic links, `.tent`, `.git` and directories with their own `.git` metadata are excluded. An empty module list is valid.

The query reuses scan's static import extractor and exclusions. A directed edge goes from an importing file's module to its dependency's module; self edges are omitted. `imports` counts deduplicated extractor records for that module pair. A Go package import first targets modules with the most specific structure-tracked directory material covering that package directory, retaining equally specific shared owners. Finer filename-prefix modules may own the package files without taking over the package import. Without a covering directory module, the import contributes once to each module owning every production Go file directly in the target package. If neither kind of package owner exists but some package files have owners, that import contributes one to `unresolved` and no edge. Completely unowned packages contribute only uncovered files. `uncovered` counts distinct unowned files participating in resolved local imports or reported local import issues; `unresolved` otherwise counts local import issues. External dependencies and unsupported languages add neither count. Unparseable import configuration fails with `INVALID_INPUT` (HTTP 422), rather than returning an apparently complete graph. Modules and edges have stable identifier ordering. `cycles` contains the strongly connected groups of two or more distinct module Node ids in these aggregated edges; it does not enumerate paths or classify a dependency as an error. Each group is sorted by Node id, and groups have stable identifier ordering. Acyclic and empty graphs return `[]`. Cycles share the graph's basis and freshness; incomplete import extraction can omit cycles.

`basis.head` is the enclosing project Git HEAD, resolved directly from its ref (null for unborn or non-Git workspaces). The response does not report Git working-tree cleanliness. Computing a graph observes current files and Node declarations, including successive edits while HEAD remains unchanged. It writes no project or Tent documents, Git history or index, executes no configured Git filters, and never runs Git status or as part of a full snapshot; disposable input caches follow the common read rules. Process-local source and import caches are derived from the live source paths and validated contents; HEAD is not a cache key.

Every dependency request validates its own inputs and returns `fresh: true` and `mode: verify` on success. `computedAt` is the UTC ISO time that query finished computing. The service starts no dependency watcher and shares no previous or in-progress graph with another request. Failed current reads report their error rather than a previous graph.

## 4. Role

A Role is one OKF v0.2 §4.1 document at `roles/<roleId>.md` with `type: role`, `id: role-…` and an optional readable title. It holds a work direction, boundaries, methods and selected references. Shared business facts remain Nodes. The Markdown is the authority; there is no metadata registry, reverse Card list or implicit responsibilities import.

`role list` reads bounded headers without capture and excludes deprecated Roles by default. `--include-deprecated` includes them, with a trailing `deprecated` marker in text; JSON retains status. `role create` saves a new document; identity cannot reuse a path already retained in Tent history. `role show` returns a bounded body/raw page with exact ETag without capturing history. `role write --base-etag` uses raw CAS and the shared mutation lock; no-op saves can capture editor bytes without rewriting them. Unknown metadata survives and lifecycle status stays local.

Role selection is explicit. Reading it does not bind a Session, claim occupation, read every related Node, create missing context, repair an invalid document or resume a pending structural operation. Missing or invalid Role documents are diagnostics. A new host conversation may explicitly read the same Role to recover its maintained direction.

`deleteRole(roleId, {baseEtag})` / `role delete <roleId> --base-etag <etag>` removes the Role document and records `role.delete` in Tent history. Missing or stale ETags reject deletion; a missing Role is not a successful delete. There is no recycle bin or restore command: use lifecycle `status: deprecated` for reversible archival. The deleted document remains in Tent history and its id/path cannot be reused. Deletion uses the same two-phase `delete.pending.json` isolation, validation and cleanup as Node deletion. Deletion and writes with lifecycle `status: deprecated` share one locked Card check. Valid, nondeprecated Cards block either operation with `PENDING_CARDS` and all blocking Card ids when the Role is their pending target, their `returnTo` in pending/consumed/returned state, or their `receivedBy` while consumed with `returnTo`. Collect returned Cards, finish outstanding returns, move pending targets, or deprecate blocking Cards before retiring the Role. Closed Cards, consumed Cards without `returnTo`, and deprecated Cards do not block deletion. Returning releases the receiving Role; collection releases the return recipient. Existing `receivedBy` and pinned Role source versions remain unchanged and readable from retained history. Ordinary Node links are not rewritten; check continues to diagnose the broken references. A directly deleted target Role remains a Card diagnostic and never makes a targeted Card public.

## 5. Card

A v3 Card is one Markdown document at `cards/<cardId>.md` with `type: card`, `id`, `schemaVersion: 3`, optional `title`, ordered `sources`, optional target and `returnTo` Role ids, delivery fields, and the prompt in its body. Creation publishes it immediately and requires a prompt, sources or both. Sources use OKF v0.2 §5.1 resource declarations; explicitly selected Nodes and Roles receive immutable `{commit,path}` event versions. External addresses are not fetched or captured. Cards do not record a sender or creator Session.

Creation captures only selected internal sources before publishing the Card. A supplied historical source is validated without reading its current live path; a live rename or deletion does not prevent reusing a valid retained source in a new Card. The first reachable path-addition event is the input baseline, and identities retained in history cannot be reused. There is no separate publication operation or persistent Card draft; a Card with `status: draft` is diagnosed as invalid. Undecided requirements stay in conversation with the user or go to the deciding Role by Card; write a Node after the decision, never as a draft. Draft Roles remain readable, including `card list --role` filtering, but cannot dispatch, receive, return or watch Cards. The browser keeps unsent Card content locally and submits it directly to `POST /api/cards` when sent.

Published body, title, ordered sources, `returnTo` and unknown metadata are immutable input. Hand-edited input remains raw-readable but reception and management operations reject `INPUT_CHANGED`. Requirements and decisions belong in Nodes; edit those Nodes when they change. Live Node moves do not rewrite old Card input or pinned sources. For in-progress Cards (`consumed` with `returnTo`), brief compares pinned Node bytes with current bytes by stable Node ID. An edit or missing source asks the receiver to reread the current requirements; an unrelated commit alone is not a content change. Goal ahead/output comparisons remain independent of Card completion.

Routine brief and UI revision reads skip Cards retained as `closed`, `consumed` without `returnTo`, or `deprecated`. Completion membership is read from the current retained Card documents in SQLite. Readers enumerate `cards/` once and skip those paths before validating live headers or hashing current bytes. Native edits to completed Cards are reported by `workspace check`, not brief; unfinished and newly discovered Cards retain current-file validation and malformed-header diagnostics. Explicit `card show`, `card take`, state-filtered lists and `--include-deprecated` still read current files. The UI map does not load Cards; Node details and history load them on demand.

Live Card lists may share a frontmatter prefix and the full decoded-text blob fingerprint from one file observation. A fresh file stat validates each observation against size, modification/change timestamps and file identity, with the existing conservative one-second cache rule. Missing or damaged cache entries, changed files and explicit content checks acquire complete bytes with the normal handle/path checks. Only the prefix and fingerprint persist in the disposable file-state cache; malformed unterminated documents are not stored there. BOM and invalid UTF-8 decoding match a complete live text read. Retained-document adapters do not expose this live capability, and adapters without it use complete text reads when checking uncaptured content. Historical Card state never authorizes skipping current validation in an explicit list.
Each Role has one pending queue; the public area is another queue, visible to all Roles but silent by default. Default order is publication time ascending, then Card id by code-unit comparison. Its effective key is the UTC ISO publication timestamp (including milliseconds) followed by `|` and the Card id. An optional `order` extension replaces that complete key. Generated keys use printable ASCII `!` through `~`, find a fractional position between adjacent complete keys, and end with `~<this Card id>`; this suffix keeps generated keys distinct from both default keys and other Cards' generated keys. At the tail, the generated key appends `~<moved Card id>` to the previous last key, retaining its timestamp prefix so later publication times still follow it; repeated tail moves may lengthen that key. Creation neither reads a queue nor assigns order, and same-second default keys still use id order. Comparisons are lexicographic, not locale-aware. Equal effective keys use publication time then id. No sidecar queue or dependency field is stored.

`card move <id> [--to <roleId> | --public] [--before <cardId> | --after <cardId>] --base-etag <etag>` changes a pending Card's destination and/or queue position; the CLI requires at least one destination or position option. The reference must be a different, nondeprecated pending Card in the destination queue. Omitting the destination retains the current queue; omitting position puts the Card last. An empty destination queue needs no explicit order. Only the moved Card is written, under the reception mutation lock and observed ETag, with `card.move` history. Body, sources, title and `returnTo` remain immutable. Clearing the target returns the Card to the public area. An already-correct position validates its ETag without adding a commit. A new target must differ from `returnTo`; deprecated or received Cards cannot move. Hand-edited target or order changes conflict with retained management state. The thin HTTP move endpoint accepts `baseEtag`, optional `target` (null means public), and optional `before` or `after` with the same semantics. Snapshot Cards expose Core's effective `orderKey` for queue presentation; sorting and moving do not infer progress from goals.

`card deprecate <id> --base-etag <etag>` cancels a task through lifecycle `status: deprecated`, including after reception. It preserves reception and immutable input, uses CAS and records the management change in history. Lists and brief omit deprecated Cards by default; `--include-deprecated` includes them. Explicit show or take warns and exposes current references, while preserving the ordinary Role gate.

`card list` reads published Cards without capture and returns delivery state, `returnTo`, `receivedBy`, `result` when present, publication time, optional `order` and the effective `orderKey`. With `--state pending`, each queue uses effective-key order before pagination; a selected Role precedes opted-in public Cards. Other lists retain publication time descending, then id ascending, with unavailable times after dated entries. Brief places pending queues before other active inputs and preserves their effective-key order. Titles, reception states, filters and header diagnostics use live files; changed files carry `uncaptured: true`, including invalid headers. Invalid live headers remain unavailable rather than displaying a historical title. An unretained handwritten file is not a published Card. `card show/get` previews a bounded body/raw page without receiving or executing it. Omitted oversized source metadata has a raw read address rather than truncated executable references. An exact Node source can be read using `node get --version-json`.

`card watch --role <role-id> [--include-open] [--timeout <seconds>]` waits for committed, nondeprecated pending Cards addressed to the supplied available Role, or returned Cards whose `returnTo` names it. It emits that Role's pending queue first, then the public pending queue only when `--include-open` is set, then returned results ordered by retained `card.return` time ascending (id breaks ties; unknown return times follow dated returns). Public results carry `fromPublic: true` in JSON and `[public]` in text. Taking a public Card claims it through `receivedBy`; concurrent claims share the reception lock, and the loser receives `RECEPTION_CONFLICT` with the winning receiver. Public Cards never wake the default watch. Watch checks immediately, then reads only the current retained event every three seconds while unchanged; a changed HEAD triggers another committed Card and timestamp query at that exact HEAD. It may read an existing validated history cache, but never creates or refreshes one. It does not capture documents, change baselines or write files. Matching Cards return immediately with one text line per Card containing its id, optional title and `tent card take <id> --role <role-id>`; a returned Card instead prints `card-ID returned by role-X: <result>` and remains visible until taken by its return recipient. JSON returns an array including `state: returned`, `receivedBy` and `result` for returned Cards. Exit codes are 0 for input, 2 for timeout with no output, and 1 for errors. Omitted timeout waits indefinitely; zero checks once. Watching neither receives Cards nor registers waiting Sessions. Agents choose their own host wakeup mechanism and ask before creating a new persistent automation.

### Reception and outputs

State is `pending`, `consumed`, `returned` or `closed`. Pending has neither `receivedBy` nor `result`. Creation accepts an optional `returnTo` naming an available Role, different from `target`. It is a delivery address, not a sender identity, and stays immutable. Without `returnTo`, an untargeted Card may be received with or without a Role; with `returnTo`, reception requires an explicit different Role so that only that receiver can return it. A targeted Card requires its specified available Role. Missing, invalid, deprecated or unsupported Roles are diagnostics, never an open fallback. Existing Cards need no conversion or format version change: without `returnTo`, take completes them.

`card take` validates published input and retained management state under the shared mutation lock. For pending input it records `consumed` and `receivedBy`, then returns a bounded input page. Retries with the same Role choice return `replayed` without authorizing another execution. For a returned Card it requires the available `returnTo` Role and records `closed`, preserving the original `receivedBy` and result. Only that return recipient can replay collection of a closed Card. No reception operation takes a Card Git version.

`card return <id> --role role-ID --result TEXT` requires a consumed Card with `returnTo` and the explicit receiving Role. It records `state: returned` and `result` in the same document. The result must be nonempty, single-line text of at most 200 Unicode characters (code points); longer details belong in Nodes, whose ids may appear in the result as UI links. No separate return-author or result-Node fields are stored. The same exact result is an idempotent replay, including after collection; a different result is rejected. A return receipt carries no decision-needed flag. Further work or a decision requires a new Card, while the decision itself belongs in a Node.

Cards have delivery state only: pending input, received work, returned result and collected result. Without `returnTo`, consumed means complete; with it, returned means complete and closed means the result was collected. In-progress Cards are exactly consumed Cards with `returnTo`. No Card read surface derives `progress`, goal counts or output lists. Pinned goals retain their own ahead/output semantics, independently of Card delivery; changing or confirming goals or outputs never retracts a Card's return.

`node link-output --card <id>` records the response in the output's `sources`. An explicit response may cross Roles, but its Card must already be received, must not be deprecated, and must have a pinned goal source on the new output's goal chain. Automatic inference requires an explicitly supplied Role matching the received Card's `receivedBy`, and exactly one matching consumed Card with `returnTo` for the selected goal. A missing or different Role cannot silently attribute the result to another receiver: choose a Card explicitly when relevant received Cards exist. Multiple matching candidates also require an explicit choice. With no relevant Card, ordinary output creation still works without a Role. A missing explicit Card is rejected with a human-readable message without a filesystem path, before creating an output or its sources. The write receipt identifies the selected Card when one is attached. A Card source is a response relationship, excluded from material comparison. Existing explicitly recorded responses keep their attribution; no new automatic backfill accompanies this change. Questions, research and pending decisions use prompt Nodes; any current output answers, whatever its tags. No return Card is required.

Manual reception fields differing from retained state remain raw-readable and diagnostic. An explicit take or return may finish its interrupted pending-to-consumed, consumed-to-returned or returned-to-closed transition when input, target and status are unchanged and the saved receiver/result exactly matches the request; it captures those saved bytes. Other management edits remain conflicts. A subsequent identical take is a replay and adds no commit. Lifecycle status is independent. File/history failures can follow a saved document; reread before retrying. Reception proves neither comprehension nor exactly-once execution.

## 6. Persistence, recovery and historical data

Initialized SQLite workspaces use the same durable write-ahead file record at `.tent/.git/tent-transaction.json`, under `mutation.lock`, for single-file and multi-file mutations. A batch records every selected document, created directory and order change before publishing its first file. Other mutations record each affected file or directory before changing it. The record contains exact before/after bytes, including binary attachments moved with Nodes. Temporary files and disposable caches are not recovery authorities.

Historical identity, first/latest versions and Node records have an incremental projection in `.tent/.git/tent-material-cache/history-index.sqlite`, separate from the authoritative history database. Each projection has an immutable event sequence cursor: subsequent events update only the new range, and content identities are parsed once per SHA-256. A Node history page selects only that identity's indexed events with SQL ordering and pagination; its revision and chronological event representation retain the existing cursor contract. Before returning history events, validate the authority bytes referenced by that selected result's before/after versions, deduplicating content digests within the read. Cached identities do not bypass content-damage errors. This validation covers the queried Node or page, without reading unrelated Node history. Missing, damaged or unwritable projections rebuild from authority, and deleting the whole cache changes no result. Projection connections close with their owning adapter. Current material observations still run on each read; historical projections never substitute for checking working materials.

Positive history availability and legacy-layout detection are shared within one adapter lifetime; an uninitialized workspace is probed again at the next request boundary, so another process can initialize it. An existing SQLite history database is checked before considering legacy layout. Successful initialization refreshes earlier availability observations in the same process. Read-side transaction recovery probes may be shared within a single request's file-read scope, but subsequent requests still detect new interrupted transactions and recovery conflicts.

Markdown files and SQLite are not one transaction. Before database publication, the synchronized file journal records the exact candidate event. SQLite obtains its write reservation, checks the prior event, inserts the immutable event, deduplicated contents, current membership and Node records, then commits with rollback-journal DELETE and synchronous EXTRA. Ordinary mutation SQL is synchronous between BEGIN and COMMIT, so another request on the same service connection cannot observe partially inserted history. Publication completes before the file record is retired. An unchanged capture still performs the required database file synchronization before acknowledging the save. A failed flush remains a failed save.

Every Tent command and service opening settles a pending file transaction under the mutation lock before returning business reads. Without a pending record, reads do not run structural recovery. A published candidate event chooses after-images; otherwise recovery restores before-images. Repeated interruption follows the same record. Bytes unlike every recorded version are external edits: preserve them, settle other files and report their paths. Conflict paths are retained separately from the retired journal. Recovery removes only empty directories and never recursively removes unexpected contents.

Crash acceptance observes the complete affected group after ordinary opening settles the transaction: all old or all new, with external-edit exceptions reported explicitly. Native file tools reading before that boundary may see intermediate files. Software checkpoints and process termination do not prove real power-loss behavior. SQLite durability depends on its VFS and storage honoring synchronization. Markdown replacement still flushes prepared file bytes before rename; supported POSIX directory entries are synchronized, while Windows uses file flushes and atomic replacement without native directory synchronization or rename write-through. New Windows directory entries are not promised to survive power loss; macOS does not require F_FULLFSYNC.

Legacy private Git workspaces are not opened through a fallback or converted on read. The bundled one-shot `migrate-history.mjs` imports a settled offline copy to a fresh target, rejects unsupported merge/additional-root histories and invalid or unmapped fixed sources, and never activates the target or edits the source. It replaces only recognized fixed-version hexadecimal scalar fields with mapped 64-hex event IDs. All other document bytes must remain identical. Its audit records original bytes, expected converted bytes and actual imported bytes separately for every historical/current document and every pin. Original raw history is retained in audit tables; the old-to-new lookup exists only in the external migration report, never as a runtime alias. Dirty/unretained current files remain current files and are listed separately; a fixed source always resolves its historical target rather than those current bytes. See [MIGRATION.md](MIGRATION.md).

There is no Git history repair, reference publisher, reflog migration or private-index mirror. SQLite settles its own interrupted database transaction; damaged or unsupported history fails explicitly rather than selecting a guessed event. The declared minimum Node runtime and the current LTS are covered by the Windows/macOS/Linux storage and six-case safety CI matrix. Only node:sqlite's exact built-in experimental-load notice is suppressed during its synchronous load; other warnings and real errors retain their normal delivery.

CLI command owners close every opened NodeFs after rendering, including failures. A Web service owns its connection for its lifetime. Closing it stops new HTTP work, waits for accepted requests and queued Core mutations, closes owned services and releases its database handle. Independent CLI writers use the same mutation lock and ETag checks; the service does not retain a transaction between requests.
All current document mutations use the Core workspace lock. Short-lived CLI processes share an exclusive on-disk mutation lock and directory guard for its bookkeeping. A live PID is not evicted because of age alone; release checks its ownership token. A crashed guard is reclaimed when its PID is absent, retaining a small tombstone directory so delayed contenders cannot displace its successor. PID reuse can require manual cleanup after all Tent writers stop; the timeout identifies the guard path. No persistent HTTP Service, watcher, event bus, Session token service or RPC passthrough is part of the current runtime. `tent ui` is an explicitly started foreground exception: a loopback HTTP server for the bundled UI, ending with its process, without Session registration or filesystem watchers. The UI polls `readWorkspaceRevision` for refreshes; ordinary browsing is read-only, while explicit edit reads capture their basis.

`tent ui [--workspace <path>] [--port <number>] [--no-open] [--idle-timeout <seconds>]` resolves an existing workspace, prints its URL and opens the default browser unless suppressed. It remembers opened workspaces in a per-user file outside `.tent`; the page can open other existing workspaces in the same process, and Ctrl+C closes all of their servers. The server uses a fresh launch token, checks Host/Origin, and writes through Core's ETag and workspace lock. Its API is private to the matching bundled frontend, not a public integration protocol. npm and plugin distributions include UI assets; development snapshots and source maps are excluded.

The Node reader opens from map metadata and reads its body, identity history, related Cards and outgoing relations independently. It does not request the workspace snapshot merely to open a Node. Incoming references are a separate, explicitly expanded whole-workspace query. Loading, empty results and failures remain distinct; failed sections can be retried. The existing workspace revision signal refreshes open sections, including body-only edits that do not change map metadata. History follows identity through moves; related Cards retain each matching source version, including deprecated and completed Cards. Pinned sources resolve identity from verified retained bytes before matching the selected Node; missing or invalid versions remain diagnostics and never retarget to a new occupant of the old path. These ordinary reads do not capture, repair or mutate documents.

Clicking a slash-marked local body directory link opens the existing file panel; editor Ctrl/Cmd-click uses the same navigation. The panel lists only direct children, directories before files, each group in case-insensitive natural name order (`B2` between `a` and `b10`, exact ties by code unit), with the current Workspace-relative path and a parent action that stops at the Workspace root. Clicking a child directory reads that next level on demand; clicking a file uses the existing suffix-based file preview or native document navigation. Browsing is read-only, stays inside the Workspace, excludes `.git` in any case and refuses aliases resolving outside the Workspace or into `.git`. Absolute `file:` directory links can be checked outside the Workspace, but UI browsing remains Workspace-only. Authenticated `GET /api/directories?path=<Workspace-path-or-file-URI>` returns this single level; `GET /api/files/text?path=<Workspace-path>` shares the existing bounded plain-text preview (256 KiB, binary rejection and truncation notice). The material-specific Node text endpoint retains its declaration check. No directory traversal, member-content read or fingerprint occurs merely by following a directory link.

The Role list starts with "All sessions", which opens the Workspace's root `AGENTS.md` as plain Markdown to read and edit. It is neither a Node nor a Role, takes no Cards, carries no Tent header and never enters Tent history; Git keeps its versions. Authenticated `GET /api/agents` returns `{path, exists, etag, text}` with `path: "AGENTS.md"`, `\n` line ends and a null ETag for a missing file. The ETag is the first 24 hexadecimal characters of the on-disk bytes' SHA-256. `PUT /api/agents` with `{baseEtag, text}` writes only when `baseEtag` matches the bytes on disk, otherwise 409 `ETAG_CONFLICT` with `details.current` and nothing written; a file created after a null-ETag read is also a conflict. The first save creates a missing file. Saving the text as opened returns `changed:false` and writes nothing, including when the original file mixes line endings; a changed save keeps the file's BOM and CRLF line ends and returns `changed:true`. Text containing NUL is refused with 415 before anything is written. Only this root file is editable through these endpoints, with the same containment rules as file reads. Files over 2 MB are refused with 413, and files that are not UTF-8 text with 415. Writes use the existing token, Origin and JSON checks and serialized request queue, followed by atomic durable replacement.

Authenticated `GET /api/revision` and `/api/snapshot` reads each have at most one active calculation per workspace. Calls arriving during that calculation form one waiting batch; its document observation starts after its callers arrived, so a newer request never joins an older observation. Waiting callers share that batch's calculation and serialized body. Disconnected callers are removed, and a batch without callers does not run. An active Core read can finish, but the service skips later read phases and response serialization if nobody remains. Snapshot `fresh=1` and `If-None-Match` decisions remain per caller. Completed results are not retained between batches, and no polling interval, file validation rule or watcher is introduced.

The optional idle timeout is a positive whole number of seconds (at most 2147483, the timer limit); without it manual UI lifetime is unchanged. It closes the entire owned UI session after that interval without a successful authenticated API response. Successful page polling counts as activity; static requests, rejected authentication, invalid Host/Origin and failed API requests do not renew it. Activity in any workspace opened by that session renews the same deadline, so switching workspaces does not close an active page. Closure cancels the timer, closes all owned servers, and removes CLI signal listeners. Init uses 300 seconds and a host-visible, stoppable background command, never a detached daemon. The CLI prints the address and idle interval even with `--no-open`.

Recognizable retired stores at the root of `.tent`, such as an old `snapshots/objects` layout, produce one consolidated diagnostic before Node indexing. They are neither imported nor deleted automatically. Names such as `notes` or `snapshots` remain valid for ordinary Nodes and grouping folders; a matching identity document identifies a current Node.

Legacy move/rename plans without a file transaction retain their structural recovery rules: the next mutation rolls back the pending move under the existing lock; conflicting external bytes preserve the plan and stop recovery. Reads do not resume these legacy records. Current SQLite-backed operations use the file transaction above, including their directory, link and order changes. If recording a completed rename in Tent history fails, recovery uses actual publication to keep the old or new name and reports uncertainty instead of claiming a complete save.

Node deletion records exact primary data and associated order writes in `delete.pending.json`. Moving the primary object to quarantine is the logical deletion point; subsequent mutations can finish verified cleanup. Reused identity or changed associated bytes causes conflict. Export rejects pending operations.

## 7. Export

`tent workspace export --output <new-directory>` creates a separate complete-graph directory and byte inventory. It preserves persistent documents, unknown metadata, order, SQLite history, Roles, Cards and ordinary retained files, including any existing attachments directory. `attachments` is not a reserved directory name: valid identity documents there follow the ordinary Node rules, and body links use normal file handling. Credentials, locks, runtime state, disposable checks, `.git/tent-material-cache` and temporary files are excluded. Export audits all retained version 1 Node records, including import portability diagnostics, for machine-absolute paths; original imported record declarations remain in audit data. Source data is never repaired or switched.

Export inventories the source under the workspace lock, copies and verifies it, then checks source membership/hashes again under the lock before publishing. Pending operations, invalid required history or missing referenced local materials prevent publication. Filesystem copying does not claim a transaction with arbitrary external editors.

Live standard references in Node, Role and Card documents inside `.tent` are checked against copied files/directories. Ordinary files are copied as bytes without interpreting frontmatter, even when they have a `.md` suffix; malformed frontmatter at native document paths still fails validation. v3 Card sources validate against copied published SQLite history; their old paths need not exist live. External workspace targets and absolute URIs are listed in `externalNotPacked` with origin, declaring path and occurrence index; bytes are not copied. Bare sources, invalid locators and nonstandard metadata appear in `unresolvedMaterials` without guessing or rewriting.

## 8. Plugin and Hooks

The four Skills are `tent-init` for empty setup, `tent-node` for relevant input and Node maintenance, `tent-role` for persistent work direction, and `tent-card` for recorded prompt input. Role and Card are independent optional objects. Command details live in on-demand references. Skill use requires no initial decomposition, fixed reading sequence, per-turn Node count, full-tree verifier.

One build produces Codex and Claude Code packages from the same bundled CLI, four Skills, references and SPEC. Each host has a thin shell for its manifest, Hook definitions and launcher, interface metadata and Hook instructions. The build places those instructions at `tent-init/references/host-hooks.md`; shared Skill text is host-independent. Each launcher explicitly selects its host. The plugin uses its installed package path and bundled runtime dependencies. It does not guess an executable from cwd, store graph data in a plugin cache, install global Hook copies, or configure MCP. npm delivery installs its declared runtime dependencies separately. Build/install/trust and real event delivery are distinct checks; package presence does not prove native activation.

`tent --version` displays the version, commit and build-session start time. `tent version --json` returns `version`, `commit`, `builtAt`, `dirty` and `runtimePath`. Version commands accept `--workspace` without inspecting or requiring that workspace. Built CLIs embed their identity independently of their installation path and adjacent package metadata; source execution has `builtAt: null`, and watch rebuilds share their build session's identity. Unknown Git identity remains null. This is local provenance, not a network update check.

SessionStart runs the native-edit collection boundary before returning the available workspace, current package entry, build identity and a short `workspace brief` hint, without loading the brief. It collects pending native Node edits under the mutation lock; when no edits are pending, it takes no write lock and performs no document write. It prepares the existing material index. The plugin registers no UserPromptSubmit hook and creates no Session registration or prompt baseline. Role selection remains explicit.

The plugin registers no Stop hook, so completion launches no Tent command and adds no context, block or notification. The existing CLI `hook stop` command returns `{}` without observing the workspace.

PostToolUse adds advisory context only after a supported file tool succeeds with a reliable write path. Claude Code supports Write, Edit, MultiEdit and NotebookEdit, matching the native structured result path to the input path. Codex apply_patch uses the successful native output's published paths, including deletion and move destinations; when Codex wraps that output with an exit code, the code must be 0. Its input alone is not write evidence. Errors, cancellation, reads, opaque shell text and uncovered files produce no file reminder. Paths in `.tent/` and operational artifact directories do not generate reminders, so normal Node/Card maintenance does not loop.

Each file is made relative to its own linked checkout before matching the main workspace's modules. Relative Codex apply_patch paths resolve from the session checkout root. Other repositories, submodules and bare repositories without a main checkout do not inherit the workspace. Checkout routing reads Git pointer files without starting Git. Native host/session/turn identities isolate reminders: Codex uses `turn_id`, Claude Code uses `prompt_id`; missing identity stays silent.

A module is a valid, non-draft Node with a directory or prefix material in `sources` marked `track: structure`. Core owns coverage parsing and selection. Each changed file names only its most specific covering modules, retaining ties. Ancestor names, Node id, readable Workspace-relative Node path and successful changed paths are shown. Modules sort by distinct changed-file count descending, then Node path. Each native turn names a Node at most once, even across concurrent hooks; another turn or session may name it again. Empty exclusive claims under `.tent/temp/stop-reviews/` are keyed by host, session, turn and Node. They contain no transcript, prose, paths, hashes or contents, need no global lock or retry, and may lose a reminder if the process crashes after claiming it.

The file reminder uses this exact text:

```text
Tent: these Nodes cover the file you just changed:
- <names> (<nodeId>, <path>): <files>
Check them before you end this turn. If one now says something the change made wrong, edit that sentence in its file. If the change settled a rule or a rejected option that also binds code it did not touch, or hit a dead end, add one short section: tent node append <nodeId> --heading <title> --body -. A lesson about these lines belongs in a code comment or a test. Otherwise say nothing about it.
```

A successful answered question tool (Claude AskUserQuestion or Codex request_user_input/request_user_input_async) gets this separate reminder, once per native tool-use identity. Empty or cancelled answers produce none. No language heuristic or Stop question list infers a decision:

```text
Tent: the user just answered. If the answer settles a requirement or a decision, record it in the Node it belongs to before you end this turn; otherwise say nothing about it.
```

Core formats plain UTF-8 text; the host adapter owns the native PostToolUse `hookSpecificOutput.additionalContext` envelope. Complete JSON including escaping and newline is at most 2 KiB. At most five modules and eight files per module are shown, with `+N more modules` for omitted modules. On overflow, remove filenames, then module lines; keep the fixed action complete. Only actually named Nodes are claimed. Preserve the omitted count from the remaining projection; Nodes omitted by either count or byte budget stay unclaimed and may be named by a later tool. After a competing claim, remove that Node from this response and rebudget, claiming any newly visible Nodes before delivery. The context joins the host's already scheduled tool-to-model request. When no maintenance is needed, the Agent says nothing about recording and gives its normal work summary.

The tool path has a separate bundled entry, loads no full CLI, starts no Git, reads no transcript, observes no material content/version and acquires no workspace mutation lock. It reads the existing `.tent/.git/tent-material-cache/stop-material-index.json` coverage only, checking its schema, workspace and index digest. Missing or corrupt coverage stays silent until the next SessionStart rebuilds it. Node edits during a session may therefore leave coverage unchanged until that boundary. This is an existing-coverage reminder, not a fresh graph inspection. SessionStart also stores exact-byte identities for the root marker Core fully parsed as valid and any candidate markers Core actually rejected on its discovery route, in the same disposable coverage cache. Tool discovery shares the normal checkout/pointer routing and candidate priority. It can use that coverage only while the root marker bytes match and every preceding marker candidate has a same-path, same-bytes, same marker-name-context Core rejection proof. This preserves ordinary project/subdirectory index.md routes without guessing their YAML. Proofs are not marker authority: no YAML parser runs in the tool, and missing, changed, malformed or wrong-root evidence means silence, never inheritance of an unproved parent root. Preparation merges known rejections for concurrent session directories; later byte changes cannot reuse an old rejection. Marker changes during a session conservatively disable that route until another SessionStart prepares it. Prepared cache schema 8 invalidates both the older main schema 7 coverage and pre-integration marker proofs; no separate cache is created.

At SessionStart the existing incremental material loader checks directory/header states, rereads changed or racy headers and rebuilds validity, hierarchy and membership through Core when needed. Its disposable cache changes no Node/Card/Role, project file, Git reference or commit; no daemon, watcher or new cache maintains it. For each host and each ordinary, uncovered and already-claimed path, run eleven adjacent hook/bare `node -e 0` pairs in one measurement window, alternating which command runs first. The median of the eleven per-pair differences (hook wall minus bare Node wall) must be at most 50 ms for each of the six cohorts. Both commands include Node startup; Tent adds no command-shell layer, while the host's own shell/startup is outside Tent's overhead. Retain every raw pair, including outliers; do not substitute the difference of two medians or select faster samples. Hook command cost and full Agent turn cost are separate measurements.

Shell and external editor changes have no reliable native write paths in these tool events. No input baseline, input hook or last-turn file notice is added. Existing ahead/behind facts in brief and check remain the fallback for those changes. Content-specific rules still need the file or SPEC section as content material. A hook notice proves no semantic synchronization: the Agent must read and maintain relevant Nodes through normal operations. Native trust, successful write events, context in the existing next request and the final visible work summary require actual host verification; synthetic handler tests alone do not prove activation.
