# Tent V0.1 Specification

This document defines Tent's current public contract. Retired commands and wire fields are removed rather than kept as aliases. Core owns document semantics and local persistence; the CLI and plugin are thin entrypoints.

## 1. Purpose and workspace

The three semantic concepts are Node, Role, and Card. Tent maintains useful parts of Agent context as linked Markdown documents: Nodes preserve reusable facts and references, Roles preserve a work direction, and Cards record prompt inputs. Normal work, answers, code edits, review and Git integration remain in the host conversation and the user's tools. Ordinary tasks need no Role or Card. There is no separate Return, managed Agent, Session registry, occupation system or task scheduler.

One Tent belongs to one workspace: the directory containing `.tent/`. Its stable `workspaceId` lives in `.tent/settings.json` and survives relocation. Ordinary commands use existing settings; they do not repair, reidentify or register the workspace. Missing or corrupt identity fails explicitly. A saved identity does not establish exclusive ownership across separate copies. Automatic discovery stops at a Git checkout or worktree root after checking that root for its own Tent; a nested clone never inherits a parent workspace. Explicit --workspace selects the intended workspace.

`tent new <workspace>` prepares an empty scaffold and independent local Git repository in a workspace-local staging directory before publishing `.tent/`. Failed preparation removes its owned staging directory and remains retryable; existing `.tent` data is never replaced. Initialization creates no Node, Role registry, remote or empty commit and does not analyze or split the project. The workspace may itself use Git or ordinary files. `.tent/` is excluded from the product repository; its Git history is independent.

Project instructions remain in workspace `AGENTS.md`. Tent neither copies their authority nor configures third-party analysis applications. Desktop, execution engines and application/format adapters are outside this version. The bundled Web UI reads and edits the same local graph through Core.

## 2. Node and OKF fields

A Node is a directory with its identity Markdown at `<directory>/<basename>.md`. A directory without that identity file is a transparent grouping folder: its Nodes belong to the nearest ancestor Node, or to the root. Placement expresses the parent/child tree; a stable `node-…` id remains the lookup handle across moves and renames. A Node has one non-empty `type` field in `primary[-secondary]` form: `primary` is `goal`, `prompt`, or `output`, and the optional suffix is project-defined. The primary type says what the content rests on: `goal` holds intent confirmed by the user, `prompt` holds agreements later work follows, and `output` holds evidence observed at a point in time. Any non-empty suffix is valid and serves only as a label. Core exports `NODE_TYPE_PRESETS`: `goal-direction|requirement|todo|question`, `prompt-spec|rule|decision|reference|procedure` and `output-asset|evidence|analysis|issue`. These are a default menu; no suffix imposes behavior, registry or extra lifecycle. There is no separate kind field.

The filename is the display name. If `title` is present, saves and structural renames keep it aligned; it is not another identity. Tags belong in each document and are aggregated on demand. Unknown YAML fields survive ordinary edits. Invalid identity/type data and duplicate handles are diagnosed, not silently repaired. Unusable subtrees stay outside ordinary content operations; explicit raw inspection remains available where supported.

Record context that will help later work: confirmed goals and constraints, useful reference pointers, observed findings, decisions and facts about real outputs. Goals can exist before implementation; unperformed results cannot. Prefer an existing fact owner and split independently useful context as it emerges. No initial task skeleton, per-turn quota, copied transcript or full-tree maintenance pass is required.

`goal` and stable `prompt` keep confirmed intent, agreements, decisions and their reasons, including who confirmed them and when if known. Context forms from Agent collaboration alone: an Agent decides within its Role or sends a Card to the Role that owns the decision, without waiting on the user. A user may intervene by changing any Node, but observing is enough. An undecided proposal belongs in a `prompt` with `status: draft`, its reasons and alternatives, until the owning Role settles it. These documents do not carry commit ids, test counts or merge/delivery status: consult Git and Card history for those records. Useful verification belongs in dated `output` evidence. A Card's reception state is not evidence that its requested work is complete.

### Lifecycle

Reuse OKF `status: draft|stable|deprecated`; omitted means stable. Status is local to the document. Editing, Git versions, material changes, checked-material records and parent status do not change it automatically. Unknown values remain intact with a diagnostic and no assumed currentness; an ordinary CAS edit may preserve them or explicitly replace them with a supported value.

Deprecated Nodes remain explicitly readable and editable without reactivation. Default content search excludes them; hierarchy navigation can expose a deprecated ancestor to reach a current child. Unknown fields, including `mode`, are ordinary metadata and do not control lifecycle.

`node archive <nodeId>` preflights the current subtree and writes deprecated only to documents not already deprecated. It captures selected preimages and returns the Git commit containing the status changes; a no-op subtree creates no commit. `node restore <nodeId> --archive-commit <commit>` accepts a reachable single-parent commit containing only the relevant status-to-deprecated edits. Current identities, paths and bytes must still match, and no later retained change to those paths may exist, including edit-and-revert. Restoration changes only those status declarations, including an originally omitted value; it leaves previously deprecated and newly added children alone. It never resets Git or revives deleted documents. Never-captured external edit-and-revert intent cannot be inferred.

### Materials and links

Reuse `resource` for the primary described material and ordered `sources` for independently related material. Each source has `resource` and may preserve standard or custom descriptive metadata. Source order, repetitions and spelling remain significant. These references locate materials; they do not prove ownership, access, synchronization or a complete impact set.

Local paths use `/` separators. `./` and `../` resolve relative to the declaring Markdown; leading `/` resolves from `.tent` and cannot escape it. A `file:` URI names an absolute filesystem path. Relative paths can reach workspace material outside `.tent`. Queries/fragments and percent encoding retain their reference meaning. Windows drive paths and UNC spelling must use a URI rather than an ambiguous local path. Node creation and writes validate new or changed addresses without requiring file existence; unchanged legacy addresses remain editable. Source reordering, removal and metadata edits retain existing address occurrences, while additional occurrences require validation.

A bare `sources.resource` can be ordinary description. Tent preserves it as unresolved instead of guessing from an extension or the existence of a similarly named file. Use an explicit `./`, `../`, `/` or absolute URI when mechanical resolution is wanted. A spaced label such as `note: reference` is description; an unspaced URI such as `urn:example:1` is an address. `resource` itself is a material address. Remote URIs are addresses and are not fetched by Tent.

Local Markdown materials (`.md` or `.markdown`, including `file:` URIs) can select a section with a nonempty fragment, such as `../Design/Design.md#State`. The fragment is the heading text used by `node get-section --heading`, decoded once from percent encoding, not a generated slug. The material version covers that section's exact text, including its heading and nested sections, ending at the next heading of the same or higher level. Frontmatter and other sections do not affect it. Missing or duplicate headings make the material unavailable; confirmation cannot clear an unavailable material's recorded basis. Batch saves resolve relative material addresses and batch references against the final document bytes. Addresses without a section and fragments on non-Markdown files retain whole-file versioning. This adds no metadata fields, and Card sources still pin complete Node or Role versions.

Standard Markdown links and standard fields support discovery of related Nodes. One Markdown AST parser drives relationship discovery and link rewriting, including reference-style links. Lookup matches exact identity, path or full name; ambiguous names remain unresolved. Wiki text such as `[[Name]]` is ordinary text. Core saves turn known Node IDs in link destinations, `resource` and `sources.resource` into relative document paths. Occurrences keep their original ranges and declaration paths. Unresolved references are visible. Tent does not add an in-document annotation protocol. Moves/renames rewrite resolvable affected live links and material addresses while preserving unknown fields, source order and occurrences; they do not rewrite historical Card input. Code, quoted HTML and unrelated text are not interpreted as links to rewrite.

Input materials use `resource` and `sources`. An output belongs to its nearest goal ancestor; this hierarchy supplies an implicit source without extra frontmatter. Other custom fields survive without transformation or material semantics. The Agent uses its existing tools to read actual materials; Tent provides no application or media adapters.

Markdown paths leaving `.tent` remain external to the Node index, even when an internal Node has the same trailing path. Internal Node renames must not redirect these references; moving the declaring Node adjusts relative addresses to preserve their original material targets.

## 3. Reading, editing and local Git

### Progressive disclosure

Header discovery resolves identity, hierarchy, status and duplicates without reading unrelated bodies. NodeFs reads frontmatter in 512-byte blocks and stops at the closing fence; an unterminated header may require EOF to diagnose it. This is still an O(N) metadata scan, without a watcher/cache or an atomic snapshot of concurrent editor changes.

Core queries return complete metadata and requested text, without CLI byte budgets, pagination or continuation cursors. CLI `node list`, summary reads and parent/children navigation disclose bounded metadata including `description`; type and tags aid discovery. Oversized display metadata is marked and retains a raw `metadataRead` address. Metadata-only responses do not provide a full-document write basis or capture Git. A full text read can be required for body search or link relations, but discovery never captures versions.

`listWorkspaceRelations` returns Markdown-link and standard-field occurrences from all valid Node, Role and Card documents in one query. It uses the same Markdown parser and material resolution rules, preserving source indices and body ranges. Retained Card sources resolve to their historical identity even after live moves or path reuse; `changedSince` reports retained path changes, including edit-and-revert. Invalid version declarations remain explicit diagnostics. Discovery does not receive Cards or capture history.

`readWorkspaceRevision` hashes identity-document paths and bytes, order, settings and the independent Git HEAD. External edits are observed even when size and modification time are unchanged. It performs no Markdown parsing, capture, repair, stat-only cache or background watching; it is a change indicator, not an atomic filesystem snapshot.

`node get` body/raw reads load the selected full document after a matching header observation. `node get <nodeId> --full --json` supplies the complete body and exact ETag for CAS editing; add `--view raw` for the complete original document including frontmatter. The internal `readNodeForEdit` function returns the raw editing snapshot. An initially invalid document, a lookup-to-read conflict and an I/O failure remain distinct errors. `node list --full` explicitly reads and captures the full tree; it is not the default discovery path.

Agent-facing Node, Role and Card reads use `text` for body and raw content, including `node get --full`, `node list --full` and `read-many` items. The selected view changes the content, never the field name; read responses have no `body` alias. Structured write inputs still use `body` to distinguish a replacement body from a raw document.

CLI Node reads without the complete body or raw document mark their ETag as `read:<etag>`, including metadata, partial pages, non-first fragments and bounded single-save readbacks. This basis can continue reads and support metadata-only edits, but Core rejects it for body/raw replacement with `INCOMPLETE_READ`; callers must obtain a complete live read first. A complete single-response body/raw read retains the canonical ETag. Batch save receipts return the canonical saved ETags for the writer's known complete inputs; they are not discovery reads. The marker prevents accidental replacement from incomplete reads; it is not authorization, a signed receipt or proof against a caller deliberately removing it. Core's complete document reads and UI editing snapshots retain canonical ETags.

CLI body/raw, search and relation pages share a 16 KiB compact JSON budget. Large display values are marked as truncated or omitted and retain exact source ranges and qualified read addresses; a truncated display is not an executable material reference. Oversized occurrences must not prevent later results from being enumerated. Text ranges use UTF-16 offsets and preserve surrogate pairs and CRLF boundaries. Body excerpts address original text.

Cursors are deterministic continuation addresses usable across short-lived CLI processes, not permissions or signed receipts. They bind source, query, observed revision and position. A changed relevant revision requires a fresh query. Header/hierarchy cursors survive body-only changes, while text cursors require the observed body revision. No cursor secret or Session cache is needed. Role/Card pages carry explicit ETag/range continuations. Summary requests do not accept text ranges, cursors or an expected full-document ETag.

Core `readNodeBatch` accepts an ordered unique `nodeIds` list, `view: body|raw` and optional `capture`; it returns every selected document. CLI `node read-many` adds `start` and a response budget including outer fields, selects the deliverable documents before capture and retains only that subset. An item's partial text continues through `node get`; outer `page.nextIndex` starts a fresh live batch, not a whole-graph snapshot. Capture failure fails the call without claiming a successful batch.

### Save semantics

`node write --input-json` accepts an observed `baseEtag`, body and/or frontmatter patch, and optional `readBack`. Omitted fields and unknown metadata survive. Raw edits and structured edits use the same Core rules. Identity, type and lifecycle retain their explicit validation. A stale basis is rejected; the CLI must not refresh it just before overwriting.

The default save response contains metadata and the captured Git version. Core `readBack` returns requested text from the actual saved bytes without rereading the file; CLI bounds that response. A partial page does not mean the whole body was read. No-op saves validate CAS, avoid rewriting Markdown and still capture newly observed bytes when needed.

Node and Role edits recheck their originally observed bytes after asynchronous reference resolution, before saving or capturing the result. An intervening external edit is a conflict; it does not become a refreshed write basis. Storage errors remain storage errors.

Creation can save body, resource, sources and tags together. An initial file/order failure rolls back the newly created Node. Deletion removes a whole Node subtree without requiring archive first; it does not delete referenced materials or rewrite inbound references. Move children that should survive before deleting their parent.

`writeNodesBatch` / `node write-many --input-json` accepts `{items:[...]}` with ordered `create` and `update` operations. A create supplies a unique local `ref`, `name`, `type`, optional `parent`, body, tags and material fields. `@ref` identifies a Node created by this batch in parent references, Markdown link destinations and material addresses; forward references and mutual links are supported, while cyclic parents and unknown references are rejected. An update supplies an existing `nodeId`, a complete live-read `baseEtag`, and raw or structured changes. Duplicate updates, stale ETags and incomplete `read:` bases are rejected before saving.

The batch validates and prepares every final document before writing, holds one Workspace lock, and captures its changed documents in one Tent commit. A failed batch rolls back its own document, directory and ordering changes; rollback failures report affected paths and conflicts while preserving external edits. Existing pending structural recovery runs first under the same lock and retains its separate recovery history. Results preserve input order and contain each saved `nodeId`, `path` and exact `etag`, so known complete inputs need no confirmation read. The batch does not return a copy of every body. No-op batches add no commit when the selected bytes are already retained. The lock serializes Tent writers; it does not make filesystem writes and Git atomic against external editors or process termination.

`checkGraph` / `workspace check` inspects Node, Role and Card documents without editing, history capture or structural recovery. It returns compact `issues` for `unresolved-link`, `invalid-material-address`, `missing-material-file` and `missing-material-section`, plus `errors` for documents that cannot be fully inspected. A section issue identifies a missing or duplicated Markdown material heading; unrelated I/O failures remain inspection errors. Paths are relative to `.tent`; local material checks use Workspace-relative and absolute `file:` resolution. External URIs and plain source descriptions are not fetched. Retained Card sources are checked against their complete pinned versions. CLI exits zero for a clean report and one when issues or inspection errors exist, retaining the JSON report on stdout. This checks addresses, file presence and selected section availability, not semantic freshness; `node check` remains the separate per-Node material-version comparison.

### Appending and editing sections

`node append <id> --body <text|-> [--heading <title>]` appends to the current body under the Workspace mutation lock without a preceding read or ETag. The optional plain-text heading selects an existing section and appends at its end, including after nested subsections; when absent from the body, it creates a level-two heading. Duplicate matching headings are an explicit error, and headings in code blocks do not count. The boundary has one blank line and a normalized trailing newline. Successful concurrent appends do not overwrite one another. CLI writes wait briefly to acquire a busy lock before reporting a timeout; they never retry an action already started or bypass its ETag check. It returns the saved full-document ETag and Git version. Use this operation for additions instead of reading and replacing the entire body.

`node get-section <id> --heading <title>` reads one complete Markdown section, including its heading, and returns `text` and an independent `sectionEtag`. It does not capture a whole-document version; saving captures the final document. The range ends at the next heading of the same or higher level; nested headings belong to the selected range and code-block text is not a heading. Missing or duplicate titles are explicit errors. `node write-section` takes the old title, that ETag as `--base-etag`, and complete replacement text as `--body`; the replacement can change or remove the heading. It compares the selected section under the mutation lock. Changes to that section conflict; changes elsewhere do not. Text outside the selected section remains unchanged; a missing separator before a following heading is added within the replacement range.

Both operations use normal address validation, Node synchronization and Git capture. Appending or replacing one section does not confirm existing material or output bases, so it cannot clear their drift. A section ETag cannot replace a full-document editing basis.

### Captures and diffs

Explicit saves capture selected identity documents' exact UTF-8 bytes into reachable commits in `.tent/.git`. Core Node, Role and Card reads capture only when explicitly requested with `capture: true`; ordinary UI browsing can stay read-only. Agent CLI live body/raw reads request capture automatically. No-op selected captures create no new commit. Discovery, historical reads and export do not capture. Reading one page retains the source document; it does not claim every page was read. Never-observed editor intermediates are not recoverable by contract.

Capture constructs each selected tree in an isolated Git index and then aligns the independent repository's ordinary index with committed HEAD. Unselected worktree bytes are never changed; external document edits remain visible as dirty files. Operational registry files, temporary data and attachments are excluded from this identity-document history through local info/exclude rules, preserving existing rules. No Git hooks run. A directory without independent Tent Git is not initialized by reading; such reads return no captured version. Card publication and reception require Tent Git.

`version: {commit,path}` names a complete history-document path within `.tent`. `node get --version-json` reads that exact Node after live edits, rename or deletion. Core `readDocumentVersion` also reads Role and Card documents. `node diff --from-json --to-json` compares two captured documents and reports path changes separately. Historical continuation binds the retained source, and cannot silently fall back to live bytes. Reachability and document paths are validated; Node-specific reads additionally validate Node identity.

Historical identity extraction, object trailers and queries use the same Node/Role/Card ID validators as live documents and preserve the original ID spelling, including accepted uppercase characters.

Captures carry `Tent-Operation`, repeated `Tent-Object` IDs and `Tent-Entry: cli|ui|core` commit trailers. Observed editor bytes use `document.external-capture`; Tent writes name the operation, such as `node.write` or `card.take`. Entry is selected by the calling adapter. These labels explain the capture, not who originally authored the bytes. Core `listNodeVersions` follows identity across locations and deletion; `listHistoryChanges` returns chronological first-parent changes from an exclusive `from` to an inclusive `to`, with ISO commit `time`. Older commits without trailers remain inspectable by document identity. CLI `node history` and `workspace changes` paginate these results.

Structural operations capture selected preimages before destructive changes and capture final paths together. They recheck observed bytes/path after preimage capture. Locks serialize cooperating Tent writers; the final check and filesystem operation are not atomic against external editors. Filesystem writes and Git ref updates are also not one transaction: a failure can follow a saved file. Inspect actual bytes/history before retrying. Multi-document failure reports known saved paths and preimage evidence instead of a false complete success.

History consumers share one retained-history read within a command. Derived history data may be cached under `.tent/.git`, keyed by the exact HEAD; a changed HEAD invalidates those results, and a cache hit does not replay history. A complete retained-history cache can extend along a single-parent commit chain, reading only added commits and missing blobs. Reset, divergent or merge history and invalid caches rebuild from Git. The cache is disposable and never enters Node or Card documents. Current documents and workspace materials are still inspected on each query, since their bytes can change without moving HEAD. No persistent service is required.

Workspace relation queries validate fixed Card sources in one reachable history walk and one blob batch, preserving per-source failures and retained-edit detection (including edits later reverted). Revision polling reads the independent Git HEAD and its loose or packed reference directly; it does not start Git or retain a process-local revision cache.

### Node synchronization and outputs

`node check <id>` computes independent `ahead` and `behind` findings from the current Node and local materials without changing Nodes or capturing Git. A goal can have both findings; each counts separately. Neutral synchronization details remain available on inspection without becoming a task or map mark. These facts are independent of OKF lifecycle `status`. A matching version proves only that recorded bytes still match, not semantic correctness. Unavailable or remote versions remain explicitly unknown; inspection makes no network requests.

Creating or saving a Node automatically observes local `resource` and `sources` with SHA-256 of the selected Markdown section or, without one, the whole file. The basis is retained by Node ID in the same Git commit as the document, outside frontmatter. Retained first-parent history supplies the current record; resetting history also resets the basis. Derived file observations reuse a local file-signature cache across CLI invocations, separating complete files and individual sections. No manual hash input is needed. Ordinary saves retain existing material and goal versions, so an unrelated edit cannot clear `behind`. New declarations are observed on save; unavailable known materials retain their old basis. Reads and captures never refresh it. Batch writes record final saved documents and bases together and roll both back on failure.

Every `goal` is a requirement regardless of suffix. An output records the semantic version of its nearest goal ancestor as an implicit source; this version is independent of `generated.at` and verification timestamps. A goal with no output anywhere in its subtree is ahead. An output under a more specific nested goal counts as an output for the broader direction, but depends only on its nearest goal. Changing that goal makes its own outputs behind and the goal ahead until the affected outputs are reviewed and confirmed. A change to an output's material alone makes that output behind without claiming the goal changed. Changed known materials and expiry cause behind independently of ahead; matching material, verification or current own outputs can anchor a Node. Otherwise it is unanchored. Conversation-only Nodes do not need invented material references.

`node link-output <goal-id> --resource <address-or-node-id> [--name <name>] [--by <actor>]` creates a child output Node and returns its identity. Relative file paths resolve from the Workspace root; `/` addresses resolve from `.tent`, and Node IDs and absolute URIs are supported. Local files must exist and be readable before creation. The default name is the file name, with a number added on collision; `--name` overrides it. The saved resource is rewritten relative to the child. Remote addresses are retained without fetching. The goal itself is unchanged. Existing outputs can instead be moved into the appropriate hierarchy; the nearest goal relationship is established by Node IDs. There is no separate output association list.

After reading and reviewing a complete live Node and relevant materials, `node confirm <id> --base-etag <etag>` refreshes its material and implicit goal bases without changing its body. A corrected body can be saved and confirmed together with `node write --confirm`, or `confirm: true` in write JSON or a write-many update item. Unavailable known material remains behind even after confirmation. These mutations require a complete live-read ETag, validate addresses, use the mutation lock and retain the resulting Node and basis together in Git. Partial reads cannot authorize them. Node frontmatter has no synchronization, planning, output-list or hash fields; native OKF authorship, verification and lifecycle fields remain independent.

### Authorship, verification and expiry

Node writes use OKF's native `generated: {by, at}`, `verified: [{by, at}]`, `stale_after` and lifecycle `status`. Creating or meaningfully changing the body or semantic metadata records the producer and time in `generated`; reads, no-op saves, verification and lifecycle changes do not. Verification remains independent of generation: editing content retains earlier verification records. Confirmation adds or refreshes one record per actor, retaining that actor's latest timestamp. Readers also accept OKF's single verification mapping.

Content-writing and confirmation commands accept `--by`; JSON writes and batch items accept `by`. Actors use `human:<id>`, `process:<id>` or `<producer>/<version>`. An unavailable host identity is recorded as the actual `tent/<version>` runtime, never a guessed model or person. Only a `human:` verifier produces `human-reviewed` trust; another verifier produces `machine-confirmed`, and no verifier is `unverified`. Trust is derived evidence, not an access-control boundary or a guarantee that the content is true.

Native timestamps use ISO 8601 with an explicit timezone. At or after `stale_after`, inspection reports `behind`, independently of whether the Node is also ahead. A verification can anchor a Node when neither finding applies. Deprecated Nodes remain outside current context counts.

The Web API exposes derived `trustTier` on Node reads and writes. `POST /api/nodes/:id/confirm` takes a complete live `baseEtag` and optional `by`, preserving the body and generation record. Web saves and confirmation default to `human:<local-username>`; an explicit actor overrides that default. Confirmation uses the same mutation serialization, authentication, origin checks and CAS errors as document saves.

### Current context and drift

`workspace brief [--role <id>]` returns one discovery page of at most 4 KiB in text or JSON. Its first line reports only behind and ahead counts, followed by behind Nodes with reasons, then ahead Nodes with known age. It also shows pending work Cards, recently written files not recorded as outputs, and changed sources of received Cards whose source goal is still ahead. Completed old Cards do not crowd out current requirements. Recent unlinked files come from observations within seven days in one of the three most recently active sessions. Independent output Nodes already record their materials and are not unlinked findings. Omitted details are counted; addresses are never cut into misleading partial paths. The optional Role filters Card inputs and received-source warnings; Node counts remain workspace-wide. Card reception is never completion evidence. Repeated inspection conflicts produce uncertainty instead of a false current state.

`workspace drift` pages ahead and behind Nodes, with both findings when a Node needs both. Both commands inspect current local material versions even without Hooks. Tent does not discover arbitrary unobserved workspace files or treat independent dated output Nodes as unrecorded files.

`GET /api/sync` returns `{nodes: {[nodeId]: {ahead?: {since?, reasons}, behind?: {reasons}}}}` with only Nodes needing attention. Each request inspects current materials independently of the snapshot revision cache. The map overlays both marks when needed and refreshes on open, focus and save; its counts match the brief.

The Web home opens on Now unless the browser has saved another view. Its three sections show Role work from Card progress, outputs since the previous visit, and current ahead/behind findings. It only observes; nothing on it waits for the user. The snapshot derives `outputAt` from retained output creation, attachment under a new goal or confirmation, sharing the Card progress history replay. Ordinary edits do not refresh completion time. Only current, nondeprecated outputs enter the completion list; a Role's most recent completed Card is ordered by its output evidence rather than its reception time. These views add no document fields or independent completion state.

Session observations are local evidence, not a fourth semantic object or a Session registry. A record contains native session/turn identifiers, observation time, provided/read/written local file addresses, optional event time, whole-file SHA-256 or explicit uncertainty, and coarse possible-requirement/decision signals. It contains no file bodies, transcript text or tool output. Records live under `temp/observations/`, one append-only JSONL history per session, and are excluded from Git capture and export. Duplicate session/turn delivery appends nothing. The write uses the workspace lock and an atomic replacement preserving earlier lines; readers report incomplete/corrupt records as uncertain. Hashes observed at Stop are labeled as Stop-time versions, not historical read-time proof.

SessionStart retains only the Tent Git commit cursor in a hashed local session baseline. Stop retains its current cursor and checks Node/Card mutation operations since that session's previous Stop or initial baseline, excluding read captures and Role-only changes. Explicit successful transcript file changes to Node/Card documents also count. These observations suppress redundant intent questions; they do not prove which Agent made a concurrent Workspace mutation. Without a retained boundary, older Git history is not treated as this turn's work. Neither cursor is a prompt baseline, registration or ownership record.

## 4. Role

A Role is one OKF document at `roles/<roleId>.md` with `type: role`, `id: role-…` and an optional readable title. It holds a work direction, boundaries, methods and selected references. Shared business facts remain Nodes. The Markdown is the authority; there is no metadata registry, reverse Card list or implicit responsibilities import.

`role list` reads bounded headers without capture. `role create` saves a new document; identity cannot reuse a path already retained in Tent Git. `role show` returns a bounded body/raw page with exact ETag and captured version. `role write --base-etag` uses raw CAS and the shared mutation lock; no-op saves can capture editor bytes without rewriting them. Unknown metadata survives and lifecycle status stays local.

Role selection is explicit. Reading it does not bind a Session, claim occupation, read every related Node, create missing context, repair an invalid document or resume a pending structural operation. Missing or invalid Role documents are diagnostics. A new host conversation may explicitly read the same Role to recover its maintained direction.

## 5. Card

A v3 Card is one Markdown document at `cards/<cardId>.md` with `type: card`, `id`, `schemaVersion: 3`, optional `title`, ordered `sources`, optional target Role id, reception fields, and the prompt in its body. Creation publishes it immediately and requires a prompt, sources or both. Sources use OKF resource declarations; explicitly selected Nodes and Roles receive Git `{commit,path}` versions. External addresses are not fetched or captured. Cards do not record a sender or creator Session.

Creation captures only selected internal sources before publishing the Card. A supplied Git source is validated without reading its current live path. The first reachable path-addition commit is the input baseline, and identities retained in history cannot be reused. There is no separate publication operation or persistent Card draft. Undecided requirements belong in Nodes with `status: draft`. The browser keeps unsent Card content locally and submits it directly to `POST /api/cards` when sent.

Published body, title, ordered sources and unknown metadata are immutable input. Hand-edited input remains raw-readable but reception and management operations reject `INPUT_CHANGED`. Requirements and decisions belong in Nodes; edit those Nodes when they change. Live Node moves do not rewrite old Card input or pinned sources. For received Cards, brief compares pinned Node bytes with current bytes by stable Node ID. An edit or missing source asks the receiver to reread the current requirements; an unrelated commit alone is not a content change.

`card move <id> --to <roleId> | --public --base-etag <etag>` is the explicit exception for a published Card's destination: only pending Cards can move. It uses the reception mutation lock, checks the observed ETag and destination Role, and retains each changed destination as `card.move` history. Clearing the target returns the Card to the public area. A no-op validates its ETag without adding a commit. A consumed Card cannot move. Hand-edited target changes conflict with retained management state.

`card deprecate <id> --base-etag <etag>` cancels a task through lifecycle `status: deprecated`, including after reception. It preserves reception and immutable input, uses CAS and records the management change in Git. Lists and brief omit deprecated Cards by default; `--include-deprecated` includes them. Explicit show or take warns and exposes current references, while preserving the ordinary Role gate.

`card list` reads published Cards without capture and returns reception, publication time and derived progress. An unretained handwritten file is not a published Card. `card show/get` previews a bounded body/raw page without receiving or executing it. Omitted oversized source metadata has a raw read address rather than truncated executable references. An exact Node source can be read using `node get --version-json`.

`card watch --role <role-id> [--timeout <seconds>]` waits for committed, nondeprecated pending Cards addressed to exactly the supplied available Role. It checks immediately, then reads only the independent Git HEAD every three seconds while unchanged; a changed HEAD triggers another Card query. Queries read the committed Card directory without history replay, cache writes or any other file writes. Matching Cards return immediately with one text line per Card containing its id, optional title and `tent card take <id> --role <role-id>`; JSON returns an array. Exit codes are 0 for input, 2 for timeout with no output, and 1 for errors. Omitted timeout waits indefinitely; zero checks once. Watching neither receives Cards nor registers waiting Sessions. Agents choose their own host wakeup mechanism and ask before creating a new persistent automation.

### Reception and outputs

State is `pending` or `consumed`. Pending has no `receivedBy`. An untargeted Card may be received with or without a Role; a selected Role is recorded as `receivedBy`. A targeted Card requires its specified available Role. Missing, invalid, deprecated or unsupported Role targets are diagnostics, never an open fallback.

`card take` validates published input and retained management state under the shared mutation lock, records consumed and returns a bounded input page. Retries with the same Role choice return `replayed` without authorizing another execution. Once received, adding, removing or changing the Role conflicts. No reception operation takes a Card Git version. There is no interrupted or completed state; finished Cards remain consumed.

Progress follows the goals referenced by the Card's sources and outputs anywhere in each goal's subtree, including outputs beneath nested goals and outputs without a `resource`. Only outputs attached to that subtree or confirmed after publication count. This uses the same subtree scope as a goal's ahead finding; an output's synchronization basis still belongs to its nearest goal. A received Card has `has-output` only when every referenced goal has such an output; otherwise it has `received-no-output`. Pending Cards retain `pending`. Derived `goalCount`, `totalGoalCount` and `outputNodeIds` allow views to show progress such as `1/2`. Cards without goal sources have `progress: null` and show reception only. These are query results, never Card frontmatter. Compare actual outputs with their current goal versions before claiming completion.

`node link-output` needs no Card parameter, output Card source, host round context or additional Hook. Questions, research and pending decisions use prompt Nodes; only implementation results count as outputs. Brief and the map can display progress without a return Card.

Manual reception fields differing from retained state remain raw-readable and diagnostic. An explicit take may finish an interrupted pending-to-consumed transition when input, target and status are unchanged and the saved receiver exactly matches the request; it captures those saved bytes. Other management edits remain conflicts. A subsequent identical take is a replay and adds no commit. Lifecycle status is independent. File/Git failures can follow a saved document; reread before retrying. Reception proves neither comprehension nor exactly-once execution.

## 6. Persistence, recovery and historical data

Sketches are workspace material files: use Excalidraw itself to save a sketch, then reference that file from a Node.

All current document mutations use the Core workspace lock. Short-lived CLI processes share an exclusive on-disk mutation lock and directory guard for its bookkeeping. A live PID is not evicted because of age alone; release checks its ownership token. A crashed guard is reclaimed when its PID is absent, retaining a small tombstone directory so delayed contenders cannot displace its successor. PID reuse can require manual cleanup after all Tent writers stop; the timeout identifies the guard path. No persistent HTTP Service, watcher, event bus, Session token service or RPC passthrough is part of the current runtime. `tent ui` is an explicitly started foreground exception: a loopback HTTP server for the bundled UI, ending with its process, without Session registration or filesystem watchers. The UI polls `readWorkspaceRevision` for refreshes; ordinary browsing is read-only, while explicit edit reads capture their basis.

`tent ui [--workspace <path>] [--port <number>] [--no-open]` resolves an existing workspace, prints its URL and opens the default browser unless suppressed. It remembers opened workspaces in a per-user file outside `.tent`; the page can open other existing workspaces in the same process, and Ctrl+C closes all of their servers. The server uses a fresh launch token, checks Host/Origin, and writes through Core's ETag and workspace lock. Its API is private to the matching bundled frontend, not a public integration protocol. npm and plugin distributions include UI assets; development snapshots and source maps are excluded.

Recognizable retired stores at the root of `.tent`, such as an old `snapshots/objects` layout, produce one consolidated diagnostic before Node indexing. They are neither imported nor deleted automatically. Names such as `notes` or `snapshots` remain valid for ordinary Nodes and grouping folders; a matching identity document identifies a current Node.

Move/rename saves a pending plan before changing directories, links and order. Removing the verified plan commits the operation. The next mutation rolls back an interrupted move under the existing lock; conflicting external bytes preserve the plan and stop recovery. Reads do not resume it. This covers process interruption, not a promise of power-loss durability or control over external editors.

Node deletion records exact primary data and associated order writes in `delete.pending.json`. Moving the primary object to quarantine is the logical deletion point; subsequent mutations can finish verified cleanup. Reused identity or changed associated bytes causes conflict. Export rejects pending operations.

## 7. Export

`tent workspace export --output <new-directory>` creates a separate complete-graph directory and byte inventory. It preserves persistent documents, unknown metadata, order, Git history, Roles, Cards, attachments. Credentials, locks, runtime state, disposable checks and temporary files are excluded. Source data is never repaired or switched.

Export inventories the source under the workspace lock, copies and verifies it, then checks source membership/hashes again under the lock before publishing. Pending operations, invalid required history or missing referenced local materials prevent publication. Filesystem copying does not claim a transaction with arbitrary external editors.

Live standard references inside `.tent` are checked against copied files/directories. v3 Card sources validate against copied reachable Git history; their old paths need not exist live. External workspace targets and absolute URIs are listed in `externalNotPacked` with origin, declaring path and occurrence index; bytes are not copied. Bare sources, invalid locators and nonstandard metadata appear in `unresolvedMaterials` without guessing or rewriting.

## 8. Plugin and Hooks

The four Skills are `tent-init` for empty setup, `tent-node` for relevant input and Node maintenance, `tent-role` for persistent work direction, and `tent-card` for recorded prompt input. Role and Card are independent optional objects. Command details live in on-demand references. Skill use requires no initial decomposition, fixed reading sequence, per-turn Node count, full-tree verifier or separate return procedure.

The plugin supplies a bundled CLI with its runtime dependencies and uses its installed package path. It does not guess an executable from cwd, store graph data in a plugin cache, install global Hook copies, or configure MCP. npm delivery installs its declared runtime dependencies separately. Build/install/trust and real event delivery are distinct checks; package presence does not prove native activation.

`tent --version` displays the version, commit and build-session start time. `tent version --json` returns `version`, `commit`, `builtAt`, `dirty` and `runtimePath`. Built CLIs embed their identity independently of their installation path and adjacent package metadata; source execution has `builtAt: null`, and watch rebuilds share their build session's identity. Unknown Git identity remains null. This is local provenance, not a network update check.

Codex SessionStart returns the available workspace, current package entry, build identity and a short `workspace brief` hint, without loading the brief. It reports a commit mismatch only when the workspace is positively identified as a Tent source checkout; different commits do not establish which is older. It does not register Sessions, read Role/Node bodies, repeat Skill descriptions or create a prompt baseline. There is no PromptSubmit or SessionEnd registration or Claude-specific Hook. Role selection remains explicit.

Stop requests asynchronous execution and emits informational JSON only. The handler never returns a blocking or continuation decision. `async: true` is not proof that a particular installed host honors background execution or delivers its output. Qualify the actual frozen host; if unsupported, leave Stop disabled and use Start plus normal CLI operations.

Activity observation is limited to the last 1 MiB of transcript and the native turn id. Explicit local inputs, successful structured read/image commands and successful file changes provide evidence; arbitrary shell text or opaque tool calls are not guessed into file facts. Partial tails, unavailable versions and unrecognized activity retain uncertainty. Cancellation preserves already observed file facts but emits no questions. Duplicate Stop events are silent. Intent signals require explicit decision language such as “决定”, “确认”, “改成”, “新增需求”, “decided”, “confirmed” or “agreed”; ordinary requests such as “请”, “需要”, “please”, “need” or “fix” are not signals. Synthetic heartbeat and environment instructions contribute none. A turn that already changed a Node or Card does not receive another intent question.

Stop asks at most three concrete questions in English with candidate answers about a newly observed unlinked output, a newly observed changed material affecting a behind Node, or possible new intent/decisions. A changed judgment calls for updating the Node and confirming its basis. Prior observations in the same session suppress repeated questions for an unchanged file version. Complete informational JSON, including encoding overhead, is at most 2 KiB. Uncertain observation alone may emit a brief uncertainty notice. The handler appends observations but never saves Node judgments, captures Node Git history, resumes structural recovery or automatically continues the Agent. The Agent answers through normal Node maintenance after reading the necessary live context.

A Hook notice proves neither semantic synchronization nor an extra Agent pass; asynchronous output may appear in the UI or a later turn. Agent judgment and normal maintenance remain necessary. Native host identity, trust and delivery must be verified in the actual host; synthetic JSON tests only validate the handler.
