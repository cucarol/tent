# Tent V0.1 Specification

This document defines Tent's current public contract. Retired commands and wire fields are removed rather than kept as aliases. Core owns document semantics and local persistence; the CLI and plugin are thin entrypoints.

## 1. Purpose and workspace

The three semantic concepts are Node, Role, and Card. Tent maintains useful parts of Agent context as linked Markdown documents: Nodes preserve reusable facts and references, Roles preserve a work direction, and Cards record prompt inputs. Normal work, answers, code edits, review and Git integration remain in the host conversation and the user's tools. Ordinary tasks need no Role or Card. There is no separate Return, managed Agent, Session registry, occupation system or task scheduler.

One Tent belongs to one workspace: the directory containing `.tent/`. Its stable `workspaceId` lives in `.tent/settings.json` and survives relocation. Ordinary commands use existing settings; they do not repair, reidentify or register the workspace. Missing or corrupt identity fails explicitly. A saved identity does not establish exclusive ownership across separate copies.

`tent new <workspace>` prepares an empty scaffold and independent local Git repository in a workspace-local staging directory before publishing `.tent/`. Failed preparation removes its owned staging directory and remains retryable; existing `.tent` data is never replaced. Initialization creates no Node, Role registry, remote or empty commit and does not analyze or split the project. The workspace may itself use Git or ordinary files. `.tent/` is excluded from the product repository; its Git history is independent.

Project instructions remain in workspace `AGENTS.md`. Tent neither copies their authority nor configures third-party analysis applications. Desktop, execution engines and application/format adapters are outside this version. The bundled Web UI reads and edits the same local graph through Core.

## 2. Node and OKF fields

A Node is a directory with its identity Markdown at `<directory>/<basename>.md`. A directory without that identity file is a transparent grouping folder: its Nodes belong to the nearest ancestor Node, or to the root. Placement expresses the parent/child tree; a stable `node-…` id remains the lookup handle across moves and renames. A Node has one non-empty `type` field in `primary[-secondary]` form: `primary` is `goal`, `prompt`, or `output`, and the optional suffix is project-defined. The primary type says what the content rests on: `goal` holds intent confirmed by the user, `prompt` holds agreements later work follows, and `output` holds evidence observed at a point in time. Any non-empty suffix is valid and serves only as a label. Core exports `NODE_TYPE_PRESETS`: `goal-direction|requirement|todo|question`, `prompt-spec|rule|decision|reference|procedure` and `output-asset|evidence|analysis|issue`. These are a default menu; no suffix imposes behavior, registry or extra lifecycle. There is no separate kind field.

The filename is the display name. If `title` is present, saves and structural renames keep it aligned; it is not another identity. Tags belong in each document and are aggregated on demand. Unknown YAML fields survive ordinary edits. Invalid identity/type data and duplicate handles are diagnosed, not silently repaired. Unusable subtrees stay outside ordinary content operations; explicit raw inspection remains available where supported.

Record context that will help later work: confirmed goals and constraints, useful reference pointers, observed findings, decisions and facts about real outputs. Goals can exist before implementation; unperformed results cannot. Prefer an existing fact owner and split independently useful context as it emerges. No initial task skeleton, per-turn quota, copied transcript or full-tree maintenance pass is required.

`goal` and `prompt` keep confirmed intent, agreements, decisions and their reasons, including who confirmed them and when if known. They do not carry commit ids, test counts or merge/delivery status: consult Git and Card history for those records. Useful verification belongs in dated `output` evidence. A Card's reception state is not evidence that its requested work is complete.

### Lifecycle

Reuse OKF `status: draft|stable|deprecated`; omitted means stable. Status is local to the document. Editing, Git versions, material changes, checked-material records and parent status do not change it automatically. Unknown values remain intact with a diagnostic and no assumed currentness; an ordinary CAS edit may preserve them or explicitly replace them with a supported value.

Deprecated Nodes remain explicitly readable and editable without reactivation. Default content search excludes them; hierarchy navigation can expose a deprecated ancestor to reach a current child. Unknown fields, including `mode`, are ordinary metadata and do not control lifecycle.

`node archive <nodeId>` preflights the current subtree and writes deprecated only to documents not already deprecated. It captures selected preimages and returns the Git commit containing the status changes; a no-op subtree creates no commit. `node restore <nodeId> --archive-commit <commit>` accepts a reachable single-parent commit containing only the relevant status-to-deprecated edits. Current identities, paths and bytes must still match, and no later retained change to those paths may exist, including edit-and-revert. Restoration changes only those status declarations, including an originally omitted value; it leaves previously deprecated and newly added children alone. It never resets Git or revives deleted documents. Never-captured external edit-and-revert intent cannot be inferred.

### Materials and links

Reuse `resource` for the primary described material and ordered `sources` for independently related material. Each source has `resource` and may preserve standard or custom descriptive metadata. Source order, repetitions and spelling remain significant. These references locate materials; they do not prove ownership, access, synchronization or a complete impact set.

Local paths use `/` separators. `./` and `../` resolve relative to the declaring Markdown; leading `/` resolves from `.tent` and cannot escape it. A `file:` URI names an absolute filesystem path. Relative paths can reach workspace material outside `.tent`. Queries/fragments and percent encoding retain their reference meaning. Windows drive paths and UNC spelling must use a URI rather than an ambiguous local path. Node creation and writes validate new or changed addresses without requiring file existence; unchanged legacy addresses remain editable. Source reordering, removal and metadata edits retain existing address occurrences, while additional occurrences require validation.

A bare `sources.resource` can be ordinary description. Tent preserves it as unresolved instead of guessing from an extension or the existence of a similarly named file. Use an explicit `./`, `../`, `/` or absolute URI when mechanical resolution is wanted. A spaced label such as `note: reference` is description; an unspaced URI such as `urn:example:1` is an address. `resource` itself is a material address. Remote URIs are addresses and are not fetched by Tent.

Standard Markdown links and standard fields support discovery of related Nodes. One Markdown AST parser drives relationship discovery and link rewriting, including reference-style links. Lookup matches exact identity, path or full name; ambiguous names remain unresolved. Wiki text such as `[[Name]]` is ordinary text. Core saves turn known Node IDs in link destinations, `resource` and `sources.resource` into relative document paths. Occurrences keep their original ranges and declaration paths. Unresolved references are visible. Tent does not add an in-document annotation protocol. Moves/renames rewrite resolvable affected live links and material addresses while preserving unknown fields, source order and occurrences; they do not rewrite historical Card input. Code, quoted HTML and unrelated text are not interpreted as links to rewrite.

Materials use only `resource` and `sources`. Other custom fields survive without transformation or material semantics. The Agent uses its existing tools to read actual materials; Tent provides no application or media adapters.

Markdown paths leaving `.tent` remain external to the Node index, even when an internal Node has the same trailing path. Internal Node renames must not redirect these references; moving the declaring Node adjusts relative addresses to preserve their original material targets.

## 3. Reading, editing and local Git

### Progressive disclosure

Header discovery resolves identity, hierarchy, status and duplicates without reading unrelated bodies. NodeFs reads frontmatter in 512-byte blocks and stops at the closing fence; an unterminated header may require EOF to diagnose it. This is still an O(N) metadata scan, without a watcher/cache or an atomic snapshot of concurrent editor changes.

Core queries return complete metadata and requested text, without CLI byte budgets, pagination or continuation cursors. CLI `node list`, summary reads and parent/children navigation disclose bounded metadata including `description`; type and tags aid discovery. Oversized display metadata is marked and retains a raw `metadataRead` address. Metadata-only responses do not provide a full-document write basis or capture Git. A full text read can be required for body search or link relations, but discovery never captures versions.

`listWorkspaceRelations` returns Markdown-link and standard-field occurrences from all valid Node, Role and Card documents in one query. It uses the same Markdown parser and material resolution rules, preserving source indices and body ranges. Retained Card sources resolve to their historical identity even after live moves or path reuse; `changedSince` reports retained path changes, including edit-and-revert. Invalid version declarations remain explicit diagnostics. Discovery does not receive Cards or capture history.

`readWorkspaceRevision` hashes identity-document paths and bytes, order, settings, annotations and the independent Git HEAD. External edits are observed even when size and modification time are unchanged. It performs no Markdown parsing, capture, repair, stat-only cache or background watching; it is a change indicator, not an atomic filesystem snapshot.

`node get` body/raw reads load the selected full document after a matching header observation. `node get <nodeId> --full --json` supplies the complete body and exact ETag for CAS editing; add `--view raw` for the complete original document including frontmatter. The internal `readNodeForEdit` function returns the raw editing snapshot. An initially invalid document, a lookup-to-read conflict and an I/O failure remain distinct errors. `node list --full` explicitly reads and captures the full tree; it is not the default discovery path.

Agent-facing Node, Role and Card reads use `text` for body and raw content, including `node get --full`, `node list --full` and `read-many` items. The selected view changes the content, never the field name; read responses have no `body` alias. Structured write inputs still use `body` to distinguish a replacement body from a raw document.

CLI Node reads without the complete body or raw document mark their ETag as `read:<etag>`, including metadata, partial pages, non-first fragments and bounded single-save readbacks. This basis can continue reads and support metadata-only edits, but Core rejects it for body/raw replacement with `INCOMPLETE_READ`; callers must obtain a complete live read first. A complete single-response body/raw read retains the canonical ETag. Batch save receipts return the canonical saved ETags for the writer's known complete inputs; they are not discovery reads. The marker prevents accidental replacement from incomplete reads; it is not authorization, a signed receipt or proof against a caller deliberately removing it. Core's complete document reads and UI editing snapshots retain canonical ETags.

CLI body/raw, search and relation pages share a 16 KiB compact JSON budget. Large display values are marked as truncated or omitted and retain exact source ranges and qualified read addresses; a truncated display is not an executable material reference. Oversized occurrences must not prevent later results from being enumerated. Text ranges use UTF-16 offsets and preserve surrogate pairs and CRLF boundaries. Body excerpts address original text.

Cursors are deterministic continuation addresses usable across short-lived CLI processes, not permissions or signed receipts. They bind source, query, observed revision and position. A changed relevant revision requires a fresh query. Header/hierarchy cursors survive body-only changes, while text cursors require the observed body revision. No cursor secret or Session cache is needed. Role/Card pages carry explicit ETag/range continuations. Summary requests do not accept text ranges, cursors or an expected full-document ETag.

Core `readNodeBatch` accepts an ordered unique `nodeIds` list, `view: body|raw` and optional `capture`; it returns every selected document. CLI `node read-many` adds `start` and a response budget including outer fields, selects the deliverable documents before capture and retains only that subset. An item's partial text continues through `node get`; outer `page.nextIndex` starts a fresh live batch, not a whole-graph snapshot. Capture failure fails the call without claiming a successful batch.

### Save semantics

`node write --input-json` accepts an observed `baseEtag`, body and/or frontmatter patch, and optional `readBack`. Omitted fields and unknown metadata survive. Raw edits and structured edits use the same Core rules. Identity, type and lifecycle retain their explicit validation. A stale basis is rejected; the CLI must not refresh it just before overwriting.

The default save response contains metadata and the captured Git version. Core `readBack` returns requested text from the actual saved bytes without rereading the file; CLI bounds that response. A partial page does not mean the whole body was read. No-op saves validate CAS, avoid rewriting Markdown and still capture newly observed bytes when needed.

Node and Role edits recheck their originally observed bytes after asynchronous reference resolution, before saving or capturing the result. An intervening external edit is a conflict; it does not become a refreshed write basis. Storage errors remain storage errors.

Creation can save body, resource, sources and tags together. An initial file/order failure rolls back the newly created Node. Deletion removes a whole Node subtree without requiring archive first; it does not delete referenced materials or rewrite inbound references. Move children that should survive before deleting their parent.

`writeNodesBatch` / `node write-many --input-json` accepts `{items:[...]}` with ordered `create` and `update` operations. A create supplies a unique local `ref`, `name`, `type`, optional `parent`, body, tags and material fields. `@ref` identifies a Node created by this batch in parent references, Markdown link destinations and material addresses; forward references and mutual links are supported, while cyclic parents and unknown references are rejected. An update supplies an existing `nodeId`, a complete live-read `baseEtag`, and raw or structured changes. Duplicate updates, stale ETags and incomplete `read:` bases are rejected before saving.

The batch validates and prepares every final document before writing, holds one Workspace lock, and captures its changed documents in one Tent commit. A failed batch rolls back its own document, directory and ordering changes; rollback failures report affected paths and conflicts while preserving external edits. Existing pending structural recovery runs first under the same lock and retains its separate recovery history. Results preserve input order and contain each saved `nodeId`, `path` and exact `etag`, so known complete inputs need no confirmation read. The batch does not return a copy of every body. No-op batches add no commit when the selected bytes are already retained. The lock serializes Tent writers; it does not make filesystem writes and Git atomic against external editors or process termination.

`checkGraph` / `workspace check` inspects Node, Role and Card documents without editing, history capture or structural recovery. It returns compact `issues` for `unresolved-link`, `invalid-material-address` and `missing-material-file`, plus `errors` for documents that cannot be fully inspected. Paths are relative to `.tent`; local file presence uses Workspace-relative and absolute `file:` resolution. External URIs and plain source descriptions are not fetched. Retained Card sources are checked against their pinned versions. CLI exits zero for a clean report and one when issues or inspection errors exist, retaining the JSON report on stdout. This checks addresses and file presence, not semantic freshness or source hashes; `node check` remains the separate per-Node material-version operation.

### Captures and diffs

Explicit saves capture selected identity documents' exact UTF-8 bytes into reachable commits in `.tent/.git`. Core Node, Role and Card reads capture only when explicitly requested with `capture: true`; ordinary UI browsing can stay read-only. Agent CLI live body/raw reads request capture automatically. No-op selected captures create no new commit. Discovery, historical reads and export do not capture. Reading one page retains the source document; it does not claim every page was read. Never-observed editor intermediates are not recoverable by contract.

Capture uses an isolated Git index, leaves unrelated staged/dirty documents and the user's index untouched, and does not run Git hooks. A directory without independent Tent Git is not initialized by reading; such reads return no captured version. Card publication and reception require Tent Git.

`version: {commit,path}` names a complete history-document path within `.tent`. `node get --version-json` reads that exact Node after live edits, rename or deletion. Core `readDocumentVersion` also reads Role, Card and annotation documents. `node diff --from-json --to-json` compares two captured documents and reports path changes separately. Historical continuation binds the retained source, and cannot silently fall back to live bytes. Reachability and document paths are validated; Node-specific reads additionally validate Node identity.

Historical identity extraction, object trailers and queries use the same Node/Role/Card ID validators as live documents and preserve the original ID spelling, including accepted uppercase characters.

Captures carry `Tent-Operation`, repeated `Tent-Object` IDs and `Tent-Entry: cli|ui|core` commit trailers. Observed editor bytes use `document.external-capture`; Tent writes name the operation, such as `node.write` or `card.take`. Entry is selected by the calling adapter. These labels explain the capture, not who originally authored the bytes. Core `listNodeVersions` follows identity across locations and deletion; `listHistoryChanges` returns chronological first-parent changes from an exclusive `from` to an inclusive `to`, with ISO commit `time`. Older commits without trailers remain inspectable by document identity. CLI `node history` and `workspace changes` paginate these results.

Structural operations capture selected preimages before destructive changes and capture final paths together. They recheck observed bytes/path after preimage capture. Locks serialize cooperating Tent writers; the final check and filesystem operation are not atomic against external editors. Filesystem writes and Git ref updates are also not one transaction: a failure can follow a saved file. Inspect actual bytes/history before retrying. Multi-document failure reports known saved paths and preimage evidence instead of a false complete success.

History queries collect commit metadata and first-parent changes in one Git log and read unique document blobs through one query-scoped batch process. Blob contents are streamed and only identities remain in memory; the process ends with the query. This avoids starting Git for every commit and file, without adding a persistent service or cache.

Workspace relation queries validate fixed Card sources in one reachable history walk and one blob batch, preserving per-source failures and retained-edit detection (including edits later reverted). Revision polling reads the independent Git HEAD and its loose or packed reference directly; it does not start Git or retain a process-local revision cache.

### Material checks

After actually checking real material, the Agent may confirm `node check` with `{expectedPath,expectedEtag,materials:[{resource,canonicalPath,observedVersion}]}`. Each supplied local resource or file URI resolves from its declaring document; `canonicalPath` is the absolute observed file and `observedVersion` its SHA-256 byte hash. Only supplied materials participate. Remote or ambiguous sources are not mechanically checked.

Confirmation validates current Node/material versions and writes one latest disposable record under `temp/material-checks/`. It changes no Markdown, status or Session state and requires no explanation or Return. Inspection reports missing, current, changed or unavailable. Current means the versions still match that assertion; it proves neither semantic correctness nor coverage of every reference. An incompatible record is changed until reconfirmed. Inspection takes the existing lock without resuming structural recovery; confirmation uses the normal mutation boundary. Export excludes this cache.

## 4. Role

A Role is one OKF document at `roles/<roleId>.md` with `type: role`, `id: role-…` and an optional readable title. It holds a work direction, boundaries, methods and selected references. Shared business facts remain Nodes. The Markdown is the authority; there is no metadata registry, reverse Card list or implicit responsibilities import.

`role list` reads bounded headers without capture. `role create` saves a new document; identity cannot reuse a path already retained in Tent Git. `role show` returns a bounded body/raw page with exact ETag and captured version. `role write --base-etag` uses raw CAS and the shared mutation lock; no-op saves can capture editor bytes without rewriting them. Unknown metadata survives and lifecycle status stays local.

Role selection is explicit. Reading it does not bind a Session, claim occupation, read every related Node, create missing context, repair an invalid document or resume a pending structural operation. Missing or invalid Role documents are diagnostics. A new host conversation may explicitly read the same Role to recover its maintained direction.

## 5. Card

A v3 Card is one Markdown document at `cards/<cardId>.md` with `type: card`, `id`, `schemaVersion: 3`, optional `title`, ordered `sources`, optional target Role id, reception fields, and the prompt in its body. Publication requires a prompt, sources or both; an unpublished draft may be empty. Sources use OKF resource declarations; an explicitly selected Node or Role receives a Git `{commit,path}` on publication. External addresses are not fetched or captured. No new whole-graph snapshot, creator Session, external byte package or separate receipt is created.

Creation captures only selected internal sources before publishing the Card. A supplied Git source is validated without reading its current live path. A handwritten v3 Card requires explicit `publish` with its observed ETag; publication captures its final resolved input, not an earlier unversioned draft. The first reachable path-addition commit is the input baseline. Deleted identities cannot be silently reused.

Published body, title, ordered sources and unknown metadata are immutable input. `target`, `state`, `receivedBy` and lifecycle `status` are management fields. Hand-edited input remains raw-readable but reception/state changes reject `INPUT_CHANGED`; a changed request is a new Card. Live Node moves do not rewrite an old Card's input or Git sources.

`moveCardDocument` and `card move <id> --to <roleId> | --public --base-etag <etag>` change a published pending Card's target under the same mutation lock as reception. The observed ETag is required, destination Roles must be available, and each changed destination is retained as `card.move` history. Clearing target returns the Card to the public area. A no-op validates the ETag without a new commit. Consumed and interrupted Cards cannot move; conflicts include current reception fields. Hand-edited target changes differ from retained management state and fail with `STATE_CHANGED`, not `INPUT_CHANGED`.

`createCardDraft`, `writeCardDraft` and `deleteCardDraft` hold the workspace mutation lock without capturing the Card or its sources. A draft has no publication history; this is independent of OKF lifecycle `status: draft`. Saving requires its observed ETag and replaces prompt, ordered sources and target, preserving unknown metadata and an omitted title. Omitted sources become empty and omitted/null target becomes public. Draft deletion also requires its ETag and writes an identity reservation at `cards/.deleted/<cardId>` before removing the Markdown; the reservation is workspace data, not publication history. Failed deletion can be retried, but that identity cannot be created, saved or published again. Published files cannot be saved or deleted through draft operations. Explicit `publishCardDocument` resolves and captures the final input; empty drafts cannot publish and `card take` rejects unpublished drafts with `UNPUBLISHED`.

`card list` reads headers without capture or a claim of executable-input validation; it includes title, `draft` and the first publication timestamp derived from Git (`null` for drafts). Drafts are excluded by default; Core `includeDrafts` / CLI `--include-drafts` includes them only when no reception `state` filter is set. Thus `--state pending` never returns unfinished drafts, even with `--include-drafts`. A header without readable history is not evidence of publication. `card show/get` previews a bounded body/raw page without receiving or executing it; reading a draft does not publish it. Omitted oversized source metadata has a raw read address rather than truncated executable references. An exact Node source can be read using `node get --version-json`.

### Reception

State is pending, consumed or interrupted in the same document. Pending has no `receivedBy`. An untargeted Card may be received with or without a Role; when selected, that Role is recorded as `receivedBy`. A targeted Card requires the specified Role. Missing, invalid, deprecated or unsupported Role targets are diagnostics, never an open fallback.

`card take` validates published input and retained management state under the shared mutation lock, records consumed and returns a bounded input page. Retries with the same Role choice, including no Role, return replayed without authorizing another execution. Once received, adding, removing or changing the Role conflicts. A receipt without a Role does not identify a particular Session or establish ownership. `interrupt` and `continue` require the observed Card Git version. Later retained changes invalidate it, including state ABA, while unrelated commits do not. Interrupted input requires explicit continue. Normal completion stays consumed with no Return or completed state.

Manual reception fields differing from retained state remain raw-readable but are not captured as fresh reception proof. Lifecycle status is independent. File/Git failures can follow a saved document; reread before retrying. Reception proves neither comprehension nor exactly-once execution. Automatic interruption is unavailable until actual host identity and event delivery qualify it; current explicit operations need no Session registry.

## 6. Persistence, recovery and historical data

Workspace annotations live in `.tent/annotations.json`, a system file rather than a Markdown annotation protocol or a Node. Version 1 has `{schemaVersion:1,map:{elements,anchors}}`: elements are JSON objects with unique nonempty string `id` and string `type`; other element fields are preserved. Anchors map element IDs to `{node,x,y}` with a Node ID and finite coordinates. Missing/deleted Nodes do not cause anchor removal. Deleted elements (`isDeleted: true`) and their anchors are omitted on save. Paint order is retained; keys are deterministic, with each element and anchor on one line.

`readAnnotations` is read-only and returns null document/ETag when absent. `writeAnnotations` replaces the file under the workspace mutation lock using `baseEtag` (`null` requires absence). Invalid input and stale bases fail explicitly. Exact no-ops neither write nor capture. Saves retain `annotations.write` history without a `Tent-Object`, using the adapter's entry; the UI adapter uses `ui`. Annotations participate in version reads, diffs and exports. An ordinary Node named `annotations` remains valid.

All current document mutations use the Core workspace lock. Short-lived CLI processes share an exclusive on-disk mutation lock and directory guard for its bookkeeping. A live PID is not evicted because of age alone; release checks its ownership token. A crashed guard is reclaimed when its PID is absent, retaining a small tombstone directory so delayed contenders cannot displace its successor. PID reuse can require manual cleanup after all Tent writers stop; the timeout identifies the guard path. No persistent HTTP Service, watcher, event bus, Session token service or RPC passthrough is part of the current runtime. `tent ui` is an explicitly started foreground exception: a loopback HTTP server for the bundled UI, ending with its process, without Session registration or filesystem watchers. The UI polls `readWorkspaceRevision` for refreshes; ordinary browsing is read-only, while explicit edit reads capture their basis.

`tent ui [--workspace <path>] [--port <number>] [--no-open]` resolves an existing workspace, prints its URL and opens the default browser unless suppressed. It remembers opened workspaces in a per-user file outside `.tent`; the page can open other existing workspaces in the same process, and Ctrl+C closes all of their servers. The server uses a fresh launch token, checks Host/Origin, and writes through Core's ETag and workspace lock. Its API is private to the matching bundled frontend, not a public integration protocol. npm and plugin distributions include UI assets and local fonts; development snapshots and source maps are excluded.

Recognizable retired stores at the root of `.tent`, such as an old `snapshots/objects` layout, produce one consolidated diagnostic before Node indexing. They are neither imported nor deleted automatically. Names such as `notes` or `snapshots` remain valid for ordinary Nodes and grouping folders; a matching identity document identifies a current Node.

Move/rename saves a pending plan before changing directories, links and order. Removing the verified plan commits the operation. The next mutation rolls back an interrupted move under the existing lock; conflicting external bytes preserve the plan and stop recovery. Reads do not resume it. This covers process interruption, not a promise of power-loss durability or control over external editors.

Node deletion records exact primary data and associated order writes in `delete.pending.json`. Moving the primary object to quarantine is the logical deletion point; subsequent mutations can finish verified cleanup. Reused identity or changed associated bytes causes conflict. Export rejects pending operations.

## 7. Export

`tent workspace export --output <new-directory>` creates a separate complete-graph directory and byte inventory. It preserves persistent documents, unknown metadata, order, annotations, Git history, Roles, Cards, attachments. Credentials, locks, runtime state, disposable checks and temporary files are excluded. Source data is never repaired or switched.

Export inventories the source under the workspace lock, copies and verifies it, then checks source membership/hashes again under the lock before publishing. Pending operations, invalid required history or missing referenced local materials prevent publication. Filesystem copying does not claim a transaction with arbitrary external editors.

Live standard references inside `.tent` are checked against copied files/directories. v3 Card sources validate against copied reachable Git history; their old paths need not exist live. External workspace targets and absolute URIs are listed in `externalNotPacked` with origin, declaring path and occurrence index; bytes are not copied. Bare sources, invalid locators and nonstandard metadata appear in `unresolvedMaterials` without guessing or rewriting.

## 8. Plugin and Hooks

The four Skills are `tent-init` for empty setup, `tent-node` for relevant input and Node maintenance, `tent-role` for persistent work direction, and `tent-card` for recorded prompt input. Role and Card are independent optional objects. Command details live in on-demand references. Skill use requires no initial decomposition, fixed reading sequence, per-turn Node count, full-tree verifier or separate return procedure.

The plugin supplies a bundled CLI with its runtime dependencies and uses its installed package path. It does not guess an executable from cwd, store graph data in a plugin cache, install global Hook copies, or configure MCP. npm delivery installs its declared runtime dependencies separately. Build/install/trust and real event delivery are distinct checks; package presence does not prove native activation.

`tent --version` displays the version, commit and build-session start time. `tent version --json` returns `version`, `commit`, `builtAt`, `dirty` and `runtimePath`. Built CLIs embed their identity independently of their installation path and adjacent package metadata; source execution has `builtAt: null`, and watch rebuilds share their build session's identity. Unknown Git identity remains null. This is local provenance, not a network update check.

Codex SessionStart returns the available workspace, current package entry and build identity. It reports a commit mismatch only when the workspace is positively identified as a Tent source checkout; different commits do not establish which is older. It does not register Sessions, read Role/Node bodies, repeat Skill descriptions or create a prompt baseline. There is no PromptSubmit or SessionEnd registration or Claude-specific Hook. Role selection remains explicit.

Stop requests asynchronous execution and emits informational JSON only. The handler never returns a blocking or continuation decision. `async: true` is not proof that a particular installed host honors background execution or delivers its output. Qualify the actual frozen host; if unsupported, leave Stop disabled and use Start plus normal CLI operations.

Activity observation is limited to the last 1 MiB of transcript and the native turn id. Cancelled or proven read-only turns are quiet. Known changed paths match declared local material using headers even when other commands have uncertain effects; the notice marks that attribution as incomplete. Unknown activity alone does not trigger a document scan or prove synchronization. At most five matching Nodes are examined, with a complete Stop response no larger than 2 KiB. A material-check record suppresses a candidate only while matching Node/material bytes and coverage remain current. These selected reads do not capture Git, mutate Markdown or resume structural recovery. Additional candidates require explicit discovery.

A Hook notice proves neither semantic synchronization nor an extra Agent pass; asynchronous output may appear in the UI or a later turn. Agent judgment and normal maintenance remain necessary. Native host identity, trust and delivery must be verified in the actual host; synthetic JSON tests only validate the handler.
