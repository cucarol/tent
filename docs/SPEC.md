# Tent V0.1 Specification

This document defines Tent's current public contract. Retired commands and wire fields are removed rather than kept as aliases. Core owns document semantics and local persistence; the CLI and plugin are thin entrypoints. Judgments such as ahead and behind are derived from current context. Events such as reception, verification and material baselines are retained.

## 1. Purpose and workspace

The three semantic concepts are Node, Role, and Card. Tent maintains useful parts of Agent context as linked Markdown documents: Nodes preserve reusable facts and references, Roles preserve a work direction, and Cards record prompt inputs. Normal work, answers, code edits, review and Git integration remain in the host conversation and the user's tools. Ordinary tasks need no Role or Card. There is no separate Return, managed Agent, Session registry, occupation system or task scheduler.

One Tent belongs to one workspace: the directory containing `.tent/`. Its stable `workspaceId` lives in `.tent/settings.json` and survives relocation. Ordinary commands use existing settings; they do not repair, reidentify or register the workspace. Missing or corrupt identity fails explicitly. A saved identity does not establish exclusive ownership across separate copies. Automatic discovery checks each directory for its own Tent and stops at a Git checkout boundary. At a linked worktree, it reads the `.git` pointer and `commondir` to find the main checkout’s `.tent/`, without starting Git. A submodule pointer without `commondir`, a nested clone, or a bare repository without a main checkout does not inherit a parent workspace. CLI commands and hooks share this discovery rule; Node edits from a linked worktree write to the main checkout’s `.tent/`. Material observations, drift and brief read the main checkout’s files, so unmerged worktree changes do not make Nodes behind. Explicit --workspace selects the intended workspace.

`tent new <workspace>` prepares an empty scaffold and independent local Git repository in a workspace-local staging directory before publishing `.tent/`. Failed preparation removes its owned staging directory and remains retryable; existing `.tent` data is never replaced. Initialization creates no Node, Role registry, remote or empty commit and does not analyze or split the project. The workspace may itself use Git or ordinary files. `.tent/` is excluded from the product repository; its Git history is independent. Initialization never edits project files or creates an attachments directory. In a Git project it adds `.tent/` to the exclude file resolved by `git rev-parse --git-path info/exclude`, shared by the main checkout and linked worktrees; existing ignore rules and project `.gitignore` bytes remain intact. Outside Git it writes no project ignore file.

Project instructions remain in workspace `AGENTS.md`. Tent neither copies their authority nor configures third-party analysis applications. Desktop, execution engines and application/format adapters are outside this version. The bundled Web UI reads and edits the same local graph through Core.

## 2. Node and OKF fields

A Node is a directory with its identity Markdown at `<directory>/<basename>.md`. A directory without that identity file is a transparent grouping folder: its Nodes belong to the nearest ancestor Node, or to the root. Placement expresses the parent/child tree; a stable `node-…` id remains the lookup handle across moves and renames. Creation requested by parent ID resolves that identity inside the same Workspace mutation lock as the write: a prior rename follows the original parent, while a missing or ambiguous parent fails without creating a child. Reuse of its old path never redirects creation to a different Node. Tent's Node vocabulary has three types: a Node has one `type`, exactly `goal`, `prompt` or `output`. Any other value, including a `goal|prompt|output-<label>` form, makes the document an invalid Tent Node; it is not converted. Retained Git versions follow the same rule: pinned Card sources and historical reads treat any other value as an invalid document. A Tent written before this rule is converted once, its Git history included, rather than read through an alias. Form and topic belong in tags. There is no separate kind field.

The filename is the display name. If `title` is present, saves and structural renames keep it aligned; it is not another identity. Names must be portable Windows file names on every platform: creation, rename and batch creation reject `< > : " / \ | ? *`, a trailing dot, and the reserved device names `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, `COM¹`, `COM²`, `COM³`, `LPT¹`, `LPT²` and `LPT³` in any case, with or without an extension. The raw input is rejected if it contains a C0 control character (U+0000–U+001F, including tab, CR and LF), DEL (U+007F), U+2028 or U+2029, even at either end; leading and trailing whitespace as JavaScript `trim()` defines it is then removed. C1 controls (U+0080–U+009F) are not rejected. Tags belong in each document and are aggregated on demand. `tags` is the native cross-cutting field of OKF v0.2 §4.1; Tent gives tags no behavior, registry or lifecycle, and keeps them free text without path separators or newlines. Core exports the suggested `NODE_TAG_PRESETS`: `direction`, `requirement`, `decision`, `spec`, `reference`, `procedure`, `asset`, `evidence`, `analysis` and `issue`. `node tags` without arguments lists the tags of current Nodes with their counts and marks presets; `--include-archived` also counts deprecated Nodes. Unknown YAML fields survive ordinary edits. Invalid identity/type data and duplicate handles are diagnosed, not silently repaired. Unusable subtrees stay outside ordinary content operations; explicit raw inspection remains available where supported.

Record context that will help later work: confirmed goals and constraints, useful reference pointers, observed findings, decisions and facts about real outputs. Goals can exist before implementation; unperformed results cannot. Prefer an existing fact owner and split independently useful context as it emerges. No initial task skeleton, per-turn quota, copied transcript or full-tree maintenance pass is required.

`goal` and stable `prompt` keep confirmed intent, agreements, decisions and their reasons, including who confirmed them and when if known. Context forms from Agent collaboration alone: an Agent decides within its Role or sends a Card to the Role that owns the decision, without waiting on the user. A user may intervene by changing any Node, but observing is enough. An undecided proposal belongs in a `prompt` with `status: draft`, its reasons and alternatives, until the owning Role settles it. These documents do not carry commit ids, test counts or merge/delivery status: consult Git and Card history for those records. Useful verification belongs in dated `output` evidence. A Card's reception state is not evidence that its requested work is complete.

### Lifecycle

Reuse OKF v0.2 §5.4 `status: draft|stable|deprecated`; omitted means stable. Status is local to the document. Editing, Git versions, material changes, checked-material records and parent status do not change it automatically. Unknown values remain intact with a diagnostic and no assumed currentness; an ordinary CAS edit may preserve them or explicitly replace them with a supported value.

Deprecated Nodes remain explicitly readable and editable without reactivation. Default resource lookup excludes them; hierarchy navigation can expose a deprecated ancestor to reach a current child. Unknown fields, including `mode`, are ordinary metadata and do not control lifecycle.

`node archive <nodeId>` preflights the current subtree and writes deprecated only to documents not already deprecated. It captures selected preimages and returns the Git commit containing the status changes; a no-op subtree creates no commit. `node restore <nodeId> --archive-commit <commit>` accepts a reachable single-parent commit containing only the relevant status-to-deprecated edits. Current identities, paths and bytes must still match, and no later retained change to those paths may exist, including edit-and-revert. Restoration changes only those status declarations, including an originally omitted value; it leaves previously deprecated and newly added children alone. It never resets Git or revives deleted documents. Never-captured external edit-and-revert intent cannot be inferred.

### Materials and links

Reuse `resource` for the primary described material and ordered `sources` for independently related material. Each source has `resource` and may preserve standard or custom descriptive metadata. Source order, repetitions and spelling remain significant. These references locate materials; they do not prove ownership, access, synchronization or a complete impact set.

Local paths use `/` separators. `./` and `../` resolve relative to the declaring Markdown; leading `/` resolves from `.tent` and cannot escape it. A `file:` URI names an absolute filesystem path. Relative paths can reach workspace material outside `.tent`. Queries/fragments and percent encoding retain their reference meaning. Windows drive paths and UNC spelling must use a URI rather than an ambiguous local path. Node creation and writes validate new or changed addresses without requiring external file existence; unchanged legacy addresses remain editable. Source reordering, removal and metadata edits retain existing address occurrences, while additional occurrences require validation. Ordinary files inside `.tent/` cannot be materials: new declarations are rejected with a direction to use Workspace files or Node, Role and Card documents, while existing declarations remain editable and `workspace check` reports them invalid. Recognized native Node, Role and Card references retain their protocols with consistent relative-path and `file:` URI behavior. Ordinary body links into `.tent/` remain file-existence references, not material baselines.

In stored documents, a bare `sources.resource` can be ordinary description. Tent preserves it as unresolved instead of guessing from an extension or the existence of a similarly named file. Use an explicit `./`, `../`, `/` or absolute URI when mechanical resolution is wanted. A spaced label such as `note: reference` is description; an unspaced URI such as `urn:example:1` is an address. `resource` itself is a material address. Remote URIs are addresses and are not fetched by Tent.

At the CLI boundary, new material declarations in `--resource`, `--sources-json`, `card create --source`, structured write frontmatter and batch create/frontmatter use Workspace-root file or directory paths, including leading `/`; directory addresses end in `/`. They are serialized to document-relative addresses. A Card response source `/cards/<card-id>.md` keeps its `.tent` root in CLI input as well as stored documents; this exception applies only to `sources`, not ordinary Workspace materials or `resource`. Bare sources become paths when they match an existing Workspace file, an explicitly slash-marked directory or a valid final-segment prefix selector; use `./` to explicitly declare a missing path, retaining the final `/` for a directory. `card create` warns on stderr, without changing what it stores, when a source starting with `./`, `/` or `.tent/` names no existing file, directory, Node or Role. Node IDs, absolute URIs and batch `@ref` keep their reference semantics. Unchanged existing material occurrences retain their stored addresses, and batch raw documents keep document addressing. Resource search uses the same Workspace-root CLI convention. `workspace check` reports `unanchored-material-file` for bare stored sources matching an existing local file or slash-marked directory, with a document-relative suggestion; it never rewrites them.

Local Markdown materials (`.md` or `.markdown`, including `file:` URIs) can select a section with a nonempty fragment, such as `../Design/Design.md#State`. The fragment is the heading text, decoded once from percent encoding, not a generated slug. The material version covers that section's text, including its heading and nested sections, ending at the next heading of the same or higher level, with text line endings normalized. For a Node material, its semantic resource/source addresses remain part of the fingerprint; other frontmatter and sections do not affect it. Missing or duplicate headings make the material unavailable; confirmation cannot clear an unavailable material's recorded basis. Batch saves resolve relative material addresses and batch references against the final document bytes. Addresses without a section and fragments on non-Markdown files retain whole-file versioning. This adds no metadata fields, and Card sources still pin complete Node or Role versions.

Standard Markdown links, standard fields and bare known `node-[a-z0-9]{6}` tokens in body text support discovery of related Nodes. Bare tokens outside Markdown link and definition spans form `mention` occurrences, including code and HTML text; unknown handles, longer tokens and self mentions do not. Mentions are never rewritten or canonicalized for semantic fingerprints. One Markdown AST parser drives relationship discovery and link rewriting, including reference-style links. Lookup matches exact identity, path or full name; ambiguous names remain unresolved. Wiki text such as `[[Name]]` is ordinary text. Core saves turn known Node IDs in link destinations, `resource` and `sources.resource` into relative document paths. Occurrences keep their original ranges and declaration paths. Unresolved references are visible. Tent does not add an in-document annotation protocol. Moves/renames rewrite resolvable affected live links and material addresses while preserving unknown fields, source order and occurrences; they do not rewrite historical Card input. Code, quoted HTML and unrelated text are not interpreted as links to rewrite.

Input materials use `resource` and `sources`. An output retains comparison bases for every goal ancestor without extra frontmatter; later changes are informational and never make the output behind. Its nearest goal remains the display owner. Other custom fields survive without transformation or material semantics. The Agent uses its existing tools to read actual materials; Tent provides no application or media adapters.

Markdown paths leaving `.tent` remain external to the Node index, even when an internal Node has the same trailing path. Internal Node renames must not redirect these references; moving the declaring Node adjusts relative addresses to preserve their original material targets.

## 3. Reading, editing and local Git

### Progressive disclosure

Header discovery resolves identity, hierarchy, status and duplicates without reading unrelated bodies. NodeFs reads frontmatter in 4096-byte blocks and stops at the closing fence; an unterminated header may require EOF to diagnose it. Before sharing or persisting a newly read prefix, its initial path state, opened handle state, post-read handle state and final path state must agree. Derived caches, including the Stop index, retain the state returned with that same header observation; an earlier independent stat cannot identify those bytes. This remains an O(N) live metadata scan, without a watcher or an atomic snapshot of concurrent editor changes.

Read scopes may cache parsed YAML values and original key order under `.tent/.git/tent-material-cache/document-headers.bin`, keyed by the content ETag of validated frontmatter prefix bytes. Header bytes, material fingerprints and revision digests may use the disposable `file-state.json` cache in the same directory. Every request validates the selected files' size, nanosecond mtime, ctime and available device/file identity. A matching entry reuses its observation without rereading source content only when its mtime is earlier than the cache observation time minus the conservative filesystem timestamp window. Racy entries always reread content. The implementation uses a one-second window; nanosecond fields do not imply that the filesystem has nanosecond precision. Content changes that preserve all of those state fields may be missed. `node check <id>` bypasses these state hits and reads the selected Node and required materials by content, including its goal/output comparison scope.

Empty or narrow reads retain other parsed headers, up to 10,000 entries, preferring headers observed by the latest cache update. They do not empty the parser cache between map navigation and detail requests.

Read scopes may also retain Markdown syntax in `.tent/.git/tent-material-cache/markdown-syntax.bin`, keyed by SHA-256 of the exact body passed to the parser. Entries contain link occurrences, mention exclusion spans, destination spans and root heading spans, without resolved Node identities or material versions. Each call applies its current catalog, known IDs, destination mapping, section selection and edit range. A changed body is parsed again; unchanged bodies reuse their syntax across processes. Narrow reads retain other bodies, up to 10,000 entries, preferring bodies observed by the latest cache update.

Semantic content may be retained in `semantic-content.bin` in the same directory, keyed by the normalized body, ordered canonical material declarations and resolved Markdown destinations. Each invocation resolves these inputs using the current document path, Workspace root and Node identity/path mapping, including edits to an existing catalog object; a matching input reuses canonical content without rewriting Markdown destinations. Unrelated Node mappings do not invalidate an entry. Narrow reads retain up to 10,000 entries. This does not cache Node validity or material observations.

Structure material derivations may retain their dependency sets in `structure-derived.bin` in the same directory. Each observation still validates current membership, path types and the source/configuration bytes selected by its coverage. Within one input scope, coverage membership, completed path-type observations and content digests may be shared across materials; the next scope rebuilds them. A hit also requires matching versions of every supporting file requested by the previous import resolution; these files must still occur in the validated listing. Changed input versions, membership or coverage run the ordinary Core resolvers again. Failed validation of a formerly required supporting file falls back to current resolution, since changed configuration may have removed that requirement. Entries hold no Node lifecycle, validity, goal state or complete query result.

One brief, Stop read or authenticated UI GET/HEAD owns one input scope. Already acquired bytes are reused by revision, header parsing, relationships and snapshots; a partial header read supplies its acquired prefix to a later full read. Parallel HTTP requests never share input scopes, in-flight source queries or complete results. Conflict retries and explicit single-Node checks start fresh content observations, and mutation checks do not reuse the surrounding read snapshot. Parsed-value callers receive separate mutable values; YAML aliases, negative zero and preserving edits retain their ordinary behavior. These caches do not hold Node validity or a complete brief/snapshot result. Missing, corrupt or incompatible caches and failed cache writes fall back to ordinary reading/parsing. Cache writes change no project file, Node/Card/Role document, Git commit or reference; native-edit collection retains its normal save and conflict rules.

Within that request, source listing, link rejection and state-cache lookup share one initial `lstat` per file. Parent directories are resolved once per request and must be ordinary directories whose real paths remain inside the allowed root without symlink or junction traversal. A regular file under a validated parent needs no per-file `realpath`; a state-cache hit returns the prior observation without a second path signature check. When source content is actually read, opened-handle and final path identity checks remain independent of those initial observations and reject concurrent replacement. These checks provide request-local observations, not an atomic snapshot; the next request validates paths and file states again.

Core queries return complete metadata and requested text, without CLI byte budgets, pagination or continuation cursors. CLI `node list`, summary reads and parent/children navigation disclose bounded identity, title, type, tags and location metadata. Tent does not project or interpret Node `description`; existing values remain unknown YAML and survive ordinary edits, without a replacement summary derived from body text. Without filters, `node list` returns direct children. `--type <type>` and repeated `--tag <tag>` instead select matching Nodes from the whole subtree under `--parent`, or the Workspace, in tree order; every given tag must match. An invalid `--type` is a usage error. Oversized display metadata is marked and retains a raw `metadataRead` address. Metadata-only responses do not provide a full-document write basis or capture Git. A full text read can be required for link relations, but discovery never captures versions. Text search belongs to the Agent's native file tools.

`listWorkspaceRelations` returns Markdown-link, mention and standard-field occurrences from all valid Node, Role and Card documents in one query. Node `relations` exposes these occurrences in both directions, including incoming Role links and pinned Card sources, with source ETags qualifying range reads across all three kinds. It uses the same Markdown parser and material resolution rules, preserving source indices and body ranges. Retained Card sources resolve to their historical identity even after live moves or path reuse; `changedSince` reports retained path changes, including edit-and-revert. Invalid version declarations remain explicit diagnostics. Discovery does not receive Cards or capture history.

`readWorkspaceRevision` hashes identity-document paths, sizes and SHA-256 content digests, order, settings and the independent Git HEAD. Digests use file-state validation; a same-size edit with a restored mtime is observed when ctime or file identity changes. It performs no Markdown parsing, capture, repair or background watching; it is a change indicator, not an atomic filesystem snapshot.

`node get` body/raw reads load the selected full document after a matching header observation. `node get <nodeId> --full --json` supplies the complete body and exact ETag for CAS editing; add `--view raw` for the complete original document including frontmatter. The internal `readNodeForEdit` function returns the raw editing snapshot and optionally informational output changes. Complete live `node get` body/raw reads, including `--full`, and complete `read-many` output items expose `changedSince`; historical reads and summaries do not compare later live materials. An initially invalid document, a lookup-to-read conflict and an I/O failure remain distinct errors. `node list --full` explicitly reads the full tree without capturing history; it is not the default discovery path.

`node get` is strictly read-only: it does not capture history, refresh baselines, or compute associations by default. Body/raw reads, including `--full`, expose declared `resource` and `sources` as an ordered `materials` array of decoded Workspace-relative paths (nonlocal references retain their address). Text mode prints one `Material: <path>` line immediately below ETag, including for an empty body, without reading material contents. Oversized metadata follows the existing bounded-read continuation contract. Complete body/raw reads return top-level `nodeId`, `text` and `etag`; partial reads additionally carry the range and continuation. Pure live body/raw reads add `uncaptured: true` when their document bytes differ from Tent HEAD or have never been captured. Text mode explains that the next write, brief or hook collects them; this notice is outside the text and ETag. `role show` and `card show` also use top-level `text` and `etag`. There is no nested `node` alias in these CLI reads. The explicit `--context` option adds a bounded navigation summary (up to 1 KiB), outside the document and ETag, on first/full reads only. Historical and continuation reads do not append it. Context rows show identity, title and type without description or body excerpts; Cards expose their delivery state and return result. Discovery outputs, including brief, Node relations and Card sources, expose unencoded Workspace-relative file paths and applicable Markdown heading names for the Agent's own file reader. Stored material addresses and Git version paths keep their canonical semantics.

Pure-read relationship queries and explicit context derive document relationships, hierarchy and material declarations from the latest captured documents in Tent HEAD. Their drift still compares those declarations and retained bases against current external material bytes, using the same inspection rules as brief/check. Material observations do not create history or move bases. Reading a live document does not change the retained document view; `uncaptured` makes the two versions explicit. No material-observation records or observation-only commits are introduced.

Discovery and export remain live: `node list`, summary, resource lookup, `list --full` and `read-many` return current disk content, paths, hierarchy and material fields. New or moved Nodes remain discoverable before capture and carry `uncaptured: true`; changed selected documents carry the same marker, except that header-only resource lookup marks only a new or moved path absent from retained history, never a body-only edit. Their text output includes the same collection notice. This does not change HEAD-derived explicit relations/context or attached drift.

`node search --resource <address>` resolves an explicit material address and returns every valid, nondeprecated, nonarchived Node that exactly declares it or whose directory/prefix material covers the Workspace file. It reuses the shared Core coverage rules. Each Node appears once with its most specific matching material as evidence: exact matches first, then longer coverage prefixes, with stable Node path/id order for ties. The result names the matching field, source index when applicable, address and exact/coverage kind. It reads headers only, never bodies or captured versions, and returns no full-document `etag` or `match.read.expectedEtag`. Its pagination revision follows the returned header information; read a Node separately to obtain content or an editing basis. Ordinary Workspace file lookup excludes `.tent/`, including when a broad directory or prefix could cover it.

Agent-facing Node, Role and Card reads use `text` for body and raw content, including `node get --full`, `node list --full` and `read-many` items. The selected view changes the content, never the field name; read responses have no `body` alias. Structured write inputs still use `body` to distinguish a replacement body from a raw document.

`readNodeTimes(fs, nodeIds)` and authenticated `GET /api/nodes/times?nodeId=...` return selected `{nodeId, contentChangedAt, recordedAt}` rows in first-request order, with duplicate ids removed. `contentChangedAt` is the UTC ISO commit time of the latest retained change to the Node's semantic body or material addresses. Creation counts; confirmation, provenance, tags, lifecycle and other metadata do not. It shares the synchronization fingerprint, including canonical material targets and Node identities at each historical version, so moves and their automatic link rewrites do not count as content changes. A retained edit-and-revert counts as the later change. Material file bytes are not observed. Missing/unreadable history or live semantic content not matching its latest retained version gives null, never a guessed filesystem modification time; an unavailable selected historical version does not discard another Node's readable time. Invalid and missing live Node ids retain the normal read errors.

For an output, `recordedAt` is the latest valid declared `generated.at` or `verified.at`, normalized to UTC; it is null for other Node types or absent timestamps. This is a recording/confirmation time for reaction comparisons, independent of the existing earliest-time `outputAt` completion rule. These are recorded clock times, not a proof of causal order. The query reads current selected documents on every request, shares one batch of selected historical versions, and neither captures native edits nor advances baselines. It adds no persistent document fields and does not run in the default snapshot.

CLI Node reads without the complete body or raw document mark their ETag as `read:<etag>`, including metadata, partial pages, non-first fragments and bounded single-save readbacks. This basis can continue reads and support metadata-only edits, but Core rejects it for body/raw replacement with `INCOMPLETE_READ`; callers must obtain a complete live read first. A complete single-response body/raw read retains the canonical ETag. Batch save receipts return the canonical saved ETags for the writer's known complete inputs; they are not discovery reads. The marker prevents accidental replacement from incomplete reads; it is not authorization, a signed receipt or proof against a caller deliberately removing it. Core's complete document reads and UI editing snapshots retain canonical ETags.

Successful CLI Node, Role and Card mutations identify the resolved `workspaceRoot` in JSON and show a Workspace line in human output.

CLI body/raw, search and relation pages share a 16 KiB compact JSON budget. Large display values are marked as truncated or omitted and retain exact source ranges and qualified read addresses; a truncated display is not an executable material reference. Oversized occurrences must not prevent later results from being enumerated. Text ranges use UTF-16 offsets and preserve surrogate pairs and CRLF boundaries. Body excerpts address original text.

Cursors are deterministic continuation addresses usable across short-lived CLI processes, not permissions or signed receipts. They bind source, query, observed revision and position. A changed relevant revision requires a fresh query. Header/hierarchy cursors survive body-only changes, while text cursors require the observed body revision. No cursor secret or Session cache is needed. Role/Card pages carry explicit ETag/range continuations. Summary requests do not accept text ranges, cursors or an expected full-document ETag.

CLI `node read-many` accepts an ordered unique `nodeIds` list and `view: body|raw`, selects documents through Core `prepareNodeBatch`, and applies `start` and a response budget including outer fields. It never captures. An item's partial text continues through live `node get`; outer `page.nextIndex` starts a fresh live batch, not a whole-graph snapshot. Changed files require a fresh read; range, ETag and response-budget checks remain in force.

CLI text reads show Node bodies in both ordinary and full reads, relation kinds and endpoint identities, Card receipts with id/target/state, and drift identities/states/reasons. Failures end with one copyable `Next: tent …` inspection or help command. `node create --id` accepts an unused Node id; existing identities or sibling names fail without overwriting, and a sibling collision identifies its existing Node. Complete first body/raw pages carry ordinary write-capable ETags; only partial Node reads carry `read:` ETags. Mutation receipts remain separate from the minimal read shape.

### Save semantics

`node write --input-json` accepts an observed `baseEtag`, body and/or frontmatter patch, and optional `readBack`. Omitted fields and unknown metadata survive. Raw edits and structured edits use the same Core rules. Identity, type and lifecycle retain their explicit validation. A stale basis is rejected; the CLI must not refresh it just before overwriting.

The default save response contains metadata and the captured Git version. Core `readBack` returns requested text from the actual saved bytes without rereading the file; CLI bounds that response. A partial page does not mean the whole body was read. No-op saves validate CAS, avoid rewriting Markdown and still capture newly observed bytes when needed.

Node and Role edits recheck their originally observed bytes after asynchronous reference resolution, before saving or capturing the result. An intervening external edit is a conflict; it does not become a refreshed write basis. Storage errors remain storage errors.

Creation can save body, resource, sources and tags together. An initial file/order failure rolls back the newly created Node. Deletion removes a whole Node subtree without requiring archive first; it does not delete referenced materials or rewrite inbound references. Move children that should survive before deleting their parent.

`writeNodesBatch` / `node write-many --input-json` accepts `{items:[...]}` with ordered `create` and `update` operations. A create supplies a unique local `ref`, `name`, `type`, optional `parent`, body, tags and material fields. `@ref` identifies a Node created by this batch in parent references, Markdown link destinations and material addresses; forward references and mutual links are supported, while cyclic parents and unknown references are rejected. An update supplies an existing `nodeId`, a complete live-read `baseEtag`, and raw or structured changes. Duplicate updates, stale ETags and incomplete `read:` bases are rejected before saving. Input validation identifies the failing item index and field; missing required fields such as `ref` explicitly say they are required.

The batch validates and prepares every final document before writing, holds one Workspace lock, and captures its changed documents in one Tent commit. A failed batch rolls back its own document, directory and ordering changes; rollback failures report affected paths and conflicts while preserving external edits. Existing pending structural recovery runs first under the same lock and retains its separate recovery history. Results preserve input order and contain each saved `nodeId`, `path` and exact `etag`, so known complete inputs need no confirmation read. The batch does not return a copy of every body. No-op batches add no commit when the selected bytes are already retained. The lock serializes Tent writers; it does not make filesystem writes and Git atomic against external editors or process termination.

`checkGraph` inspects Node, Role and Card documents without editing, history capture or structural recovery. The CLI `workspace check` first runs the native-edit collection boundary described below. It returns compact `issues` for `unresolved-link`, `invalid-material-address`, `missing-material-file`, `missing-material-section` and `node-git-mismatch`, plus `errors` for documents that cannot be fully inspected. `node-git-mismatch` names a Node identity document that exists on disk but not in the Tent Git HEAD tree, or exists in that tree but not on disk; it is skipped without Tent Git. A section issue identifies a missing or duplicated Markdown material heading; unrelated I/O failures remain inspection errors. Core paths are relative to `.tent`; CLI inspection paths are Workspace-relative. Local material checks use Workspace-relative and absolute `file:` resolution. For a leading-slash body link missing under `.tent`, if the same file exists from the Workspace root, the unresolved-link reason gives the correct document-relative link, retaining URI encoding and any query or fragment. This diagnostic neither changes the leading-slash anchor nor rewrites the document. External URIs and plain source descriptions are not fetched. Retained Card sources are checked against their complete pinned versions. CLI exits zero for a clean report and one when issues or inspection errors exist, retaining the JSON report on stdout. This checks addresses, file presence and selected section availability, not semantic freshness; `node check` remains the separate per-Node material-version comparison.

Explicit `node create`, `write`, `append` and `write-many` receipts include advisory `warnings` when a goal or prompt declares a local file material that is not tracked by its owning Git index. The hint recommends `output` for a result observed at one time, because the untracked file's old bytes are not retained for a content comparison. Both `resource` and `sources` count; output Nodes, directory/prefix coverage, remote or unresolved sources, and Tent identity documents do not trigger it. Missing files or Git inspection failures are not guessed to be untracked. This advice is not stored in the Node and does not change its type, synchronization basis, write success or confirmation rules. The Core write result and the HTTP Node-save response carry the same advice; CLI text prints it once and JSON keeps the array. It does not add work to brief or drift, nor retain material bytes.

Those receipts also advise when this write adds a whole local Markdown material to a goal or prompt and the document has at least two sibling section headings below its title. Changing a section reference to a whole-document reference counts as adding the whole material; retaining a whole reference does not repeat the advice. Markdown syntax determines headings, excluding code blocks and frontmatter. Both ordinary files and Tent identity documents qualify. Section references, directory/prefix structure, remote or unresolved sources, outputs and unreadable materials do not trigger this hint. The advice recommends specific sections when those are sufficient; it never rewrites declarations, changes a type, or confirms a synchronization baseline.

### Native file reads and edits

Agents can read a Node's Markdown through their native file reader and edit its body with tools that check the old text. Node creation, material declarations, explicit confirmation and Card protocol operations remain available through the CLI. Before Node, Role and Card mutations, Workspace export/brief/check/drift and SessionStart hooks observe the Workspace, Core compares current Node bytes with independent Tent Git HEAD and collects valid edits under the mutation lock. Stop uses only the current transcript and live Node metadata; it does not collect edits or acquire the mutation lock. Pure CLI reads (`node get/read-many/list/search/relations/history`, tag discovery, `role list/show`, `card list/show/get/watch` and `workspace scan/check-modules`) do not collect native edits or capture their selected documents. Help and pure Core queries do not collect edits.

Collection retains the exact native file bytes without rewriting the document or inventing producer metadata. Valid frontmatter changes use the same identity, material, provenance and lifecycle validation as CLI raw edits. Existing material and goal bases remain unchanged; newly declared materials follow the same save rules as CLI additions. Invalid YAML or metadata is left untouched and uncaptured, quarantined for the current command, and listed in full by brief and workspace check. Untracked new files remain discoverable by check; create Nodes through the CLI. A later native repair is checked again against retained bytes. Storage failures and unstable observations are never classified as invalid frontmatter.

An unchanged collection probe needs no mutation lock. If its initial document scan detects changing bytes, collection acquires the lock and observes once again before validating or capturing anything. A concurrent-edit failure during that locked observation still fails collection; storage failures do not trigger another observation. This never retries a save or a caller's action.

Each boundary retains the final bytes it observes. Two edits separated by collection boundaries retain two versions; intermediate edits between boundaries are not automatically recoverable. Native tools remain responsible for avoiding lost updates; Tent does not add a second editing harness.

### Appending

`node append <id> --body <text|-> [--heading <title>]` appends to the current body under the Workspace mutation lock without a preceding read or ETag. The optional plain-text heading selects an existing section and appends at its end, including after nested subsections; when absent from the body, it creates a level-two heading. Duplicate matching headings are an explicit error, and headings in code blocks do not count. The boundary has one blank line and a normalized trailing newline. Successful concurrent appends do not overwrite one another. CLI writes wait briefly to acquire a busy lock before reporting a timeout; they never retry an action already started or bypass its ETag check. It returns the saved full-document ETag and Git version. Use this operation for additions instead of reading and replacing the entire body.

Appending uses normal address validation, Node synchronization and Git capture. It does not confirm existing material or output bases and cannot clear their drift. Agents edit type, tags and body text through their file tools or `node write`; full-document CAS remains required when using the latter for replacement.

### Captures and diffs

Explicit saves capture selected identity documents' exact UTF-8 bytes into reachable commits in `.tent/.git`. Core Node, Role and Card reads capture only when explicitly requested with `capture: true`; ordinary UI browsing can stay read-only. Pure CLI reads, including `node read-many`, never request capture. A partial batch item continues against live bytes; an unchanged file continues, while a changed file rejects its cursor and requires a fresh read. Range, ETag and output budgets still apply. No-op selected captures create no new commit. Historical queries themselves do not capture. An explicit Core capture while reading one page retains the source document; it does not claim every page was read. Never-observed editor intermediates are not recoverable by contract.

Capture constructs each selected tree in an isolated Git index and then aligns the independent repository's ordinary index with committed HEAD. Unselected worktree bytes are never changed; external document edits remain visible as dirty files. Operational registry files, temporary data are excluded from this identity-document history through local info/exclude rules, preserving existing rules. No Git hooks run. A directory without independent Tent Git is not initialized by reading; such reads return no captured version. Card publication and reception require Tent Git.

`version: {commit,path}` names a complete history-document path within `.tent`. `node get --version-json` reads that exact Node after live edits, rename or deletion. Core `readDocumentVersion` also reads Role and Card documents and `canvas.json`. Core `readDocumentDiff` compares two captured documents for the UI and reports path changes separately. Historical continuation binds the retained source, and cannot silently fall back to live bytes. Reachability and document paths are validated; Node-specific reads additionally validate Node identity.

The Web map stores its layout, regions and drawings in the fixed `.tent/canvas.json` file. Core accepts only version 2 with `positions` mapping Node IDs directly to finite `[x,y]` coordinates: the card's top-left corner in map coordinates, recorded only for manually moved cards. `regions` contains `{id,name,box:[x,y,w,h]}` with string IDs unique within the region list, possibly empty names, finite coordinates and positive finite width and height. Regions contain no member list; the UI derives membership from positions. `drawings` contains `id` and `kind: pen|text|shape`, without a `node` attachment field. Other drawing fields belong to the UI and are preserved without interpretation. The old `forms`, grouped position layers, drawing attachments and version 1 are rejected, without compatibility reads or automatic conversion. References to absent Nodes are retained; Core never prunes the canvas. The file is limited to 5 MiB of UTF-8, participates in workspace revision, history/diff and complete export, and carries no Node/Role/Card identity.

On the Web map, holding one card over another for about half a second and letting go forms a region; dragging a card into a region adds it, and a region grows to hold its cards but never shrinks. A region counts only cards placed by hand: a tree card that happens to sit under it after relayout is not a member. A card taken out of the tree leaves no stand-in; the tree closes its space. Inside a region the map draws only relations Tent already records (parent/child, references, shared material files, code imports, and outputs returned through Cards), one style each. Dragging a region's title moves its members, renaming edits only the region, and dissolving it returns its cards to the tree. The pen toolbar draws shapes, lines, freehand strokes and text; it does not create regions. Shape and card endpoints are visual attachments owned by the UI and do not create Tent relations. Undo and redo cover drawings, manually placed cards and regions within the current page. Edits are written to the canvas about two seconds after the last change.

Identity extraction is gated by the document path in history ranges and capture metadata. A malformed canvas retained by an external Git commit remains readable as historical bytes without contributing frontmatter identity, even when its blob is identical to a Node document. It cannot make the workspace history or snapshot report duplicate Node identities. Position keys keep the existing Node ID case rules.

Core `readCanvasDocument` returns `{etag,canvas}` with both values null when missing, without creating or capturing a file. Malformed, unsupported or oversized existing files fail with `INVALID_INPUT` and are never reset. `writeCanvasDocument` replaces the whole file under the workspace mutation lock, requires the observed `baseEtag` (null for creation), preserves selected external preimages and records `canvas.write`. An ETag mismatch returns `ETAG_CONFLICT` with `details.current: {etag,canvas}`. Cooperating writers use this lock; the existing external-editor and filesystem/Git transaction limits apply. `GET /api/canvas` and queued `PUT /api/canvas` expose these Core operations behind the service's Bearer/Host/Origin/JSON checks, with 422 validation failures, 409 conflicts and 413 oversized HTTP bodies. PUT returns `{etag,version?}`. There is no canvas CLI command or snapshot summary field.

Historical identity extraction, object trailers and queries use the same Node/Role/Card ID validators as live documents and preserve the original ID spelling, including accepted uppercase characters.

Captures carry `Tent-Operation`, repeated `Tent-Object` IDs and `Tent-Entry: cli|ui|core` commit trailers. Observed editor bytes use `document.external-capture`; Tent writes name the operation, such as `node.write` or `card.take`. Entry is selected by the calling adapter. These labels explain the capture, not who originally authored the bytes. `GitDocumentHistory.nodeVersions` follows identity across locations and deletion; `listHistoryChanges` returns chronological first-parent changes from an exclusive `from` to an inclusive `to`, with ISO commit `time`. Older commits without trailers remain inspectable by document identity. CLI `node history` paginates Node versions; the UI consumes the shared change query.

Structural operations capture selected preimages before destructive changes and capture final paths together. They recheck observed bytes/path after preimage capture. Locks serialize cooperating Tent writers; the final check and filesystem operation are not atomic against external editors. Filesystem writes and Git ref updates are also not one transaction: a failure can follow a saved file. Inspect actual bytes/history before retrying. Multi-document failure reports known saved paths and preimage evidence instead of a false complete success.

History consumers share one retained-history read within a command. Derived history data may be cached under `.tent/.git`, keyed by the exact HEAD; a changed HEAD invalidates those results, and a cache hit does not replay history. A complete retained-history cache can extend along a single-parent commit chain, reading only added commits and missing blobs. Reset, divergent or merge history and invalid caches rebuild from Git. The cache is disposable and never enters Node or Card documents. Current documents and workspace materials are still inspected on each query, since their bytes can change without moving HEAD. No persistent service is required.

Workspace relation queries validate fixed Card sources in one reachable history walk and one blob batch, preserving per-source failures and retained-edit detection (including edits later reverted). Revision polling reads the independent Git HEAD and its loose or packed reference directly; an unchanged HEAD needs no Git process. A changed HEAD updates completed-Card membership from its tree difference. Polling does not retain a process-local revision cache.

### Node synchronization and outputs

`Tent-Node-Record` is a commit-message trailer in the independent repository at `.tent/.git`. Each line contains a JSON pair `[nodeId, record]`, validated as `NodeBasisRecord` in `src/core/base/node-basis-record.ts`; a commit can carry records for several Nodes. Version 1 records carry `v: 1`, ordered material identities and observed content versions, optional fingerprint versions, a coverage goal's own intent basis, and an output's ancestor-goal bases with their observed materials. Same-version extension fields are accepted. The record is written with the affected document when its basis changes, outside Markdown frontmatter.

All fields below belong to record version 1. Core's `prepareNodeSyncSave` constructs records for creation, saves and confirmation; `GitDocumentHistory` validates and writes their trailers. `GitDocumentHistory.nodeRecords` validates retained records for current synchronization inspection. CLI and UI do not interpret trailers independently.

| Field                               | Version 1 value and meaning                                                                                                                                                                                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `v`                                 | Required literal `1`; selects the record schema.                                                                                                                                                                                                                     |
| `materials`                         | Required ordered array of this Node's material bases, including an empty array.                                                                                                                                                                                      |
| `materials[].identity`              | Required canonical material identity. Local `file:` URIs use `file-sha256:<hex>`; declarations that cannot be resolved use `unresolved-sha256:<hex>`. Their raw addresses are not retained in the record.                                                            |
| `materials[].version`               | Optional 64-character lowercase SHA-256 content digest; absent means no sampled version.                                                                                                                                                                             |
| `materials[].fingerprintVersion`    | Literal `2`; required when `version` is present, optional otherwise.                                                                                                                                                                                                 |
| `materials[].structureDependencies` | Optional structure basis: sorted unique external targets, directories ending in `/` (Workspace root is `./`) and file targets without a trailing slash. Its digest must match `version`, including in ancestor-goal bases. An observed empty dependency set is `[]`. |
| `goalBasis`                         | Optional own intent basis for a goal with own or descendant-goal local Workspace directory or prefix coverage: `version` is its semantic SHA-256 digest and `fingerprintVersion` is literal `2`.                                                                     |
| `goals`                             | Optional ordered array of the output's ancestor-goal bases.                                                                                                                                                                                                          |
| `goals[].nodeId`                    | Required canonical `node-*` identity of the ancestor.                                                                                                                                                                                                                |
| `goals[].version`                   | Required 64-character lowercase SHA-256 semantic digest of that ancestor.                                                                                                                                                                                            |
| `goals[].fingerprintVersion`        | Required literal `2`.                                                                                                                                                                                                                                                |
| `goals[].materials`                 | Required ordered array using the same material fields above, observed for this output.                                                                                                                                                                               |

Same-version extension fields at any object level survive reading, but do not supply a baseline for known fields. Capture and export reject machine-absolute paths even in extensions. The record version and semantic fingerprint version are separate: the former selects the shape, the latter identifies the digest algorithm. Retired `repository` and `directoryFiles` fields are tolerated as opaque extensions when reading old records, ignored by synchronization, and omitted from newly constructed bases. Existing history is not migrated.

Ahead is a current finding with reasons; there is no inferred start time. Captures do not write acknowledgment trailers, and readers ignore old `Tent-Output-Acknowledged` fields without changing history.

`GitDocumentHistory.nodeRecords()` reads the latest record for each Node on the retained first-parent lineage; records found only on a merge's other parents do not participate. Missing, unversioned, unsupported or invalid records provide no baseline for that Node, while other Node records remain usable. A newly written versioned record containing a machine-absolute path cannot be captured or exported. Older history is left intact and is not migrated. An output without a usable record has unknown comparisons; metadata or structural edits cannot invent its baseline, and unknown comparisons never make a frozen output behind. One explicit confirmation establishes its current basis when its materials are readable. Ordinary saves cannot invent missing existing bases; new material declarations can acquire their own initial observations while previous unknown bases stay unknown. Core's `retainedNodeRecords` uses these bases for synchronization queries. CLI and UI consume these Core results; disposable history caches are derived from the trailers, not the authority for their contents.

`node check <id>` computes independent `ahead` and `behind` findings from the current Node and local materials without changing Nodes or capturing Git. A goal can have both findings; each counts separately. Neutral synchronization details remain available on inspection without becoming a task or map mark. These facts are independent of OKF v0.2 §5.4 lifecycle `status`. A matching version proves only that recorded bytes still match, not semantic correctness. Unavailable or remote versions remain explicitly unknown; inspection makes no network requests.

Creating or saving a Node automatically observes local `resource` and `sources` with SHA-256 of the selected Markdown section or, without one, the whole file. The basis is retained by Node ID in the same Git commit as the document, outside frontmatter. Retained first-parent history supplies the current record; resetting history also resets the basis. Derived file observations reuse a local file-signature cache across CLI invocations, separating complete files and individual sections. No manual hash input is needed. Every ordinary save retains existing material and goal versions, including an output whole-body rewrite and native file edits. Only creation or explicit confirmation establishes or refreshes existing dependencies. Metadata edits, no-op saves and equivalent line-ending changes cannot clear `behind`. New declarations are observed on save; unavailable known materials retain their old basis. Document reads never refresh it; native collection preserves old bases and observes only newly declared materials. Batch writes record final saved documents and bases together and roll both back on failure before HEAD publication.

A local material address ending in `/` declares directory coverage in either `resource` or `sources[].resource`. It follows the same CLI and stored-address rules as a file, preserving the trailing slash; queries and fragments are invalid. Without `track: structure`, a directory supplies coverage for resource lookup and module checks, but no content fingerprint, baseline or changed-file list. Adding, deleting, renaming or editing its members does not make a Node or dependent output behind. Declaration and link-output checks retain lightweight address and directory-existence validation without recursively reading members. A rule that must follow content names the specific file or Markdown section.

Structure observation leaves project files, Node/Role/Card documents and Git commits/references unchanged. It does not execute Git filters, fetch missing objects or initialize repositories. Nonignored current members use trustworthy Git ignore interpretation; tracked ignored members remain excluded. Outside project Git, the existing independent Tent Git can interpret Workspace `.gitignore` rules without its private or global excludes. Without a trusted interpreter, rules requiring interpretation make the observation unavailable. Workspace enumeration independently excludes `.tent/`, including root-directory and `.t*` coverage, regardless of ignore rules. One inspection may share listed path types between its live/tracked listings and material resolvers; later inspections observe them again, including missing paths and errors. These listing types never replace the live path, symbolic-link and file-identity checks used when reading source bytes. Concurrent ancestry checks in one request may share an in-flight path query; a finished query never authorizes a later read. Final file-identity checks always issue their own fresh query, including when another ancestry query is still pending.

File and section materials are read only at their declared live location. Missing or unreadable materials are unavailable and remain behind; Tent does not search other checkouts or substitute retained Git blobs. No repository locator is recorded for fallback.

A local address ending in one `*` in its final segment declares prefix coverage, for example `src/core/card-*`. It covers paths beginning with that prefix, including nested paths. Other wildcard positions, multiple stars, queries and fragments are invalid. Without `track: structure`, prefixes supply only coverage, with no member-content reads or baselines. The parent directory must exist for existence checks; an empty match is valid. Prefix and directory membership share `src/core/base/material-coverage.ts`; no child module is automatically subtracted, and `.tent/` never belongs to Workspace file coverage.

Only a `sources` entry can opt into structure observation with `track: structure`, and only for a directory or prefix material. Omitted `track` keeps directory/prefix coverage only; top-level `resource` does not enable structure tracking. A module is a Node with at least one such explicit structure source; tags never enable this behavior. Structure means the set of outgoing local dependencies from member production files, using the shared `extractRepositoryImports` static extractor. Test-file imports do not participate. For each structure source, internal targets are the union of the same Node's structure-source members, resolved with the shared member rules. Ordinary coverage sources and other Nodes do not expand this union. Each source retains its own outgoing dependency set and baseline; only target exclusion uses the union. External targets are grouped by directory, except a nonmember sibling in the importing member's directory is represented by its file path, so a prefix group can distinguish its neighboring files. Incoming dependencies, file membership and ordinary content changes are not part of the fingerprint. Creating, deleting or renaming files changes a structure fingerprint only when the outgoing target set changes.

Structure observations retain `structureDependencies` outside frontmatter. `node check` exposes up to 20 `changedDependencies` in target order, each with `target` and `state: added|deleted`; `changedDependenciesOverflow` reports any omitted count. Coverage and structure declarations of the same address can coexist; only the structure declaration stores a basis. The `track` mode contributes to goal and Node-material semantic fingerprints, so changing it is a material declaration change visible to dependent outputs. Old directory-content records are ignored without migration. Existing baselines still move only through the normal creation, new-declaration and explicit confirmation rules; editing prose does not silently acknowledge changed material.

Structure observation inherits the shared extractor's supported languages and resolution limits; it is not a syntax validator or a guarantee about runtime dependency behavior. Unsupported languages supply no import edges. Reported relevant resolution failures and unreadable required bytes leave the observation unavailable; no partial set is confirmed as a complete dependency basis. Reads retain the same zero-authoritative-write boundary as content observation.

A Go import targets a package directory. If all of that package's production files are members, the edge is internal; if none are members, the package directory is an external dependency. If only part of the package belongs to the Node's structure-source union, the observation is unavailable and identifies the partially overlapping package. A package-level edge cannot establish which individual nonmember files are dependencies, so it must not be discarded or expanded into guessed file edges.

A structure-tracked module's prose can become stale after code-content edits without mechanical drift. Turn-end review is best effort: shell or external-editor edits absent from the observed turn, cancelled turns and undelivered prompts may never be raised. A rule that must follow specific content must also name that file or SPEC section as content material. Fewer structure alerts do not establish greater accuracy or complete content freshness.

Goal and Node-material semantic fingerprints contain LF-normalized body text, ordered canonical `resource`/`sources[].resource` addresses and explicit structure modes. Type, tags, provenance, lifecycle, descriptive source metadata and Card response edges do not contribute. Ordinary text materials normalize line endings; binary bytes remain exact. Confirming an upstream Node without changing its meaning does not make consumers behind.

An output records a result at one time. Changes to its own materials or any ancestor goal never make it behind, regardless of tags, including `asset`. Only an explicit `stale_after` expiry makes an output behind. Its retained comparison bases still cover its own materials and every goal ancestor between it and the root, including deprecated or archived ancestors. A goal's body, ordered material addresses and materials are compared independently of type, tags, lifecycle and verification metadata. Confirming a goal refreshes its own material basis and, when it or a current descendant goal declares local Workspace directory or prefix coverage, its own intent basis; it does not refresh any output's comparison bases. A batch uses the final saved goal and material bytes regardless of item order.

Unavailable baselines remain unknown. Reads do not reconstruct, confirm, rewrite, migrate or bulk-confirm old records.

Complete live output reads return informational `changedSince` entries when recorded and current versions actually differ. Each entry is `{kind: "material", resource}` for an own material or `{kind: "goal", nodeId, name}` for the nearest goal (the first goal upward, skipping intervening prompts and outputs). More distant goals do not produce notices; their retained bases and comparison states remain unchanged. Each changed goal appears once even when both its body and materials changed. No changes means the field is omitted. These entries are separate from the Node text and never enter the brief's behind list. Inspection retains exact material addresses, goal IDs and distinct recorded/current versions; unavailable or unknown comparisons are not claimed as known changes. Explicit output confirmation refreshes its comparison bases and verification time, clearing the changes that can be observed. Reads and ordinary saves do not refresh those bases.

`readOutputComparisons` provides a pure selected-output batch using the same observation as synchronization. Each result has `nodeId`, nearest-first `goals: [{goalId, state}]` and `changedSince` (an empty array when no change is known). A goal is `current` only when its body and all comparable materials match the output's retained basis; any proven difference makes it `changed`, otherwise a missing basis, unreadable material or inconclusive inspection makes it `unknown`. Unknown never claims a change or a match. An ancestor body that cannot be read is locally unknown; other ancestors retain their completed comparisons, while known changedSince entries remain limited to own materials and the nearest goal, and other selected outputs still return. Output expiry and its own material changes do not alter goal comparisons. Duplicate output IDs are read once in first-request order; unknown IDs and non-output Nodes are rejected. The query captures no native edits, writes no baselines and does not inspect unrelated output bodies. `GET /api/outputs/compare?nodeId=<id>&nodeId=<id>` exposes this batch to the authenticated bundled UI on demand, independently of the snapshot cache; it adds no automatic snapshot work.

Every `goal` is a requirement regardless of tags. A goal declaring at least one local Workspace directory or prefix in `resource` or `sources`, or having a current descendant goal with such coverage, retains its own semantic intent basis on creation or explicit confirmation. Grouping goals use their own body and declarations for this basis; child intent is not folded into it. Adding a qualifying descendant does not silently establish a missing parent basis. Batch creation and confirmation use the final hierarchy and declarations. Ordinary saves and native capture preserve it. Matching that basis clears ahead independently of outputs; a missing or changed basis requires confirmation or a matching current output. Single files, Node/Role references and external URLs do not qualify, and `track: structure` is not required. Its material drift remains an independent behind finding. For goals without this coverage, a goal without any active `output` anywhere in its subtree is ahead. When there is no matching own intent basis, outputs clear ahead only when at least one current output has retained baselines matching that goal's current body and all its materials. Missing or unavailable comparisons cannot establish a match. One output must match the whole goal; partial matches from different outputs cannot be combined. An output under a nested goal can satisfy its ancestor goals independently. Confirming one output or creating a new matching output clears ahead without refreshing the older outputs' informational changes. This uses the existing current-output scope, adds no time fields and replays no history. A change to an output's own material alone does not make its goal ahead. Goals and prompts continue to track their own material changes as behind; expiry is an independent behind finding for every Node type. Matching own intent, material, verification or current outputs can anchor a Node; otherwise it is unanchored. Conversation-only Nodes do not need invented material references.

`node link-output <goal-id> --resource <address-or-node-id> [--name <name>] [--tags <a,b>] [--by <actor>] [--role <id>] [--card <id>]` creates a child `output` Node and returns its identity and any selected `cardId`. Its tags are exactly those given with `--tags`; none are added automatically. CLI local file or slash-marked directory paths, including `/` addresses, resolve from the Workspace root; Node IDs and absolute URIs are supported. Core link-output retains its bundle-root `/` convention. Local materials must exist and be readable before creation. A local path under `.worktrees/` remains accepted, with a `warnings` receipt reminding the caller to merge into the main checkout before linking an output; CLI text displays the same warning. The default name is the material's file or directory name, or `Output` for a root directory, with a number added on collision; `--name` overrides it. The saved resource is rewritten relative to the child. Remote addresses are retained without fetching. The goal itself is unchanged. Existing outputs can instead be moved into the appropriate hierarchy; goal dependencies use stable Node IDs. There is no separate output association list.

After reading and reviewing a complete live Node and relevant materials, `node confirm <id> --base-etag <etag>` refreshes its material and implicit goal bases without changing its body. All Node types use `node write --confirm`, or `confirm: true` in write JSON or a write-many update item, to save and confirm together. Rewriting a complete output body without confirmation preserves its comparison bases and does not clear informational changes. Explicit confirmation also records verification. Unavailable known material remains unavailable after confirmation; it contributes behind only for goals and prompts. These mutations require a complete live-read ETag, validate addresses, use the mutation lock and retain the resulting Node and basis together in Git. Partial reads cannot authorize them. Node frontmatter has no synchronization, planning, output-list or hash fields; native OKF v0.2 §5 authorship, verification and lifecycle fields remain independent.

Only explicit confirmation refreshes an existing output's dependency bases. Ordinary whole-body edits, metadata-only input and neutral address normalization do not establish review. HEAD publication completes a capture; failure to mirror the ordinary Git index afterward cannot roll back published documents or bases. Recapturing retained documents retries that disposable mirror; pre-publication failures still roll back.

### Authorship, verification and expiry

Node writes use OKF v0.2 §5.2, §5.4 and §5.5 native `generated: {by, at}`, `verified: [{by, at}]`, `stale_after` and lifecycle `status`. Creating or meaningfully changing the body or semantic metadata records the producer and time in `generated`; reads, no-op saves, verification and lifecycle changes do not. Verification remains independent of generation: editing content retains earlier verification records. Confirmation adds or refreshes one record per actor, retaining that actor's latest timestamp. Readers also accept OKF's single verification mapping.

Content-writing and confirmation commands accept `--by`; JSON writes and batch items accept `by`. Actors use `human:<id>`, `process:<id>` or `<producer>/<version>`. An unavailable host identity is recorded as the actual `tent/<version>` runtime, never a guessed model or person. Only a `human:` verifier produces `human-reviewed` trust; another verifier produces `machine-confirmed`, and no verifier is `unverified`. Trust is derived evidence, not an access-control boundary or a guarantee that the content is true.

Native timestamps use ISO 8601 with an explicit timezone. An invalid `stale_after` is an invalid-header diagnostic under the normal tree quarantine rules; it does not fail map or synchronization reads for the rest of the Workspace. At or after `stale_after`, inspection reports `behind`, independently of whether the Node is also ahead. A verification can anchor a Node when neither finding applies. Deprecated Nodes remain outside current context counts.

The Web API exposes derived `trustTier` on Node reads and writes. `POST /api/nodes/:id/confirm` takes a complete live `baseEtag` and optional `by`, preserving the body and generation record. Web saves and confirmation default to `human:<local-username>`; an explicit actor overrides that default. Confirmation uses the same mutation serialization, authentication, origin checks and CAS errors as document saves.

### Current context and drift

`workspace brief [--role <id>]` reports behind and ahead counts, then every invalid Node with its full Workspace-relative file path and reason. Every pending Card and returned receipt addressed to the Role in scope remains visible. The remaining priority is ahead Nodes, changed received sources, other unfinished Cards and behind details. Behind Nodes whose only problem is missing retained baselines are folded into one count with `tent workspace drift --json` as the inspection command. Optional detail fits a 4 KiB text/JSON budget; mandatory invalid Nodes, pending Cards and returned receipts may exceed that budget and are never omitted. After allocating actionable details, brief always appends up to 12 live root Nodes as `roots: [{nodeId, name, type, path}]`, reusing the current header catalog without reading bodies or constructing relations for navigation. Untyped Nodes use `type: null`. Root paths are complete Workspace-relative Markdown files; archived and invalid Nodes are excluded, children are not promoted. The entries follow actionable sections, may exceed the detail budget, and never displace them; `omitted.roots` counts additional roots and text directs them to `+N more · tent node list`. CLI discovery outputs contain no relative time fields; known times retain their absolute ISO values. It also shows changed sources of received Cards whose source goal is still ahead. Completed old Cards do not crowd out current requirements. Omitted details are counted; addresses are never cut into misleading partial paths. The optional Role filters Card inputs and received-source warnings; Node counts remain workspace-wide. A consumed Card without returnTo is complete; a consumed Card with returnTo remains in progress until returned. Card delivery never proves that a goal is fulfilled. Repeated inspection conflicts produce uncertainty instead of a false current state.

`workspace drift` pages ahead and behind Nodes, with both findings when a Node needs both. Each `node-behind` item includes the inspection's existing `materials`: occurrence addresses, tracking and goal context, states, recorded/current versions, reasons, and available structure dependency changes with their overflow count. These are evidence of dependency changes, not proof that the Node's text is outdated; unavailable or unanchored material stays explicit. Coverage accepts file, directory and prefix materials from any valid Node that is neither deprecated nor archived. A module is such a Node with at least one valid `sources[].track: structure` material, which must name a local directory or prefix. Ordinary file materials, untracked directories and legacy `resource` directories provide coverage but do not establish module status; once a Node is a module, all its attached materials count as members. Prefix syntax is one final `*` in the last path segment, matching tracked Workspace-relative paths beginning with the preceding text. Directory and prefix membership use Core's shared `structureMaterialCoverage` and `materialCoverageContains` authority, with the host platform's path comparison policy. Material paths use the normal declaration-owner resolution rules. Most-specific matching module material owns a file; equal specificity prefers file, prefix, then directory, followed by stable Node path/id order. A module's parent is its nearest module ancestor in the Node tree. These checks consume declared tracking metadata without modifying it or recording structural fingerprints.

The draft summary and live `check-modules --json` module facts include two current, derived fields. They are computed from repository evidence, never written into Node bodies or retained as coverage claims:

- `testedBy: string[]` lists distinct, sorted Workspace-relative test files with direct static imports into handwritten production members. File targets credit their most-specific module owner. A Go package target credits the owners of its direct production files and its directory owner; test evidence also rolls up to each module ancestor. Tests, generated files and vendor files are not production targets. No test execution, transitive helper coverage or implicit same-package reference is inferred. A missing entry does not prove that no test covers the module.
- `coChanges: {moduleId, sharedCommits, moduleCommits, ratio}[]` lists non-ancestor module pairs meeting the existing history thresholds below. `moduleCommits` counts eligible commits touching the current module, and `ratio` is `sharedCommits / moduleCommits`, so the two directions can have different ratios. The pair is selected using the less-frequently changed member's ratio and lift, as in the history rules. Entries sort by the other module's path and id. `allow:` markers suppress findings, not these facts.

Core's `MODULE_MAP_THRESHOLDS` defines these rules:

- `map.uncovered`: tracked files with no coverage, grouped by immediate parent directory. This rule cannot be excepted; generated and vendor files still need a covering Node.
- `map.unowned`: covered handwritten production code files without a module owner, grouped by immediate parent directory. It uses the same code classification as the size rules, excluding tests, generated and vendor files. Coverage by an ordinary Node does not establish module ownership. This rule cannot be excepted; add a directory or filename-prefix structure source to the responsible Node, or attach the files to an existing module. Module identity and the Stop entry point remain unchanged.
- `module.oversized` / `module.skewed`: only leaf modules with at least 20 handwritten production code files qualify; tests, generated and vendor files are excluded. A module must exceed 20% of repository production files, or strictly exceed three times the mathematical median of its other nonempty sibling modules. It must also contain at least two directory or filename-prefix groups of at least three production files each. Oversized takes precedence over skewed.
- `deps.cycle`: a pair has `module-load` imports in both directions, with at least three such imports in the smaller direction and a smaller/larger ratio of at least 10%. Deferred, type-only and compile-time occurrences contribute neither counts nor ratios; a separate loading occurrence of the same import still counts. Tests and `index.*` barrel files are excluded; ancestor/descendant module edges are internal. Go package targets use directory-material ownership, or the unique module owning all direct non-test Go files in the package, not a fabricated target file. A package split among modules without a directory owner is reported as unassigned, rather than inventing a dependency edge. Execution filtering does not remove dependency edges, test-attribution evidence or unassigned-import diagnostics.
- `history.always-together`: a pair shares at least five commits, at least 90% of the less-frequently changed member's commits, and lift of at least two. Lift is shared commits times eligible commits divided by the product of individual commit counts. History follows first-parent and excludes empty commits and commits changing more than 50 files. Ancestor/descendant module pairs are excluded from both history rules.
- `history.generated-apart`: the same history thresholds, but more than half of at least one module's member files are generated. It replaces `history.always-together` for that pair.

A size rule is excepted when its exact positive marker `allow:<rule-code>` appears in that module's body, without spaces around the colon. A pair rule is excepted when either module has a body line containing that marker and a resolvable Markdown link to the other module, such as `allow:deps.cycle [other](../other/other.md)`. Merely mentioning a rule code, including saying it must be fixed, does not declare an exception. No prescribed heading or duplicate declaration is required; an unrelated link, a link on a different line or a code-fenced link does not declare a pair exception. `map.uncovered` and `map.unowned` cannot be excepted. Rules in active descendant prompt Nodes apply to their nearest module ancestor, stopping at nested modules. Pair links resolve relative to the prompt document before applying to that module. Goal and output descendants do not supply rules. Exceptions never change stored documents or hide inspection failures.

Import extraction is a pure Core function over Workspace-relative POSIX paths and caller-supplied file contents. It resolves literal TS/JS imports, exports, require and dynamic import calls through relative paths and scoped `tsconfig*.json` paths aliases; Go module-local imports target package directories; Python imports resolve repository-local files under the root, `src` or `lib`, including relative imports. Extensionless script targets try `.ts`, `.tsx`, then `.d.ts` before JavaScript suffixes; directory index candidates likewise try `index.ts`, `index.tsx`, then `index.d.ts` before JavaScript indexes. It never executes source, package resolvers or configuration. Comments and quoted examples do not create edges. Test directories (`test`, `tests`, `__tests__`, `spec`, `testdata`, `fixtures`), `.test`/`.spec` files, Go `_test.go` and Python `test_*.py` are excluded from dependency edges. Unsupported languages supply no edges. A Go edge retains a directory target; other resolved targets are files. Edges are deduplicated and ordered; unresolved relative imports and unparseable configurations are reported separately, without claiming complete language/compiler analysis. Source/configuration reads never follow symbolic links.

Every `RepositoryImport` has a mandatory `execution` classification. All classes remain dependency evidence, including for structure observations, module edges and direct test attribution. Occurrences with the same importer, target and specifier but different execution classes remain distinct; an eager occurrence cannot be erased by a type-only or deferred occurrence.

- `module-load`: a source-level runtime load outside a function body, including ordinary Python imports, script imports/re-exports and literal top-level `require`/dynamic `import`, PHP include/require expressions, and Go package imports (which establish package initialization order). Ordinary conditional branches are conservatively included; this is possible loading evidence, not proof that the branch runs.
- `deferred`: Python imports in function/method bodies (including nested and async definitions), script literal loads in function/method/arrow bodies or default parameters, and PHP include/require expressions in function/method/closure/arrow bodies. A class body in Python executes while the class is defined and inherits its enclosing context; a method body is deferred.
- `type-only`: TypeScript declaration-wide `import type`/`export type`, type-only import-equals declarations, all dependencies in `.d.ts`/`.d.mts`/`.d.cts` files, and Python imports under a recognized positive `TYPE_CHECKING` suite. Python recognizes imports of `TYPE_CHECKING` from `typing`/`typing_extensions`, their aliases, and qualified module aliases, with optional parentheses. Nested suites inherit the context. Runtime `else` branches, negated guards and compound conditions do not become type-only by assumption.
- `compile-time`: Rust module/use declarations, Java imports, C# using directives, C/C++ preprocessor includes and PHP namespace use declarations. These establish source/name dependencies; the extractor does not claim that these declarations load or initialize the referenced code at runtime.

Classification uses lexical source context, not a call graph, interpreter, type checker or build pipeline. It does not evaluate immediate function invocations, decorators, runtime rebinding of typing guards, arbitrary constant conditions or compiler-dependent semantic import elision. In particular, inline TypeScript modifiers such as `import { type T }` and `export { type T }` remain `module-load`, as `verbatimModuleSyntax` can retain an empty import/re-export with a module specifier; mixed type/value declarations do too. Only declaration-wide type syntax guarantees erasure independently of those emit choices. Complex script type expressions and class field initialization are not analyzed as execution contexts.

`GET /api/modules/deps` is a separate authenticated read query returning `{basis: {head}, modules: [{nodeId, files}], edges: [{from, to, imports}], cycles: [[nodeId]], uncovered, unresolved, computedAt, fresh, mode, reason?}`. They use the shared material coverage resolver; the longest matching prefix wins for each file, and equally specific modules all own it. `files` counts distinct nonignored regular Workspace files owned by each module, including tests and non-code files. Empty modules remain in the result. Symbolic links, `.tent`, `.git` and directories with their own `.git` metadata are excluded. An empty module list is valid.

The query reuses scan's static import extractor and exclusions. A directed edge goes from an importing file's module to its dependency's module; self edges are omitted. `imports` counts deduplicated extractor records for that module pair. A Go package import first targets modules with the most specific structure-tracked directory material covering that package directory, retaining equally specific shared owners. Finer filename-prefix modules may own the package files without taking over the package import. Without a covering directory module, the import contributes once to each module owning every production Go file directly in the target package. If neither kind of package owner exists but some package files have owners, that import contributes one to `unresolved` and no edge. Completely unowned packages contribute only uncovered files. `uncovered` counts distinct unowned files participating in resolved local imports or reported local import issues; `unresolved` otherwise counts local import issues. External dependencies and unsupported languages add neither count. Unparseable import configuration fails with `INVALID_INPUT` (HTTP 422), rather than returning an apparently complete graph. Modules and edges have stable identifier ordering. `cycles` contains the strongly connected groups of two or more distinct module Node ids in these aggregated edges; it does not enumerate paths or classify a dependency as an error. Each group is sorted by Node id, and groups have stable identifier ordering. Acyclic and empty graphs return `[]`. Cycles share the graph's basis and freshness; incomplete import extraction can omit cycles.

`basis.head` is the enclosing project Git HEAD, resolved directly from its ref (null for unborn or non-Git workspaces). The response does not report Git working-tree cleanliness. Computing a graph observes current files and Node declarations, including successive edits while HEAD remains unchanged. It writes no project or Tent documents, Git history or index, executes no configured Git filters, and never runs Git status or as part of a full snapshot; disposable input caches follow the common read rules. Process-local source and import caches are derived from the live source paths and validated contents; HEAD is not a cache key.

Every dependency request validates its own inputs and returns `fresh: true` and `mode: verify` on success. `computedAt` is the UTC ISO time that query finished computing. The service starts no dependency watcher and shares no previous or in-progress graph with another request. Failed current reads report their error rather than a previous graph.

`GET /api/map` is the first-screen read: `{workspace: {id, name, revision, generatedAt}, nodes, modules}`. Each Node contains `id`, `name`, `path`, `notePath`, `depth`, `type`, `tags`, `status`, `archived`, `parentId`, `childIds`, `stale`, `invalid` and optional `invalidReason`. It preserves current tree order, hierarchy and invalid-header diagnostics, and reuses that same header catalog for module ownership. `modules` contains the dependency query's graph and basis, without its HTTP freshness fields. `stale` means explicit `stale_after` expiry at `generatedAt`; material ahead/behind findings remain an on-demand `/api/sync` read. The map excludes Node bodies, Card/Role documents, relation details and retained history. Existing Node/Card/Role body and history endpoints, and the full `/api/snapshot` aggregation, supply details on demand.

The map revision hashes Workspace identity, exact validated Node headers, projected hierarchy/expiry and module graph/basis. It is distinct from the full Workspace revision and must not be compared with `/api/revision` or `/api/sync.revision`. Card/Role or Node body-only changes do not directly change the map revision. Scale acceptance uses the same 10,000-file, 2,000-Node, 5,000-Card fixture: brief one second, native Stop 300 ms, and first actual UI data view one second remain targets. Record measured time honestly; loading placeholders, startup subtraction or background warm-up cannot replace those measurements.

`GET /api/sync` returns `{revision, nodes: {[nodeId]: {ahead?: {since?, reasons}, behind?: {reasons}}}}` with only Nodes needing attention. The revision is read before inspecting materials so the Web UI can load its first snapshot and sync result concurrently and recheck when their revisions differ. Each request inspects materials using its own file-state-validated inputs. The map overlays both marks when needed and refreshes on open, focus and save, and every 30 seconds while the page is visible, because a material edited outside Tent leaves the revision unchanged; a timed read never queues behind one in flight. Its counts match the brief. An output completion time is omitted when its explicit `stale_after` expires. This uses its current provenance without inspecting its own or ancestor materials; expiry can change completion without a new revision. When the latest sync result shows an output with a completion time is behind, the Web UI requests `GET /api/snapshot?fresh=1` once for that disagreement; the service builds that request at the current revision without retaining a snapshot result for later requests. Card delivery state is independent of these findings. Attention text reads reasons by kind: changed or deleted materials by file name, missing baselines, unverifiable materials and expiry as such; an ahead goal says whether it has no current output or no output with a matching goal baseline. No onset time is inferred.

The Web page shows the map. Roles sit on it as a robot dock at the top left: one row per Role and one for the public area, each counting in-progress Cards (`consumed` with `returnTo`), pending input and returned receipts awaiting collection; folded, the dock is a column of faces with the in-progress and waiting counts on badges. Hovering a robot, or clicking it to keep it lit, marks the Nodes carried by the Cards on its desk (pending input, in-progress work or returned receipts addressed to it) and draws lines to them. Dropping a Node, a picked set or a region's cards on a robot starts a browser draft for that Role with those Nodes as sources in order. It only observes; nothing on it waits for the user. Behind findings whose reasons are only missing baselines or unverifiable materials draw quieter on the map, since nothing is known to have changed. The CLI brief and drift keep per-Node findings and identifiers for targeted review. The snapshot derives `outputAt` from the earliest valid `generated.at` or `verified.at` in each current output, normalized to UTC ISO. Missing timestamps supply no completion time; commit events are not replayed. These views add no document fields or independent completion state.

The Web UI shows a Node's own file by the suffix of its `resource`, never by its type or tags: `.html`/`.htm` in a sandboxed frame without scripts, with a new-tab view that keeps the same sandbox; images in place; `.mp4`, `.webm`, `.mp3` and `.wav` in native players; Markdown and code as before, with the path among the properties; any other file as a card with its name, size, Workspace-relative path and a copy button. Trees, relation lists and the map mark such Nodes with a file icon and suffix. A missing file is marked on its card and on the map rather than failing the page. A remote URI is shown with an external link and never fetched or embedded. `GET /api/files?path=` serves a file inside the Workspace root after following links, as `application/octet-stream` unless it is an image, HTML, audio or video, with `Content-Security-Policy: sandbox` and `nosniff`; absolute paths, `..`, backslashes and `.git` segments, or a link leading outside the root, return 403 `FORBIDDEN_PATH`. Audio and video are limited to 200 MB, other files to 20 MB. `POST /api/files/info` with `{paths}` returns each file's size and modification time, or null when it is missing or refused; the page reads it again when the revision moves and when sync flags are reread.

Ordinary confirmation keeps a generated output's completion time, so it does not reappear as newly finished on the home page. No history is replayed and no timestamp field is added; verification still keeps only the latest entry per actor. A verified-only imported output can move forward when the same actor overwrites its sole earlier verification. Content rewrites refresh `generated.at`: an older retained verification keeps the completion time, otherwise it moves with generation.

## 4. Role

A Role is one OKF v0.2 §4.1 document at `roles/<roleId>.md` with `type: role`, `id: role-…` and an optional readable title. It holds a work direction, boundaries, methods and selected references. Shared business facts remain Nodes. The Markdown is the authority; there is no metadata registry, reverse Card list or implicit responsibilities import.

`role list` reads bounded headers without capture and excludes deprecated Roles by default. `--include-deprecated` includes them, with a trailing `deprecated` marker in text; JSON retains status. `role create` saves a new document; identity cannot reuse a path already retained in Tent Git. `role show` returns a bounded body/raw page with exact ETag without capturing history. `role write --base-etag` uses raw CAS and the shared mutation lock; no-op saves can capture editor bytes without rewriting them. Unknown metadata survives and lifecycle status stays local.

Role selection is explicit. Reading it does not bind a Session, claim occupation, read every related Node, create missing context, repair an invalid document or resume a pending structural operation. Missing or invalid Role documents are diagnostics. A new host conversation may explicitly read the same Role to recover its maintained direction.

`deleteRole(roleId, {baseEtag})` / `role delete <roleId> --base-etag <etag>` removes the Role document and records `role.delete` in Tent Git. Missing or stale ETags reject deletion; a missing Role is not a successful delete. There is no recycle bin or restore command: use lifecycle `status: deprecated` for reversible archival. The deleted document remains in Tent Git history and its id/path cannot be reused. Deletion uses the same two-phase `delete.pending.json` isolation, validation and cleanup as Node deletion. Deletion and writes with lifecycle `status: deprecated` share one locked Card check. Valid, nondeprecated Cards block either operation with `PENDING_CARDS` and all blocking Card ids when the Role is their pending target, their `returnTo` in pending/consumed/returned state, or their `receivedBy` while consumed with `returnTo`. Collect returned Cards, finish outstanding returns, move pending targets, or deprecate blocking Cards before retiring the Role. Closed Cards, consumed Cards without `returnTo`, and deprecated Cards do not block deletion. Returning releases the receiving Role; collection releases the return recipient. Existing `receivedBy` and pinned Role source versions remain unchanged and readable from Git. Ordinary Node links are not rewritten; check continues to diagnose the broken references. A directly deleted target Role remains a Card diagnostic and never makes a targeted Card public.

## 5. Card

A v3 Card is one Markdown document at `cards/<cardId>.md` with `type: card`, `id`, `schemaVersion: 3`, optional `title`, ordered `sources`, optional target and `returnTo` Role ids, delivery fields, and the prompt in its body. Creation publishes it immediately and requires a prompt, sources or both. Sources use OKF v0.2 §5.1 resource declarations; explicitly selected Nodes and Roles receive Git `{commit,path}` versions. External addresses are not fetched or captured. Cards do not record a sender or creator Session.

Creation captures only selected internal sources before publishing the Card. A supplied Git source is validated without reading its current live path; a live rename or deletion does not prevent reusing a valid retained source in a new Card. The first reachable path-addition commit is the input baseline, and identities retained in history cannot be reused. There is no separate publication operation or persistent Card draft. Undecided requirements belong in Nodes with `status: draft`. The browser keeps unsent Card content locally and submits it directly to `POST /api/cards` when sent.

Published body, title, ordered sources, `returnTo` and unknown metadata are immutable input. Hand-edited input remains raw-readable but reception and management operations reject `INPUT_CHANGED`. Requirements and decisions belong in Nodes; edit those Nodes when they change. Live Node moves do not rewrite old Card input or pinned sources. For in-progress Cards (`consumed` with `returnTo`), brief compares pinned Node bytes with current bytes by stable Node ID. An edit or missing source asks the receiver to reread the current requirements; an unrelated commit alone is not a content change. Goal ahead/output comparisons remain independent of Card completion.

Routine brief and UI revision reads skip Cards retained in Tent Git as `closed`, `consumed` without `returnTo`, or `deprecated`. Their paths form a disposable completion list in `.tent/.git/tent-material-cache/`, updated from changed `cards/` paths when Tent Git HEAD changes. Readers enumerate `cards/` once and skip listed paths before validating headers or hashing current bytes. A missing, corrupt or incompatible list is rebuilt from retained Card documents with the same result. Native edits to completed Cards are reported by `workspace check`, not brief; unfinished and newly discovered Cards retain current-file validation and malformed-header diagnostics. Explicit `card show`, `card take`, state-filtered lists and `--include-deprecated` still read current files. The UI map does not load Cards; Node details and history load them on demand. No Card moves or file-format changes are involved.

Each Role has one pending queue; the public area is another queue, visible to all Roles but silent by default. Default order is publication time ascending, then Card id by code-unit comparison. Its effective key is the UTC ISO publication timestamp (including milliseconds) followed by `|` and the Card id. An optional `order` extension replaces that complete key. Generated keys use printable ASCII `!` through `~`, find a fractional position between adjacent complete keys, and end with `~<this Card id>`; this suffix keeps generated keys distinct from both default keys and other Cards' generated keys. At the tail, the generated key appends `~<moved Card id>` to the previous last key, retaining its timestamp prefix so later publication times still follow it; repeated tail moves may lengthen that key. Creation neither reads a queue nor assigns order, and same-second default keys still use id order. Comparisons are lexicographic, not locale-aware. Equal effective keys use publication time then id. No sidecar queue or dependency field is stored.

`card move <id> [--to <roleId> | --public] [--before <cardId> | --after <cardId>] --base-etag <etag>` changes a pending Card's destination and/or queue position; the CLI requires at least one destination or position option. The reference must be a different, nondeprecated pending Card in the destination queue. Omitting the destination retains the current queue; omitting position puts the Card last. An empty destination queue needs no explicit order. Only the moved Card is written, under the reception mutation lock and observed ETag, with `card.move` history. Body, sources, title and `returnTo` remain immutable. Clearing the target returns the Card to the public area. An already-correct position validates its ETag without adding a commit. A new target must differ from `returnTo`; deprecated or received Cards cannot move. Hand-edited target or order changes conflict with retained management state. The thin HTTP move endpoint accepts `baseEtag`, optional `target` (null means public), and optional `before` or `after` with the same semantics. Snapshot Cards expose Core's effective `orderKey` for queue presentation; sorting and moving do not infer progress from goals.

`card deprecate <id> --base-etag <etag>` cancels a task through lifecycle `status: deprecated`, including after reception. It preserves reception and immutable input, uses CAS and records the management change in Git. Lists and brief omit deprecated Cards by default; `--include-deprecated` includes them. Explicit show or take warns and exposes current references, while preserving the ordinary Role gate.

`card list` reads published Cards without capture and returns delivery state, `returnTo`, `receivedBy`, `result` when present, publication time, optional `order` and the effective `orderKey`. With `--state pending`, each queue uses effective-key order before pagination; a selected Role precedes opted-in public Cards. Other lists retain publication time descending, then id ascending, with unavailable times after dated entries. Brief places pending queues before other active inputs and preserves their effective-key order. Titles, reception states, filters and header diagnostics use live files; changed files carry `uncaptured: true`, including invalid headers. Invalid live headers remain unavailable rather than displaying a historical title. An unretained handwritten file is not a published Card. `card show/get` previews a bounded body/raw page without receiving or executing it. Omitted oversized source metadata has a raw read address rather than truncated executable references. An exact Node source can be read using `node get --version-json`.

`card watch --role <role-id> [--include-open] [--timeout <seconds>]` waits for committed, nondeprecated pending Cards addressed to the supplied available Role, or returned Cards whose `returnTo` names it. It emits that Role's pending queue first, then the public pending queue only when `--include-open` is set, then returned results ordered by retained `card.return` time ascending (id breaks ties; unknown return times follow dated returns). Public results carry `fromPublic: true` in JSON and `[public]` in text. Taking a public Card claims it through `receivedBy`; concurrent claims share the reception lock, and the loser receives `RECEPTION_CONFLICT` with the winning receiver. Public Cards never wake the default watch. Watch checks immediately, then reads only the independent Git HEAD every three seconds while unchanged; a changed HEAD triggers another committed Card and timestamp query at that exact HEAD. It may read an existing validated history cache, but never creates or refreshes one. It does not capture documents, change baselines or write files. Matching Cards return immediately with one text line per Card containing its id, optional title and `tent card take <id> --role <role-id>`; a returned Card instead prints `card-ID returned by role-X: <result>` and remains visible until taken by its return recipient. JSON returns an array including `state: returned`, `receivedBy` and `result` for returned Cards. Exit codes are 0 for input, 2 for timeout with no output, and 1 for errors. Omitted timeout waits indefinitely; zero checks once. Watching neither receives Cards nor registers waiting Sessions. Agents choose their own host wakeup mechanism and ask before creating a new persistent automation.

### Reception and outputs

State is `pending`, `consumed`, `returned` or `closed`. Pending has neither `receivedBy` nor `result`. Creation accepts an optional `returnTo` naming an available Role, different from `target`. It is a delivery address, not a sender identity, and stays immutable. Without `returnTo`, an untargeted Card may be received with or without a Role; with `returnTo`, reception requires an explicit different Role so that only that receiver can return it. A targeted Card requires its specified available Role. Missing, invalid, deprecated or unsupported Roles are diagnostics, never an open fallback. Existing Cards need no conversion or format version change: without `returnTo`, take completes them.

`card take` validates published input and retained management state under the shared mutation lock. For pending input it records `consumed` and `receivedBy`, then returns a bounded input page. Retries with the same Role choice return `replayed` without authorizing another execution. For a returned Card it requires the available `returnTo` Role and records `closed`, preserving the original `receivedBy` and result. Only that return recipient can replay collection of a closed Card. No reception operation takes a Card Git version.

`card return <id> --role role-ID --result TEXT` requires a consumed Card with `returnTo` and the explicit receiving Role. It records `state: returned` and `result` in the same document. The result must be nonempty, single-line text of at most 200 Unicode characters (code points); longer details belong in Nodes, whose ids may appear in the result as UI links. No separate return-author or result-Node fields are stored. The same exact result is an idempotent replay, including after collection; a different result is rejected. A return receipt carries no decision-needed flag. Further work or a decision requires a new Card, while the decision itself belongs in a Node.

Cards have delivery state only: pending input, received work, returned result and collected result. Without `returnTo`, consumed means complete; with it, returned means complete and closed means the result was collected. In-progress Cards are exactly consumed Cards with `returnTo`. No Card read surface derives `progress`, goal counts or output lists. Pinned goals retain their own ahead/output semantics, independently of Card delivery; changing or confirming goals or outputs never retracts a Card's return.

`node link-output --card <id>` records the response in the output's `sources`. An explicit response may cross Roles, but its Card must already be received, must not be deprecated, and must have a pinned goal source on the new output's goal chain. Automatic inference requires an explicitly supplied Role matching the received Card's `receivedBy`, and exactly one matching consumed Card with `returnTo` for the selected goal. A missing or different Role cannot silently attribute the result to another receiver: choose a Card explicitly when relevant received Cards exist. Multiple matching candidates also require an explicit choice. With no relevant Card, ordinary output creation still works without a Role. A missing explicit Card is rejected with a human-readable message without a filesystem path, before creating an output or its sources. The write receipt identifies the selected Card when one is attached. A Card source is a response relationship, excluded from material comparison. Existing explicitly recorded responses keep their attribution; no new automatic backfill accompanies this change. Questions, research and pending decisions use prompt Nodes; any current output answers, whatever its tags. No return Card is required.

Manual reception fields differing from retained state remain raw-readable and diagnostic. An explicit take or return may finish its interrupted pending-to-consumed, consumed-to-returned or returned-to-closed transition when input, target and status are unchanged and the saved receiver/result exactly matches the request; it captures those saved bytes. Other management edits remain conflicts. A subsequent identical take is a replay and adds no commit. Lifecycle status is independent. File/Git failures can follow a saved document; reread before retrying. Reception proves neither comprehension nor exactly-once execution.

## 6. Persistence, recovery and historical data

Sketches are workspace material files: use Excalidraw itself to save a sketch, then reference that file from a Node.

All current document mutations use the Core workspace lock. Short-lived CLI processes share an exclusive on-disk mutation lock and directory guard for its bookkeeping. A live PID is not evicted because of age alone; release checks its ownership token. A crashed guard is reclaimed when its PID is absent, retaining a small tombstone directory so delayed contenders cannot displace its successor. PID reuse can require manual cleanup after all Tent writers stop; the timeout identifies the guard path. No persistent HTTP Service, watcher, event bus, Session token service or RPC passthrough is part of the current runtime. `tent ui` is an explicitly started foreground exception: a loopback HTTP server for the bundled UI, ending with its process, without Session registration or filesystem watchers. The UI polls `readWorkspaceRevision` for refreshes; ordinary browsing is read-only, while explicit edit reads capture their basis.

`tent ui [--workspace <path>] [--port <number>] [--no-open] [--idle-timeout <seconds>]` resolves an existing workspace, prints its URL and opens the default browser unless suppressed. It remembers opened workspaces in a per-user file outside `.tent`; the page can open other existing workspaces in the same process, and Ctrl+C closes all of their servers. The server uses a fresh launch token, checks Host/Origin, and writes through Core's ETag and workspace lock. Its API is private to the matching bundled frontend, not a public integration protocol. npm and plugin distributions include UI assets; development snapshots and source maps are excluded.

The Node reader opens from map metadata and reads its body, identity history, related Cards and outgoing relations independently. It does not request the workspace snapshot merely to open a Node. Incoming references are a separate, explicitly expanded whole-workspace query. Loading, empty results and failures remain distinct; failed sections can be retried. The existing workspace revision signal refreshes open sections, including body-only edits that do not change map metadata. History follows identity through moves; related Cards retain each matching source version, including deprecated and completed Cards. Pinned sources resolve identity from verified retained bytes before matching the selected Node; missing or invalid versions remain diagnostics and never retarget to a new occupant of the old path. These ordinary reads do not capture, repair or mutate documents.

Authenticated `GET /api/revision`, `/api/sync` and `/api/snapshot` reads each have at most one active calculation per workspace. Calls arriving during that calculation form one waiting batch; its document observation starts after its callers arrived, so a newer request never joins an older observation. Waiting callers share that batch's calculation and serialized body. Disconnected callers are removed, and a batch without callers does not run. An active Core read can finish, but the service skips later read phases and response serialization if nobody remains. Snapshot `fresh=1` and `If-None-Match` decisions remain per caller. Completed results are not retained between batches, and no polling interval, file validation rule or watcher is introduced.

The optional idle timeout is a positive whole number of seconds (at most 2147483, the timer limit); without it manual UI lifetime is unchanged. It closes the entire owned UI session after that interval without a successful authenticated API response. Successful page polling counts as activity; static requests, rejected authentication, invalid Host/Origin and failed API requests do not renew it. Activity in any workspace opened by that session renews the same deadline, so switching workspaces does not close an active page. Closure cancels the timer, closes all owned servers, and removes CLI signal listeners. Init uses 300 seconds and a host-visible, stoppable background command, never a detached daemon. The CLI prints the address and idle interval even with `--no-open`.

Recognizable retired stores at the root of `.tent`, such as an old `snapshots/objects` layout, produce one consolidated diagnostic before Node indexing. They are neither imported nor deleted automatically. Names such as `notes` or `snapshots` remain valid for ordinary Nodes and grouping folders; a matching identity document identifies a current Node.

Move/rename saves a pending plan before changing directories, links and order. Removing the verified plan commits the operation. The next mutation rolls back an interrupted move under the existing lock; conflicting external bytes preserve the plan and stop recovery. Reads do not resume it. This covers process interruption, not a promise of power-loss durability or control over external editors. If recording a completed rename in Tent Git fails while Tent Git HEAD is still the commit read after the move, the rename is rolled back under the same lock before the error is reported, so disk and Git keep the old name. If HEAD already records the new name, or Tent Git cannot show whether it does, the disk keeps the new name, the error states which case applies, and `workspace check` reports any remaining difference between disk and Git.

Node deletion records exact primary data and associated order writes in `delete.pending.json`. Moving the primary object to quarantine is the logical deletion point; subsequent mutations can finish verified cleanup. Reused identity or changed associated bytes causes conflict. Export rejects pending operations.

## 7. Export

`tent workspace export --output <new-directory>` creates a separate complete-graph directory and byte inventory. It preserves persistent documents, unknown metadata, order, Git history, Roles, Cards and ordinary retained files, including any existing attachments directory. `attachments` is not a reserved directory name: valid identity documents there follow the ordinary Node rules, and body links use normal file handling. Credentials, locks, runtime state, disposable checks, `.git/tent-material-cache` and temporary files are excluded. Export checks version 1 records in all copied Git commit objects, including unreachable commits, for machine-absolute paths; unversioned historical records are preserved verbatim. Source data is never repaired or switched.

Export inventories the source under the workspace lock, copies and verifies it, then checks source membership/hashes again under the lock before publishing. Pending operations, invalid required history or missing referenced local materials prevent publication. Filesystem copying does not claim a transaction with arbitrary external editors.

Live standard references in Node, Role and Card documents inside `.tent` are checked against copied files/directories. Ordinary files are copied as bytes without interpreting frontmatter, even when they have a `.md` suffix; malformed frontmatter at native document paths still fails validation. v3 Card sources validate against copied reachable Git history; their old paths need not exist live. External workspace targets and absolute URIs are listed in `externalNotPacked` with origin, declaring path and occurrence index; bytes are not copied. Bare sources, invalid locators and nonstandard metadata appear in `unresolvedMaterials` without guessing or rewriting.

## 8. Plugin and Hooks

The four Skills are `tent-init` for empty setup, `tent-node` for relevant input and Node maintenance, `tent-role` for persistent work direction, and `tent-card` for recorded prompt input. Role and Card are independent optional objects. Command details live in on-demand references. Skill use requires no initial decomposition, fixed reading sequence, per-turn Node count, full-tree verifier.

One build produces Codex and Claude Code packages from the same bundled CLI, four Skills, references and SPEC. Each host has a thin shell for its manifest, Hook definitions and launcher, interface metadata and Hook instructions. The build places those instructions at `tent-init/references/host-hooks.md`; shared Skill text is host-independent. Each launcher explicitly selects its host. The plugin uses its installed package path and bundled runtime dependencies. It does not guess an executable from cwd, store graph data in a plugin cache, install global Hook copies, or configure MCP. npm delivery installs its declared runtime dependencies separately. Build/install/trust and real event delivery are distinct checks; package presence does not prove native activation.

`tent --version` displays the version, commit and build-session start time. `tent version --json` returns `version`, `commit`, `builtAt`, `dirty` and `runtimePath`. Built CLIs embed their identity independently of their installation path and adjacent package metadata; source execution has `builtAt: null`, and watch rebuilds share their build session's identity. Unknown Git identity remains null. This is local provenance, not a network update check.

SessionStart runs the native-edit collection boundary before returning the available workspace, current package entry, build identity and a short `workspace brief` hint, without loading the brief. It collects pending native Node edits under the mutation lock; when no edits are pending, it takes no write lock and performs no document write. It writes no session baseline. It reports a commit mismatch only when the workspace is positively identified as a Tent source checkout; different commits do not establish which is older. Its returned context includes no Role/Node bodies or repeated Skill descriptions, and it creates no Session registration or prompt baseline. There is no PromptSubmit or SessionEnd registration. Each package includes native SessionStart and Stop definitions; the published Codex definitions stay byte-identical. Role selection remains explicit.

Stop runs synchronously. It continues the Agent only when this turn has observed writes covered by a module, the turn was not cancelled, and native `stop_hook_active` is not true. Codex receives `{decision:"block",reason:message}`; Claude Code receives `{hookSpecificOutput:{hookEventName:"Stop",additionalContext:message}}`. Qualify delivery and one continuation on each actual frozen host. An active Stop is silent even after the continuation used tools; duplicate events are silent independently of the host's own continuation limit. No observed writes or only uncovered writes produce no review.

Observed file paths in any linked worktree of the same repository are made relative to that worktree’s root before matching the main checkout’s modules, regardless of the session directory. Relative Codex apply_patch paths resolve from the session checkout root. `.worktrees/` is not itself an excluded activity path; repository pointers determine ownership. Files in other repositories do not match these modules. Branch directory renames may therefore remain unmatched. Stop asks about rules and decisions without requiring a merge; it does not read branch content for material state. Checkout routing reads only Git pointer files, without starting Git.

Activity observation reads backwards in chunks from the transcript end until the requested turn begins, with an 8 MiB read limit, using the native turn identity: Codex `turn_id`, or Claude Code `prompt_id` matched to top-level user `promptId`. Claude versions without this identity are silent; no identity is invented. Successful structured reads and file changes provide evidence. Claude Read, Write and Edit facts require paired successful tool results matching the structured file address; sidechains do not belong to the turn. Arbitrary shell text or opaque tool calls are not guessed into file facts, and no HEAD diff supplies turn membership. Repeated Codex contexts for the same turn do not replace its start; Claude tool results and sidechains are not prompt starts. A turn whose beginning falls beyond the limit and unrecognized activity retain uncertainty. Cancelled turns emit no questions. Stop does not hash files or persist session file observations. Intent signals require explicit decision language such as “决定”, “确认”, “改成”, “新增需求”, “decided”, “confirmed” or “agreed”; ordinary requests such as “请”, “需要”, “please”, “need” or “fix” are not signals. Synthetic heartbeat and environment instructions contribute none. A turn with explicit Node or Card write evidence does not receive another intent question.

A module is a current valid Node holding at least one directory or prefix material in `sources` with `track: structure`. Ordinary evidence directories and top-level `resource` do not make modules; tags have no effect. Module names match declared addresses alone, regardless of whether the file is ignored, tracked or unavailable. Core owns membership parsing: a prefix has exactly one `*`, at the end of its last segment, and matches the corresponding Workspace-relative path prefix. For each written file, only the most specific covering modules are named; equally specific modules are all retained. Each name includes its ancestor name chain, Node id and readable Workspace-relative file path such as `.tent/Core/Card/Card.md`, without ancestor bodies. Before truncation, modules are ordered by the number of distinct files written in this turn, descending, then by Node path. At most five modules and eight files per module are shown, with `+N more modules` for omitted modules.

The review uses this text, with module lines filled in:

```text
Tent turn review. This turn changed files that these Nodes cover:
- <ancestor names / name> (<nodeId>, <path>): <file>, <file>
Tent keeps what code cannot hold: a rule or a rejected option that also binds code this turn did not touch, or a dead end. A lesson about these lines belongs in a code comment or a test.
If one of these Nodes now says something this turn made wrong, edit that sentence in its file. If this turn produced something worth keeping, add one short section: tent node append <nodeId> --heading <title> --body -. If neither applies, reply that nothing needs recording; no command is needed.
```

The same message merges English questions with candidate answers about possible new intent/decisions. The `Update existing <goal-id>` answer selects the first goal among this turn's matched modules in the order above; when none is a goal, only the create and discussion answers remain. Observation uncertainty remains internal and adds no incomplete-observations message. Stop does not inspect or ask about unlinked outputs or behind Nodes. The next input-side brief reports behind Nodes. Stop performs no file availability or ignore lookup. Core accepts a plain UTF-8 text byte limit and has no host type or return envelope. Each CLI host adapter owns transcript parsing, native turn identity and the return format. The CLI deducts wrapper bytes before asking Core for text, then tightens that limit for any JSON escaping overhead. Complete host JSON, including encoding overhead and its final newline, is at most 2 KiB; on overflow remove filenames, then module lines, and shorten question fields without dropping a question kind. The fixed review text remains complete. The Agent answers through normal Node maintenance after reading the necessary live context.

The synchronous path never captures native Node edits, inspects workspace synchronization, observes material versions or acquires/waits for `mutation.lock`. Native edits are collected at the next normal Tent command boundary, including a `node append` run by the Agent. Active, cancelled and no-write events return before loading the material index. An exclusive empty claim in `.tent/temp/stop-reviews/`, keyed by a SHA-256 of native host/session/turn identity, permits at most one review response for a repeated event even across concurrent processes; it has no global lock or retry and stores no transcript, file content or hashes. A crash after claiming but before delivery can lose that review. A claim write failure emits no continuation. This is per-event deduplication, not suppression of later turns that happen to write identical bytes.

The persistent incremental material index uses `.tent/.git/tent-material-cache/stop-material-index.json`. Each lookup checks directory and header file states using the same state fields and racy rule as other read caches. A changed directory is enumerated again; a changed or racy header is physically read again. A change to topology or header content rebuilds validity, hierarchy, duplicate ids and material membership through the same Core catalog and coverage rules. Body text and sibling display order do not affect this index. Missing, corrupt, incompatible or unwritable caches fall back to direct calculation without changing the result. Cache writes change no project file, Node/Card/Role document, Git commit or reference. No daemon or watcher maintains this index, and it supplies no ignore rules. Reads are not an atomic snapshot of concurrent edits; a held workspace lock must not delay Stop. Native hook cost and full Agent continuation cost remain separately reported.

Module freshness against code content is best effort: writes not observed this turn, including shell or external editor changes, cancelled turns and undelivered reviews receive no question. A rule that must follow particular content needs that file or SPEC section as content material. This Stop membership rule does not change existing material fingerprints or baselines; structure fingerprints are a separate feature.

A Hook notice proves no semantic synchronization. Agent judgment and normal maintenance remain necessary. Native host identity, trust and synchronous delivery must be verified in the actual host, including one continuation and no tools when nothing needs recording; synthetic JSON tests only validate the handler.
